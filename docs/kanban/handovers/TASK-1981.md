**Decisions & gotchas**
- `tickets.id` is `uuid` on PostgreSQL (`defaultRandom`) and text on SQLite, the same as `giveaways`. The ticket said "text primary key, UUID"; using `uuid` avoids a `TEXT_ID_COLUMNS` entry. The repository generates the id with `crypto.randomUUID()`.
- `openTicket` runs in `withTransaction`: insert the settings row `onConflictDoNothing`, then `UPDATE ... SET next_number = next_number + 1 RETURNING next_number`, number = returned - 1, then insert the ticket. The atomic UPDATE row-locks on PostgreSQL, so concurrent opens (tested with `Promise.all` of 5) get 1..5. A failed insert (duplicate channel) rolls the increment back; tested. It joins a caller's `tx` (rollback tested).
- `openTicket` creates the settings row with `is_enabled = false` when none exists. `getSettings` returns `null` when no row exists, so TASK-1982/1983 should treat null as "tickets off, defaults".
- `upsertSettings(guildId, patch)` takes a patch that excludes `guildId` and `nextNumber`, so saving settings can never reset the counter.
- `close(ticketId, { closedBy, reason?, closedAt? })` takes the ticket id (not the channel id) and returns `true` only when it changed an `open` row. `setClaimedBy(ticketId, userId | null)` also only touches `open` tickets and returns the ticket or `null`. Callers find the ticket with `findByChannelId` first.
- `create/update/delete/count/findById/exists` implement `BaseRepository`. `create` accepts an optional `id` (`NewTicketInput`), like the giveaway tests.
- The `tickets` unique index on `(guild_id, number)` stays valid after `opener_id` is tombstoned, since the tombstone touches neither column.
