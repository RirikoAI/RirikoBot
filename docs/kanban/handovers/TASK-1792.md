## GROOMING · 2026-10-04T18:50:17Z · Claude Code (Opus 5.5)

**Approach**
1. `deploy/host/bin/ririko-watchdog.sh`: `flock -n` on the deploy lock; when it is busy, exit 0.
2. List the containers with `docker ps -a --filter label=com.docker.compose.project=ririko --format '{{.Names}} {{.Label "com.docker.compose.service"}}'`, then read `docker inspect --format '{{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{end}}'` for each.
3. Restart unhealthy containers, judge the stack, check `df --output=pcent /`, and ping `HEALTHCHECK_PING_URL` (success) or `HEALTHCHECK_PING_URL/fail` with `--data-raw "<reason>"`.
4. `systemd/ririko-watchdog.service` (`Type=oneshot`) and `ririko-watchdog.timer` (`OnBootSec=2min`, `OnUnitActiveSec=1min`).
5. Tests with fake `docker`, `curl` and `df`.

**Relevant code**
- `deploy/host/bin/ririko-deploy.sh` (TASK-1781): the lock path and config loading. Reuse them, do not redefine them.
- `Dockerfile:100,122`: bot and web HEALTHCHECK start periods are 120 s and 60 s. A container in `starting` is not unhealthy; do not restart it.
- `docker-compose.production.yml`: postgres has a `pg_isready` healthcheck; lavalink has none.

**Pitfalls**
- A container with no healthcheck has an empty health status; judge it by `State.Status == running`.
- Healthchecks.io alerts when pings stop, so a failed watchdog run or a dead host alerts too. Give the check a 2-minute period and a few minutes of grace in the runbook.

**Out of scope**
- Metrics, dashboards and log shipping.

## PROGRESS · 2026-10-04T22:52:12Z · claude-medium (Claude Sonnet 5.5) · REVIEW

**Files changed**
- `deploy/host/bin/ririko-watchdog.sh` (new, root, installed by bootstrap as `/usr/local/bin/ririko-watchdog`). Conventions of `ririko-deploy.sh` / `ririko-backup.sh`: `ririko.conf` parsed for the known keys `HEALTHCHECK_PING_URL` and `DISK_ALERT_PERCENT` and never sourced (file wins, one pair of quotes stripped, a missing file is an empty one); `RIRIKO_CONF`, `RIRIKO_LOCK` (default `/run/lock/ririko-deploy.lock`), `DOCKER` and `CURL` overrides, plus `DF` and `LOGGER`. A run:
  1. `flock -n` on the lock (fd 9); when it is held: one log line, exit 0, nothing restarted or pinged.
  2. `docker ps -a --filter label=com.docker.compose.project=ririko --format '{{.Names}} {{.Label "com.docker.compose.service"}}'`. No container of the project (nothing deployed, or only `ririko-lavalink`): one log line, exit 0, no ping, no logger. `docker ps` failing: exit 1 with no ping, so the monitor alerts.
  3. `docker inspect` per container (`{{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{end}}`). `unhealthy` gives `docker restart`, logged through `logger -t ririko-watchdog -p daemon.warning` and stdout, and the reason "<service> was unhealthy and was restarted" (or "... could not be restarted"). `starting` is left alone.
  4. Healthy = bot, web and postgres running and `healthy` (a service with no healthcheck is "reports no health", missing is "is missing", other states "is exited" etc.), lavalink running only if the project has it (absent is fine), no unhealthy container this run, and `df --output=pcent /` below `DISK_ALERT_PERCENT` (default 85; at the limit counts as full).
  5. The lock is released (`exec 9>&-`), then: reasons present gives `curl -fsS -m 10 --retry 3 -o /dev/null --data-raw "<reasons joined by '; '>" <url>/fail`; only starting containers gives no ping at all (log line); otherwise `curl ... <url>`. A failing ping is only a warning. No URL: it only logs.
  - Invalid `HEALTHCHECK_PING_URL` (not https) or `DISK_ALERT_PERCENT` (not 1 to 100): the restarts still run (the percent falls back to 85, no ping), and the run exits 1 at the end with the error on stderr. Any argument: exit 2.
- `deploy/host/systemd/ririko-watchdog.service` (new): `Type=oneshot`, `ExecStart=/usr/local/bin/ririko-watchdog`, `After=docker.service network-online.target`, `TimeoutStartSec=2min`, `Nice=5`.
- `deploy/host/systemd/ririko-watchdog.timer` (new): `OnBootSec=2min`, `OnUnitActiveSec=1min`, `AccuracySec=5s`.
- `deploy/host/ririko.conf.example`: new commented "ririko-watchdog" section with both keys, defaults and setup advice.
- `scripts/deploy-host.test.ts`: 44 new tests (129 in the file, 197 in `scripts`). Fake docker (project-aware `ps`, per-container `inspect` state, `restart` that moves the container to `running starting`), curl (also records whether the lock was free at ping time), df and logger, all inside the bash process like the deploy and backup scenarios. Covered: the exact docker calls and the healthy ping with the trailing slash stripped; lavalink absent / running / exited; containers of other projects ignored (an unhealthy `ririko-lavalink` one is never restarted); restart plus logger lines plus the `/fail` reason; several unhealthy containers joined with the disk reason; no restart loop while `starting` and the heartbeat resuming once healthy; `starting` sends nothing; five failing states; a failing restart; six disk thresholds (default and configured, below / at / above) and the limit named in the reason; no URL (only logs, still restarts), no ririko.conf, a failing ping; one line and exit 0 with nothing deployed (no conf, untouched example, configured URL, only another project); `docker ps` failing (exit 1, no ping); five invalid settings (exit 1, restarts still happen); a `$(...)` conf line never runs; exit 2 for an argument; with real `flock`: lock held means one line, no docker call, no ping, no logger, and the next run resumes; the lock is free when curl runs. **Decisions & gotchas**
- A container that is only `starting` sends neither a heartbeat nor `/fail`: after a host boot or a watchdog restart (bot start period 120 s) a `/fail` would be noise, and the monitor's grace period still alerts if the stack never turns healthy. The restart itself already sent one `/fail` with its reason.
- The lock is held only while inspecting and restarting (and released before the ping), so a deploy that starts in that window exits 3. A long deploy (up to `READY_TIMEOUT`) sends no heartbeat; see the FLAG on TASK-1772 for the grace period advice.
- A permanently broken container is restarted again after its start period ends (about every 2 to 3 minutes for the bot), with a `/fail` each time; Docker has no back-off for this. Acceptable for now.
- A required service with no healthcheck would never be healthy; bot, web and postgres all define one (Dockerfile, `docker-compose.production.yml`), and a test pins the service names to the compose file.
- `docker ps` failing exits 1 every minute while Docker is down (a failed unit in journald); that is a real outage, not the unconfigured-host noise the grooming note warns about.
