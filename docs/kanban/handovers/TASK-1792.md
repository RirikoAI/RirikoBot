## GROOMING · 2026-10-04T18:50:17Z · Claude Code (Opus 5.5)

**Approach**
1. `deploy/host/bin/ririko-watchdog.sh`: `flock -n` on the deploy lock; when it is busy, exit 0.
2. List the containers with `docker ps -a --filter label=com.docker.compose.project=ririko --format '{{.Names}} {{.Label "com.docker.compose.service"}}'`, then read `docker inspect --format '{{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{end}}'` for each.
3. Restart unhealthy containers, judge the stack, check `df --output=pcent /`, and ping `HEALTHCHECK_PING_URL` (success) or `HEALTHCHECK_PING_URL/fail` with `--data-raw "<reason>"`.
4. `systemd/ririko-watchdog.service` (`Type=oneshot`) and `ririko-watchdog.timer` (`OnBootSec=2min`, `OnUnitActiveSec=1min`).
5. Tests with fake `docker`, `curl` and `df`.

**Relevant code**
- `deploy/host/bin/ririko-deploy.sh` (TASK-1781): the lock path and config loading. Reuse them, do not redefine them.
- `Dockerfile:100,122`: bot and web HEALTHCHECK start periods are 120 s and 60 s. A container in `starting` is not unhealthy; do not restart it.
- `docker-compose.production.yml`: postgres has a `pg_isready` healthcheck; lavalink has none.

**Pitfalls**
- A container with no healthcheck has an empty health status; judge it by `State.Status == running`.
- Healthchecks.io alerts when pings stop, so a failed watchdog run or a dead host alerts too. Give the check a 2-minute period and a few minutes of grace in the runbook.

**Out of scope**
- Metrics, dashboards and log shipping.
