## GROOMING · 2026-10-04T18:58:43Z · Claude Code (Opus 5.5)

**Approach**
1. In `ririko-deploy-ssh`, read the instance from `$1` (set by the forced command) when `RIRIKO_ROLE=lavalink`, and pass it to `sudo -n /usr/local/bin/ririko-deploy deploy <version> <instance>`.
2. In `ririko-deploy`, branch on `RIRIKO_ROLE`. Reuse the download and wait functions from TASK-1781.
3. The instance's port and password come from its env file (`LAVALINK_PASSWORD`) and a fixed map (production 2333, staging 2334). The `/version` check runs on the host with `curl -fsS -H "Authorization: <password>"` against `WG_ADDRESS`.
4. Watchdog: a consecutive-failure counter per instance in `/opt/ririko/state/watchdog-lavalink-<instance>`.
5. CircleCI: add a `host` parameter (app or lavalink) to the deploy job, then add the two jobs and contexts to the release workflow.

**Pitfalls**
- Recreating a Lavalink container drops every playing session on it; the sha256 no-op is the point of this task. Hash both files as fetched from the tag.
- Deploy each Lavalink instance before its app host, because a new application.yml can be what a release depends on (plugin pins).
- The Lavalink password must not appear in `ps` output for long or in logs. Read it from the env file into a variable and pass it as a curl header from a file (`-H @file`) or a here-string.

**Out of scope**
- Changing Lavalink settings in `docker/lavalink/application.yml`.

## PROGRESS · 2026-10-05T00:15:03Z · claude-medium (Claude Sonnet 5.5) · REVIEW

**Files changed**
- `deploy/host/bin/ririko-deploy-ssh.sh`: the first argument (the forced-command argument that bootstrap writes for the Lavalink keys) is the instance. It must be `staging` or `production` (anything else: `instance not allowed`, exit 2), is appended to the words and never read from `SSH_ORIGINAL_COMMAND`; the command regex is unchanged (only `deploy <version>` and `status`). Without an argument (app role) nothing changes.
- `deploy/host/bin/ririko-deploy.sh`: `deploy <version> [<instance>]`, `status [<instance>]`.
  - Config keys (parsed, never sourced): `RIRIKO_ROLE` (app|lavalink), `WG_ADDRESS`, `WG_PEERS`, `LAVALINK_INSTANCES`, `LAVALINK_READY_TIMEOUT` (default 180), `LAVALINK_PRODUCTION_HEAP`, `LAVALINK_STAGING_HEAP`. `validate_lavalink_conf` checks them (exit 1).
  - Instances: `LAVALINK_INSTANCES` (space or comma list) or else the ports in the 4th field of the `WG_PEERS` entries (2333 production, 2334 staging). An instance the host does not run, a missing instance, or an unknown word: exit 2 before the env check, the lock and the download. An instance on an app host: exit 2.
  - `deploy_lavalink`: order conf, env file and password check (exit 1), lock (`take_lock`, shared with the app deploy), `releases/.tmp.*` cleanup, state. Downloads `deploy/lavalink/docker-compose.yml` and `docker/lavalink/application.yml` into `releases/<version>/` with the repository layout (each file replaces its old copy with one `mv -f`, because both instances share the directory and a running container has `application.yml` mounted from it). `sha256sum` of both files is compared with `state/lavalink-<instance>.sha`: equal prints `unchanged`, records current/previous and exits 0 without a Docker call. Otherwise `pull lavalink-<instance>`, `up -d lavalink-<instance>`, wait up to `LAVALINK_READY_TIMEOUT` for `GET http://<WG_ADDRESS without prefix>:<port>/version` to answer 200 (password as `curl --header @-` on stdin, never an argument), state files `lavalink-<instance>.current/.previous/.sha` on success; on failure diagnostics, then the previous release of that instance (exit 4, 5 when none).
  - Compose is called with env `WG_ADDRESS`, both `LAVALINK_*_ENV_FILE` (an instance this host does not run gets `/dev/null`, so its missing env file cannot stop the other), and the heap keys when set.
  - Refactored without behaviour change for the app role: `fetch_release_files` (shared download loop) and `take_lock`.
- `deploy/host/bin/ririko-watchdog.sh`: `RIRIKO_ROLE=lavalink` checks project `ririko-lavalink`: per configured instance a running container `lavalink-<instance>` and `/version` 200 (same password handling); counter in `$RIRIKO_ROOT/state/watchdog-lavalink-<instance>` (new `RIRIKO_ROOT` override, default `/opt/ririko`); the third consecutive failed check restarts the container and resets the counter; every failed check posts `/fail`; a missing container is reported but never restarted; no container of the project means one log line and exit 0 (nothing deployed). The ending (disk check, lock release, ping) moved into `finish`, shared by both roles. Services ending in `-plugins` are ignored (BUG-0036 init containers).
- `deploy/host/bootstrap.sh`: `set_conf_role` (called from `create_layout`) writes/keeps `RIRIKO_ROLE=lavalink` in `/etc/ririko/ririko.conf` for `--role lavalink` (in place, other lines kept, owner and mode kept); the app role writes nothing and removes a leftover lavalink line. Next-steps text for the lavalink role updated. (Added to `context.files`.)
- `deploy/host/ririko.conf.example`: new section with `RIRIKO_ROLE`, `LAVALINK_INSTANCES`, `LAVALINK_READY_TIMEOUT`, `LAVALINK_*_HEAP`, all commented out.
- `.circleci/config.yml`: `deploy` job gets the enum parameter `host` (`app` default, `lavalink`); new workflow jobs `deploy-lavalink-staging` and `deploy-lavalink-production` (contexts of the same names, tag filters like their app jobs); order release, deploy-lavalink-staging, deploy-staging, approve-production, deploy-lavalink-production, deploy-production. `ssh-host` is reused unchanged except the exit-2 message.

**Decisions & gotchas**
- ririko-deploy-ssh cannot read `ririko.conf` (the deploy user cannot traverse `/etc/ririko`, 0750 root), so it does not read `RIRIKO_ROLE`: a forced-command argument means a Lavalink key. `ririko-deploy` (root) reads `RIRIKO_ROLE` and enforces the pairing: a Lavalink host refuses a missing instance, an app host refuses one (exit 2).
- Live hosts: `RIRIKO_ROLE` is not in lavalink-staging's `/etc/ririko/ririko.conf` yet. Run `bootstrap.sh --role lavalink` again (it adds the line) before the first Lavalink deploy or the watchdog will keep treating the host as an app host. The first deploy there has no `.sha`, so it recreates the container once. `/opt/ririko/lavalink-staging.env` must exist with `LAVALINK_PASSWORD`.
- `state/lavalink-<instance>.current` is updated on an `unchanged` deploy too, so a later rollback target is a release that exists.
- The `unchanged` check needs a state `.sha` and a `.current`; both are written only after a successful start, so a failed first deploy is retried in full.
- Heap keys are an addition (the epic grooming asked for `LAVALINK_PRODUCTION_HEAP=768m` on this VM, and the compose file reads it from the environment, which the deploy now sets from `ririko.conf`).
- The CI job's `deploy-lavalink-*` contexts need the Lavalink host's tunnel hostname and a key bootstrapped with `--deploy-key-staging` / `--deploy-key-production`; the maintainer creates them.
- Editing `deploy/host` files with the Bash tool collapses `\\` in heredocs; I fixed three damaged escapes (`$'\n'`, `$'\r'`, `\'*\'`), and a test now compares the shared functions of the two scripts word for word.
