## GROOMING · 2026-10-04T18:58:43Z · Claude Code (Opus 5.5)

**Approach**
1. In `ririko-deploy-ssh`, read the instance from `$1` (set by the forced command) when `RIRIKO_ROLE=lavalink`, and pass it to `sudo -n /usr/local/bin/ririko-deploy deploy <version> <instance>`.
2. In `ririko-deploy`, branch on `RIRIKO_ROLE`. Reuse the download and wait functions from TASK-1781.
3. The instance's port and password come from its env file (`LAVALINK_PASSWORD`) and a fixed map (production 2333, staging 2334). The `/version` check runs on the host with `curl -fsS -H "Authorization: <password>"` against `WG_ADDRESS`.
4. Watchdog: a consecutive-failure counter per instance in `/opt/ririko/state/watchdog-lavalink-<instance>`.
5. CircleCI: add a `host` parameter (app or lavalink) to the deploy job, then add the two jobs and contexts to the release workflow.

**Pitfalls**
- Recreating a Lavalink container drops every playing session on it; the sha256 no-op is the point of this task. Hash both files as fetched from the tag.
- Deploy each Lavalink instance before its app host, because a new application.yml can be what a release depends on (plugin pins).
- The Lavalink password must not appear in `ps` output for long or in logs. Read it from the env file into a variable and pass it as a curl header from a file (`-H @file`) or a here-string.

**Out of scope**
- Changing Lavalink settings in `docker/lavalink/application.yml`.
