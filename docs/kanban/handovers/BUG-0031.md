## GROOMING · 2026-10-02T20:27:42Z · Claude Code (Opus 5.5)

**Approach**
- Fix the root cause in the Postgres schema. 26 columns use `bigint(..., { mode: 'bigint' })`:
  - `pg/economy.ts`: 9.
  - `pg/tcg.ts`: 13.
  - `pg/games.ts`: 3.
  - `pg/xp.ts`: 1.
- Switch them to `{ mode: 'number' }`, and change their defaults from `0n` to `0`. The SQL type stays BIGINT, so `PG_SCHEMA_DDL` and existing databases do not change.
- Remove the `BigInt(...)`, `0n` and `Number(...)` conversions the repositories and services add for these columns. The main ones are in `economy.repository.ts` (19), `xp.repository.ts`, `market-listing`, `card-trade`, `waifu-guild` and `tcg-item`, and in adventure `adventure-payout.service.ts`, `reward-effects.ts` and `reward-rank.ts`.
- Check each raw-SQL read. `db.execute` rows come back as strings or bigint from `pg`, and `mode` does not apply to them.

**Why number is safe**
- `Number.MAX_SAFE_INTEGER` is about 9e15 credits or XP. No reachable balance comes close.

**Pitfalls**
- Keep the `FOR UPDATE` locks and the conditional updates from TASK-1242.
- Public signatures that accept `number | bigint` can keep doing so, but they convert once at the boundary.
- Run `pnpm test:postgres` locally: `docker run -d --rm --name ririko-pg-test -e POSTGRES_PASSWORD=test -p 55432:5432 postgres:16-alpine`, then `TEST_POSTGRES_URL=postgres://postgres:test@127.0.0.1:55432/postgres`.
- The estimate is raised from 3 to 5 points for the adventure raw-SQL paths.

## PROGRESS · 2026-10-03T06:21:31Z · Claude Code (Opus 5.5) · REVIEW

**Files changed**
- `packages/database/src/schema/pg/{economy,games,tcg,xp}.ts`: all 26 `bigint` columns now use `{ mode: 'number' }`, and their defaults changed from `0n` to `0`. The SQL type stays BIGINT, so `PG_SCHEMA_DDL` and existing databases are unchanged.
- Repositories:
  - The Postgres write paths no longer wrap these columns in `BigInt()` or use `0n`: `economy` (`getOrCreateBalance`, `modifyBalance`), `xp` (create, update, `addXp`, the two rank queries), `card-trade`, `market-listing`, `item`, `tcg-item`, `waifu-guild` and `achievement`.
  - `modifyBalance` still does its overflow-safe arithmetic in `bigint` and writes `Number(...)`.
- `packages/services/src/waifu-tcg/game-modes/pvp-duel-service.ts`: the wager balance checks compare numbers directly.
- `packages/database/src/repositories/numeric-columns.test.ts` (new, `describeDialects`) checks that a balance, its transaction, an XP account and a market listing come back as `typeof number` on both dialects, and that plain arithmetic works.

**Verification**
- `pnpm typecheck` passes.
- `pnpm vitest run packages/database/src packages/services/src`: 1328 tests pass. The 59 skipped are the Postgres variants.
- `pnpm lint --quiet` and `pnpm format:check` pass.
- `pnpm test:postgres` against local `postgres:16-alpine`: 144 files, 1386 tests pass, 1 skipped. This includes the adventure raw-SQL payout and XP suites and the new test.
- `pnpm test:coverage`: 2710 tests pass, and every threshold holds.

**Decisions & gotchas**
- I left alone the `bigint` code that does not read these columns as bigint. Adventure credits are decimal strings with `bigint` math by design (`reward-rank.ts`, `adventure-payout.service.ts`). The migration coin audit and Discord permission bits stay too.
- `EnhancementService.enhance` still takes `bigint` credits. Its callers convert once, which is harmless.
- I did not narrow the `number | bigint` unions in public parameter types (`ModifyBalanceParams`, `RewardResult`). They accept both, so nothing breaks. A later cleanup could narrow them.
