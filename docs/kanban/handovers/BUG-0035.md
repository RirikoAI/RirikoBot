## GROOMING · 2026-10-04T22:54:20Z · Claude Code (Opus 5.5)

**Approach**
1. In `deploy/host/bin/ririko-deploy.sh` `cmd_deploy`, replace `flock -n 9` with a bounded wait:
   - try `flock -n 9` first;
   - when that fails, log "waiting up to Ns for the host lock" and run `flock -w "$DEPLOY_LOCK_WAIT" 9`;
   - exit 3 with the existing message when the wait times out.
2. `DEPLOY_LOCK_WAIT` defaults to 300 and must be digits only. `ririko-backup.sh` handles `BACKUP_LOCK_WAIT` the same way; copy its pattern.
3. Tests and docs as in the acceptance list.

**Why**
- The watchdog takes the lock for a few seconds every minute, and the backup holds it while it dumps Postgres. CI should not fail on that.
- A 300 s wait stays well inside the CI job's `no_output_timeout` of 20 minutes, because the deploy logs while it waits.

**Pitfalls**
- Keep exit 3: the CI job and `docs/release.md` already map it to "host busy".
- `flock -w` takes seconds and accepts decimals; keep the value digits only, to match the other keys.

**Out of scope**
- The watchdog and the backup scripts.

## REVIEW · 2026-10-04T23:13:50Z · Claude Code (Opus 5.5) · REWORK

**Issues**
- **The conf value is ignored for the wait.** `cmd_deploy` calls `flock -n`/`flock -w "$DEPLOY_LOCK_WAIT"` at line ~323, but `load_conf` (which reads `DEPLOY_LOCK_WAIT` from `ririko.conf`) runs afterwards, at line ~330. A value set in `/etc/ririko/ririko.conf`, the documented place, never applies, and the wait always uses the environment or the 300 default.
- **The value is checked after use.** `validate_conf` runs after the wait, so a bad value (for example `soon`) reaches `flock -w` first and fails as a misleading exit 3.
- **Fix:** call `load_conf` and `validate_conf` before taking the lock. They only read and check a file, so running them outside the lock is safe. Keep the rest of the lock code as it is. Update the PROGRESS note's claim about ordering accordingly.
- **Tests:** add a test that sets `DEPLOY_LOCK_WAIT=10` **in the temporary conf file** (not the environment), holds the lock for about 1 second and expects exit 0. Make the invalid-value test expect exit 1 without waiting.
- **Run verify_cmd from PowerShell** (`bash` resolves to WSL, which has real `flock`) so the lock tests actually run, and report that none were skipped. The first run skipped 8 of them.
