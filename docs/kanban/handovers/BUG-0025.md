## GROOMING · 2026-10-08T14:00:00Z · claude-opus (coordinator)

**Approach**
1. Collection stats. Add one `WaifuCardRepository` method (name it e.g. `getCollectionStats(userId, tx?)`) that returns `{ uniqueCards, elements, mythicCards }` for a user: distinct `user_cards.card_id`, distinct `waifu_cards.element` over the owned cards, and owned cards whose `waifu_cards.rarity` is `MYTHIC` (count distinct card ids). Implement both dialect branches like the rest of the repository. Add a `describeDialects` case to `waifu-card.repository.behaviour.test.ts`.
2. In `AchievementService`, add a method (e.g. `syncCollection(userId)`) that reads the stats through the optional `waifuCardRepo` (already a constructor option; return early when it is missing) and calls `recordProgress(userId, 'CARD_COUNT' | 'ELEMENTAL_COUNT' | 'MYTHIC_CARD_COUNT', value, true)`. Call it at the start of `getUserAchievements`, `claimAchievement` and `claimAll`. This backfills existing players and covers the tutorial starter card, adventure payouts and achievement reward cards without hooking each of them. Make sure the call in `claimAchievement` happens before the unlock check and outside the claim transaction. `claimAll` should sync once, not once per achievement (pass a flag or sync before the loop and call an internal claim).
3. Add a small bot helper `apps/bot/src/commands/tcg/achievement-progress.ts` that wraps `services.achievementService.recordProgress(...)` (and the collection sync) in a try/catch and logs the error with the bot's existing logger. Every bot call site uses it, so a failure never breaks a reply. Follow the pattern the quest progress calls already use in `game.command.ts` (lines ~184 and ~353).
4. Record at each source (bot layer):
   - `game.command.ts` duel: winner gets `PVP_WINS` +1, nothing on `DRAW`. Both the challenger and the target can be the winner.
   - `game.command.ts` raid: `BOSS_DAMAGE` + `attackRes.damageDealt` after a successful attack.
   - `dungeon-battle.manager.ts` after `finalizeBattleResult` (~line 207): on a victory in a non-tutorial season, `DUNGEON_FLOOR` = `runResult.highestFloorCleared`, absolute.
   - `gear-actions.ts` (~line 15) and `item.command.ts` (~line 393): when `result.newLevel >= MAX_ENHANCEMENT_LEVEL` (10), `EQUIPMENT_ENHANCE_10` = 1, absolute.
   - `economy/commands.ts` daily (~line 63): after a successful claim, `DAILY_STREAK` = `res.streak`, absolute.
   - Collection sync after `dropManager.claimDrop` succeeds (`card.command.ts` ~line 322), after `tradeService.acceptTrade` (`trade.command.ts` ~line 155, both sender and receiver), and after `marketService.buyListing` (`market.command.ts` ~line 129, buyer).
5. Set `TRACKED_ACHIEVEMENT_TYPES` in `packages/core/src/config/tcg-catalog.ts` to all nine seeded types, and update the comments that say only some types are tracked (top of `tcg-catalog.ts`, `tcg-achievement-admin.service.ts`). Update the expectation in `tcg-item-catalog.service.test.ts` (~line 256) to the full list; that is a real behaviour change, not a weakened test.
6. If `docs/waifu-tcg.md` section 14 describes how progress is tracked, add one short line naming the sources. Do not rewrite the section.

**Pitfalls**
- `recordProgress` with a delta is read-modify-write, not atomic. Fine for this ticket; do not add locking.
- `isAbsolute` keeps the max, so trading a card away or losing a streak never lowers progress. Keep that.
- `DUNGEON_FLOOR` must ignore tutorial seasons (tutorial floors T1–T4 would otherwise count as floors 1–4, harmless but wrong).
- The World Boss Raid (`BossRaidService`) is in memory; its damage history is lost on restart. Only record new damage; there is no backfill for PvP wins or raid damage.
- Commands serve both slash and prefix through `ctx`; one call site covers both.
- The behaviour test for the repository must pass on SQLite and PostgreSQL (`describeDialects`). PostgreSQL tests need the test database the suite already uses.

**Out of scope**
- `QuestService` (in-memory quests) and its progress.
- New achievement types, rewards, unlock notifications or DMs.
- Moving `AchievementService` construction or injecting it into other services.
- Web dashboard page changes beyond what follows from `TRACKED_ACHIEVEMENT_TYPES`.

**Decisions & gotchas**
- `syncCollection` propagates DB errors inside `getUserAchievements`, `claimAchievement` and `claimAll` (the services package has no logger; the bot-layer helpers are where errors are caught and logged). A failing stats query therefore fails those three calls, which would only happen when the database itself is failing.
- `DUNGEON_FLOOR` uses `!isTutorial` from `StartBattleOptions`, the same signal the manager already uses for tutorial handling, rather than `session.isTutorial`, because the manager tests fake the session.
- The tracked-types test compares against the set of seeded requirement types, so adding a seed without tracking it fails the test.
- Dungeon "next floor / retry" buttons call `startBattle` again, so each win finalises through the same hook; no second call site was needed.

**New CodeGraph queries**
