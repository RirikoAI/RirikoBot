**Decisions & gotchas**
- **Dashboard readiness.** `getDatabase` rejects while the database is behind, so every dashboard request, `/api/ready` and also `/api/health` answer with an error or 503 until the bot (or `ririko db:migrate`) has migrated the database. The rejected start is not cached and its client is closed, so the next request checks again and the dashboard recovers without a restart. The log line is `[web] ready probe: dashboard not available: SchemaNotReadyError: The database schema is behind this dashboard: N pending migration(s) (ids)...`. A database with tables but no migration records (every pre-ADR-015 database) counts as behind until the bot or the CLI has adopted it. The dashboard's compose service depends only on PostgreSQL, so on a first start it waits for the bot.
- **Downgrade guard in the dashboard** uses the new `MigrationStatus.unknownContract`; unknown additive migrations only log a warning.
- **`createSqliteClient` is no longer a way to get a schema.** Anything that opened a new SQLite file and relied on it must call `migrateDatabase` (the bot, `ririko db:migrate`, `db-reset` and `legacy-upgrade` do). `apps/web/e2e/support/seed.ts` and `commands-sync.ts` (an in-memory registry database) keep `autoMigrate: true`.
- `db:migrate` failure output prints `error.details.problems` (the adoption refusal report). `--status` never fails on the guard (exit 0); only a real run or `--dry-run` returns 2.

**For the maintainer's `next dev` on :3000 (action needed once)**
- The dashboard no longer creates or upgrades the schema. Until the development database has migration records, the dashboard shows errors and `/api/ready` answers 503 with the log line above.
- Run once against the development database (same `.env`): `pnpm cli db:migrate --dry-run` to see the plan, then `pnpm cli db:migrate`. Starting the bot does the same. A database built with `db:push` is adopted: a SQLite backup is written to `<db dir>/backups/pre-migrate-<stamp>.sqlite` first, missing tables, columns and indexes are added, and `0000_baseline` is recorded. If adoption refuses, the report lists why and nothing is changed.
- `next dev` needs no restart; its next request checks again. `pnpm db:push` stays a development shortcut, but after adoption a schema change needs `pnpm db:generate` and a migration (AGENTS.md rule 9).
