- The token in the start URL must not stay in the browser history: redirect to `/step/welcome` right after setting the cookie.
- Do not log request bodies.
- `assets/installer/` must be found both from `tsx` (source) and from `dist` (built, and the Docker image at `/app`): resolve it from the repository root the same way other CLI code finds `assets/`, not from `__dirname` guesses.
- Tests: start the server on port 0 in tests only (the production option forbids a random port), inject the checks and a temporary folder for the file.
- Keep `render.ts` free of I/O so it can be unit tested without the server.

**Out of scope**

- Client-side JavaScript of any kind.

**Decisions & gotchas**
- No new runtime dependency. Access: start token (32 bytes) is exchanged once for `ririko_setup` (HttpOnly, SameSite=Strict); everything else without the cookie is 403. Host must be 127.0.0.1, localhost or [::1] with the bound port, plus the listen address when it is not loopback. A present Origin must match. Every POST needs the per-session `_csrf` and a form content type; bodies over 256 KB get 413.
- `startInstallerServer({ profile, envFile?, host?, port?, root? }, deps)`: `root` (default: the workspace root) holds `.env.example`, `assets/installer` and `docs/legal`. `envFile`, when given, must equal `<root>/.env` or `<root>/.env.production`; otherwise it throws (the writer only writes the profile file of a root). Port 0 works for tests only; CLI code (TASK-1925) must keep 3999 as the default. A port in use rejects with a message that names `--port`. Returns `{ url, host, port, envFile, stopped, close }`; `stopped` resolves `'finished' | 'idle' | 'closed'`.
- Checks: a page is complete when `validatePage` is clean and every active check has a non-`fail` result for the current values. The result is stored with an HMAC fingerprint of the values the check reads (`checkInputs`), so a change forces a new check, and a later page closes again until it passes. `warn` counts as passing. GET never runs checks. `verify` ("Test the connection") re-runs the page's checks and re-renders.
- Fields without JavaScript: all fields of a page are in the HTML; conditional ones carry `data-cond` and the server serves `/assets/conditions.css`, generated from the page model (`conditionalCss`), that shows them for their switch and select value (`:has`). A `@supports not selector(:has(*))` fallback shows all of them. The server, not the browser, decides what is required; hidden fields' posted values are stored but ignored.
- Secrets: a saved secret is never rendered (empty field, "keep the current value" note); posting an empty secret keeps the stored one. The Install summary uses `maskSecret`. Errors from checks are already redacted (TASK-1922). Nothing is logged except the error name of an unexpected 500.
- Update mode: answers start from `prefillValues` of the existing file (a SQLite path is not taken for the PostgreSQL field); switches are inferred from the presence of their keys. The result page leaves out `pnpm db:reset` when the file existed.
- `GET /download` works only after the two boxes were saved in the session; `POST /download` (the Install page button) saves them and returns the file as an attachment. A session-stable secret generator makes Download and Finish produce the same generated secrets.
- Finish writes through `writeEnv`; on a schema error the Install page shows the errors and nothing is written. After a successful Finish response is sent, the server closes (idle connections now, others after 250 ms). Idle stop: 30 minutes (`idleMs` injectable).
- The icons are plain SVG shapes drawn for this wizard, not the MDI glyphs (no icon font, no copy of MDI paths).
- Layout was not checked in a real browser or at 375px width; the CSS follows the 1.x structure with a `max-width: 767px` rule that hides tab text and tightens padding. Worth a look by the reviewer.

**Blocking bug**: pressing **Next** on Welcome returns **403 Forbidden**. Every form POST fails in a real browser.
- Cause: the server sends `Referrer-Policy: no-referrer` (`server.ts:152`). Under the Fetch spec, a non-GET, non-CORS request with that policy sends `Origin: null`, and the origin check at `server.ts:595-598` rejects `null`. The tests pass because they set `Origin` by hand.
- Fix: use `Referrer-Policy: same-origin` (the start token never leaves the origin, and the token URL is replaced by a redirect anyway). Keep rejecting any other origin, and keep rejecting `Origin: null`.
- Add a test that would have caught it: a POST that sends the `Origin` a browser computes from the served `Referrer-Policy` (assert the header is not `no-referrer`, and that a POST with `Origin: http://127.0.0.1:<port>` plus the cookie and `_csrf` passes).
