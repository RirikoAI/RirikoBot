## 1. Summary of Work Accomplished
**Symptom:** "The passkey could not be verified. Please try again." on the `/verify` sign-in check in Edge. Adding a passkey worked in both Firefox and Edge.

**Root cause, found from the new rejection log:**
```
[web] Passkey check rejected for user …: User verification required, but user could not be verified
```
- The Windows passkey used through Edge signed without the user-verification (UV) flag.
- STORY-117 required UV (`userVerification: 'required'` and `requireUserVerification: true`), so the check was rejected.
- Firefox only looked fine: adding a passkey counts as a passkey check, so that session never ran a sign-in check.

**Three defects hid the cause:**
1. Verification failures were not logged, so the reason was invisible.
2. `getWebServices()` cached its services on `globalThis`. After a hot reload the server kept running old code, so new logging never executed.
3. The cached `PasskeyService` threw a `PasskeyVerificationError` from the old module instance. The reloaded action's `instanceof` check failed, and the error escaped as an unhandled rejection instead of an error result. The same class-identity problem can happen whenever a cached object crosses bundler module instances.

**Changes:**
- [passkeys.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/lib/server/auth/passkeys.ts):
  - UV is requested (`userVerification: 'preferred'`) but not required. User presence is still required, and the library enforces UP.
  - `register` and `authenticate` return a `PasskeyOutcome` (`{ ok: true, value }` or `{ ok: false, message }`) instead of throwing. `PasskeyVerificationError` is removed.
  - Every rejection is logged as `[web] Passkey <registration|check> rejected for user <id>: <reason>`. Malformed responses log field paths only, never values.
- [verify/actions.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/app/verify/actions.ts) and [account/security/actions.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/app/account/security/actions.ts): use the outcome; no `instanceof` checks remain.
- [services.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/lib/server/services.ts): only the database connection is cached on `globalThis`. Services are built once per module instance, so hot reloads pick up new code and classes always match their importers.
- [soft-authenticator.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/lib/server/auth/testing/soft-authenticator.ts): a `userPresent` option, set per authenticator or per assertion.
- **Docs:** ADR-013 revision item 7 (UV requested, not required, with reasoning) and `docs/dashboard.md` §2.3.

## 3. Roadblocks, Gotchas & Decisions Made
- **Security trade-off:** UV adds protection only against someone already using the owner's unlocked device, and that person also holds the browser session. The passkey is a second factor after Discord sign-in, so a stolen cookie or Discord account still cannot pass. The user delegated security choices of this kind ("keep it secure but not overengineered").
- **File watching on the Z: drive does not fire, so Next hot reload never runs there.** Restart `pnpm dev:web` after code changes. This is why the stale singleton was so misleading.
- **Next writes a dev log to `apps/web/.next/dev/logs/next-development.log`.** Its timestamps are relative to server start. It is the easiest place to read server errors when the dev server runs in another console.
- **In a non-TTY Git Bash, `pnpm` fails** ("cannot safely launch non-Node Windows command shim"). Launch with `npx` from a script instead: `npx tsc -b && cd apps/web && npx next dev`.
