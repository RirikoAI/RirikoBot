## GROOMING · 2026-10-04T18:50:17Z · Claude Code (Opus 5.5)

**Approach**
1. `deploy/host/bin/ririko-backup.sh`: subcommands `run` (default) and `init`. Load `/etc/ririko/ririko.conf`; take the deploy lock with `flock -w 1800`.
2. Dump: `docker compose -p ririko exec -T postgres pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"`. Read the database name and user from the host env file, with the compose defaults `ririko`/`ririko`. Write to a temporary file, then move it into place.
3. restic: `docker run --rm` with `RESTIC_IMAGE` (pin a version tag in `ririko.conf.example`). Pass secrets with `--env-file` pointing at a 0600 temporary file built from the config, not with `-e KEY=value`. Mount `/opt/ririko/backups/nightly:/backup/postgres:ro` and each volume at `/backup/<volume>:ro`.
4. Retention and the Sunday `restic check` (`date -u +%u` is 7).
5. Pings with `curl -fsS -m 10 --retry 3`.
6. `systemd/ririko-backup.service` (`Type=oneshot`) and `ririko-backup.timer` (`OnCalendar=*-*-* 03:30:00 UTC`, `Persistent=true`, `RandomizedDelaySec=10min`).
7. Tests with fake `docker`, `curl` and `date`.

**Pitfalls**
- Lightsail buckets are S3 buckets: `RESTIC_REPOSITORY=s3:s3.us-east-1.amazonaws.com/<bucket>/<env>` with the bucket's access key.
- Losing `RESTIC_PASSWORD` makes every backup unreadable. The runbook (TASK-1772) tells the maintainer to keep an offline copy; the script cannot help.
- `SECRET_VAULT_KEY` lives only in `.env.production`. Without it, the stored guild credentials in a restored database cannot be decrypted. It stays out of the backup on purpose.

**Out of scope**
- Lightsail instance snapshots (a console setting in the runbook). Restore automation; the runbook documents the restore commands.

**Files changed**
- `deploy/host/bin/ririko-backup.sh` (new): subcommands `run` (default) and `init`; anything else exits 2. Reuses `ririko-deploy.sh`'s conventions: `ririko.conf` parsed for known keys and never sourced (file wins, single or double quotes stripped); `RIRIKO_ROOT`, `RIRIKO_CONF`, `RIRIKO_LOCK` (default `/run/lock/ririko-deploy.lock`), `DOCKER` and `CURL` overrides; the compose files come from `releases/<state/current>/.compose-files`, the same `compose()` call as the deploy script (`RIRIKO_VERSION`, `RIRIKO_ENV_FILE`, `--env-file`).
  - `run`: (1) loads the conf; when `RIRIKO_ENV_NAME`, `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` is empty it logs one line naming the missing keys and exits 0; (2) when no release is deployed (`state/current` empty, not a version, or its directory gone) it logs one line and exits 0; neither case pings. (3) Validates the conf (https-only `BACKUP_PING_URL` first, so later failures can ping `/fail`; env name, numeric lock wait, and `RESTIC_IMAGE` must carry a tag or sha256 digest and not be `:latest`). (4) Takes the lock: `flock -n`, else logs "waiting up to Ns" and `flock -w BACKUP_LOCK_WAIT` (exit 3 on timeout). The lock is held for the whole run, so a backup and a deploy never overlap. (5) `compose exec -T postgres sh -c 'exec pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB"'` into `backups/nightly/ririko.dump.part`, moved over `ririko.dump` only when non-empty, so a failed dump keeps the last good one. (6) restic via `docker run --rm --env-file <0600 file> -v <mount>:ro ... <image>`: `backup --host $RIRIKO_ENV_NAME /backup/postgres /backup/<volume>...` with `backups/nightly` and `ririko_ririko_data`, `ririko_card_images`, `ririko_boss_images`, `ririko_welcomer_backgrounds` mounted read-only; then `forget --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --prune`; then `check` when `date -u +%u` is 7. (7) `curl -fsS -m 10 --retry 3` pings `BACKUP_PING_URL` on success and `<url>/fail` on any failure (an ERR trap covers unexpected errors); a failing ping only logs a warning.
  - `init`: requires the five keys (exit 1 otherwise), runs `restic cat config`, and runs `restic init` only when that fails, so repeating it is harmless. It takes no lock and never pings.
  - The secrets file lives in `mktemp -d` under `$RUNTIME_DIRECTORY` (systemd gives the unit a tmpfs `/run/ririko-backup`), is passed with `--env-file`, and is removed on exit; secrets never appear on a command line.

**Decisions & gotchas**
- `RIRIKO_ENV_NAME` is required (no hostname fallback), so an unconfigured host is detected the same way for every key.
- The database name and user come from the postgres container's own `POSTGRES_USER`/`POSTGRES_DB` (as in `ririko-deploy.sh`) instead of parsing the host env file; the compose defaults therefore apply automatically.
- The backup holds the deploy lock until restic finishes (the upload may take minutes), so a deploy that starts meanwhile exits 3. The alternative (releasing after the dump) would let a deploy restart containers while the volumes are read.
- A stack with a deployed release but a stopped Postgres is a failure (dump fails, `/fail` ping), not a skip.
- Secrets come only from `ririko.conf`; ambient `RESTIC_*`/`AWS_*` variables are unset at the start.
- `restic` runs without a persistent cache directory; at this data size every `forget`/`check` re-reading the indexes is cheap. Add a cache volume if the repository grows.
- The conf parser strips one pair of surrounding quotes, so a password that itself begins and ends with the same quote must be wrapped in a second pair (documented in the example).
- File mode assertions for the env file run only where the file system keeps modes (a probe skips them on Git Bash/NTFS); WSL, Linux CI and the `verify_cmd` run enforce 0600.

## REVIEW · 2026-10-04T22:41:09Z · Claude Code (Opus 5.5) · REWORK

**Checked and fine**
- Conf parsing, the pinned image, read-only mounts, the secrets `--env-file` on tmpfs, retention, the Sunday check, the pings, the unconfigured exit 0, and the units.

**Issues**
- **Hold the lock for the dump only.** It is held now until restic finishes, which can take a long time for the first upload and the Sunday `check`. TASK-1792's watchdog skips (no heartbeat) while the lock is held, so every long backup would trip the Healthchecks.io alert, and any deploy in that window fails with exit 3.
  - Take the lock, run `pg_dump` into `ririko.dump`, release the lock (`flock -u 9` or close fd 9), then run restic.
  - Restic reads the volumes read-only, so a deploy during the upload is safe: the volumes outlive the containers.
  - A dump that fails still exits non-zero with `/fail`.
- Update the tests: the lock is free while restic runs (for example, a fake docker that runs `flock -n` on the lock path during the restic call and records the result), and the wait and timeout tests still cover the dump phase.
- Keep everything else unchanged.
