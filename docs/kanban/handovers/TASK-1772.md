## FLAG · 2026-10-04T23:05:00Z · from TASK-1791 · claude-sonnet-worker-1791 (Claude Sonnet 5.5)

**Finding**: `deploy/host/bin/ririko-backup.sh` and `deploy/host/ririko.conf.example` (new section "ririko-backup") define what the runbook has to document: the keys `RIRIKO_ENV_NAME`, `RESTIC_REPOSITORY` (`s3:s3.us-east-1.amazonaws.com/<bucket>/<env>`), `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, optional `RESTIC_IMAGE`, `BACKUP_PING_URL` (https only) and `BACKUP_LOCK_WAIT` (default 1800). The timer ships enabled by bootstrap, but a run only logs "backup is not configured" and exits 0 until the five required keys are set and a release is deployed.
**Impact on this ticket**: the runbook should cover, in order: create the Lightsail bucket and its access key; fill the keys; `sudo ririko-backup init` (safe to repeat); `sudo systemctl start ririko-backup.service` for a first backup and `journalctl -u ririko-backup`; keep an OFFLINE copy of `RESTIC_PASSWORD` (losing it makes every backup unreadable); `SECRET_VAULT_KEY` is deliberately not backed up. Restore commands are not scripted: restic runs as `docker run --rm --env-file <file> -v <dir>:/restore docker.io/restic/restic:<tag> restore latest --host <env> --target /restore`, then `pg_restore` of `ririko.dump` into the stack. Exit codes of `ririko-backup`: 0 done or skipped, 1 failed, 2 bad command, 3 lock not free within `BACKUP_LOCK_WAIT`. The backup holds the deploy lock for its whole run, so a deploy during a backup exits 3.

## FLAG · 2026-10-04T22:51:50Z · from TASK-1792 · claude-medium (Claude Sonnet 5.5)

**Finding**: `deploy/host/bin/ririko-watchdog.sh`, `systemd/ririko-watchdog.{service,timer}` and the new "ririko-watchdog" section of `deploy/host/ririko.conf.example` define what the runbook has to document: the optional keys `HEALTHCHECK_PING_URL` (https only) and `DISK_ALERT_PERCENT` (1 to 100, default 85). The timer runs every minute (2 minutes after boot) on every host, also before ririko.conf is filled in and before the first deploy; with no container of compose project `ririko` a run logs one line and exits 0 without a ping.
**Impact on this ticket**: the runbook should cover: create a Healthchecks.io check per host with a 1 minute period and a few minutes of grace (silence means trouble, so a dead host or a docker outage alerts as well); put its ping URL in `HEALTHCHECK_PING_URL`; read the log with `journalctl -u ririko-watchdog` or `journalctl -t ririko-watchdog` (restarts and the reason of every failed check go through logger). Behaviour: an `unhealthy` container of project `ririko` is restarted with `docker restart`; the stack is healthy when bot, web and postgres report healthy and lavalink, if the project has one, is running (the Lightsail hosts have none); healthy and root file system below `DISK_ALERT_PERCENT` pings the URL, otherwise `<url>/fail` gets a one-line reason; while a container is only `starting` (after a boot or a restart) it sends neither, and the grace period decides. Containers of other projects (`ririko-lavalink`) are ignored. Exit codes of `ririko-watchdog`: 0 checked or skipped, 1 could not check (docker unreachable, lock file) or invalid setting, 2 bad command line. The watchdog takes the shared deploy lock without waiting and skips (exit 0, no ping) while a deploy or the backup dump holds it; it holds the lock only while it inspects and restarts containers (a few seconds at most), so a deploy that starts in that window exits 3 and CI can simply retry. A long deploy (up to READY_TIMEOUT) therefore sends no heartbeat: use a grace period of at least that long on the staging and production checks, or accept one alert per slow deploy.
