## GROOMING · 2026-10-04T18:50:17Z · Claude Code (Opus 5.5)

**Approach**
1. Add a parameterized `deploy` job (`cimg/base:current`, `resource_class: small`).
2. Install cloudflared: download the pinned `cloudflared-linux-amd64.deb` from its GitHub release, check `sha256sum -c` against a sha256 you compute and commit, then `sudo dpkg -i`.
3. Write the SSH key and `known_hosts`, then run ssh with `-o ProxyCommand="cloudflared access ssh --hostname %h"`.
4. Extend the `release` workflow: `deploy-staging` (requires `release`), `approve-production` (`type: approval`, requires `deploy-staging`), `deploy-production` (requires `approve-production`). The last two use the final-only tag filter `/^v\d+\.\d+\.\d+$/`.
5. Write `scripts/circleci-deploy.test.ts` with `yaml` (a root devDependency since TASK-1761).
6. Update `docs/release.md`.

**Relevant code**
- `.circleci/config.yml`: the `release` job and the `release` workflow, and the comment that keeps its filter in sync with `RELEASE_TAG_PATTERN`.
- `scripts/release-tags.test.ts` already checks the release filter and that no `:latest` image is named. Keep those checks passing.

**Pitfalls**
- CircleCI runs a job on tags only when that job has a tag filter. Every new job needs `filters.tags.only` and `branches.ignore: /.*/`.
- Check `cloudflared access ssh --help` for the version you pin. Service tokens can be passed as `--service-token-id`/`--service-token-secret` or through the `TUNNEL_SERVICE_TOKEN_ID`/`TUNNEL_SERVICE_TOKEN_SECRET` environment variables; prefer the environment variables so the secret is not in ssh's argv.
- `DEPLOY_SSH_KEY_B64` is base64 because CircleCI context values are single-line.
- Only a restricted context stops a non-maintainer: the approval job itself has no context, but `deploy-production` runs with `deploy-production`. Document the security group setting.
- Agents never create the contexts, push tags or approve.

**Out of scope**
- Host scripts (TASK-1781). Changes to the `ci` workflow.

## GROOMING · 2026-10-04T20:32:34Z · Claude Code (Opus 5.5)

**Verified on the staging host (cloudflared 2026.9.3)**
- `cloudflared access ssh --hostname %h` as the ssh `ProxyCommand` reads the Access service token from the `TUNNEL_SERVICE_TOKEN_ID` and `TUNNEL_SERVICE_TOKEN_SECRET` environment variables. Use them, not the command-line flags, so the secret stays out of argv.
- The `ssh-staging` Access application uses a Service Auth policy. Without a token the hostname answers 403; with one, the HTTP check answers 200 and SSH works.
- Pin `known_hosts` under the SSH hostname. The local test used `HostKeyAlias`; CI can store the line as `ssh-staging.ririko.ai ssh-ed25519 ...` instead.
