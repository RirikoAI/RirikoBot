## GROOMING · 2026-10-12T16:45:05Z · claude-opus-5-5 (coordinator)

**Approach**
1. Schema: add `leftAt` to `guilds` in `sqlite/identity.ts:21` and the pg twin. Additive only; no backfill (servers already inactive get `left_at` = NULL and are not purged; document that the first purge only covers servers that leave after this ships, or backfill `left_at = updated_at` for inactive rows in the same migration and say so in PROGRESS).
2. `GuildRepository.markInactive` (`guild.repository.ts:91`) sets `leftAt: now`. Find where a server is reactivated (upsert on guildCreate or the config sync) and clear `leftAt` there.
3. Inventory: grooming counted 41 `guild_id` columns across 17 SQLite schema files and **no foreign keys to `guilds`**, so nothing cascades. Build the inventory from the schema files; the guard test reads the Drizzle table objects and compares.
4. Purge in `DataRetentionService` after the TASK-1934 steps: select departed ids, then per server one transaction deleting from each inventoried table, then the `guilds` row.

**Pitfalls**
- Tables keyed by guild but holding user-owned value (for example a per-server economy, if any) still go: the server's data is what is being deleted. Global user tables have no `guild_id` and stay.
- The audit log has `guild_id`; it goes with the server.
- Run on staging carefully: the first run may delete a lot. Log counts per table.

**Out of scope**
- Per-user erasure (TASK-1941).

**Migration `0004_guild_left_at` (both dialects, additive)**
```
ALTER TABLE guilds ADD left_at integer;                                           -- pg: timestamp with time zone
UPDATE guilds SET left_at = updated_at WHERE is_active = 0 AND left_at IS NULL;   -- pg: is_active = false
```
Not a contract migration. The `UPDATE` is a deliberate backfill that I appended by hand to the generated file (the embedder and `db:check` read the SQL file, so they stay in step; the snapshot has no data). `markInactive` sets `updated_at` to the time of departure and nothing else updates an inactive row, so `updated_at` is the departure time. The 90 days of servers that are already inactive start then. Without it they would have `left_at` NULL and never be purged. A test runs the embedded backfill statement on both dialects.

**Maintainer: apply the migration to the local development database** (the one `next dev` on port 3000 uses), from the repository root with the same `DATABASE_URL` that `next dev` reads: `pnpm cli db:migrate` (`pnpm cli db:migrate --status` first shows it pending; it also applies `0002_user_consents` and `0003_data_retention_indexes` if they are still pending). The bot applies it at startup while `DB_AUTO_MIGRATE` is true. Restart `next dev` afterwards if it was started before the migration; queries on `guilds` select `left_at`, so they fail until it is applied.

**Before the first deploy to staging**: the first purge runs one minute after the bot is ready and removes the data of every server with `is_active = false` and `left_at` older than 90 days, which after the backfill means every server marked inactive more than 90 days ago. See what it will take first: `SELECT id, name, left_at FROM guilds WHERE is_active = false AND left_at < now() - interval '90 days'` (PostgreSQL). The log then shows one line per server with row counts.

**How the purge is made safe**
- Selection: `is_active = false AND left_at < cutoff` (cutoff = clock minus 90 days). A server that left exactly at the cutoff stays; 1 ms earlier it goes. Tested on both dialects.
- One server per transaction (`withTransaction`). Inside it `purgeGuild` reads the `guilds` row again with the same condition (`FOR UPDATE` on PostgreSQL) and returns `null` without deleting when the bot was added back between the list and the purge. A failure rolls that server back (tested with a `BEFORE DELETE` trigger on the last table, on both dialects); the other servers still run and the UTC day stays open for the hourly retry.
- Batches: every statement deletes or unlinks at most 5000 rows (`deleteInBatches` and `PURGE_BATCH_SIZE`, found by `rowid` on SQLite and `ctid` on PostgreSQL, because several tables have composite keys). Tests use a batch size of 2.
- Log: one line per purged server, counts per table only: `[DataRetention] Deleted server <id>: xp_accounts=12, guilds=1; unlinked from the server: reminders=2`. The summary line gains `departedGuild=N` (servers purged).
- Rejoin: `upsert` clears `left_at`, so a server back before 90 days is not listed and keeps everything (tested, also for the race).

**Decisions and gotchas**
- I did not stop at BLOCKED for the three user-owned tables (`economy_transactions`, `reminders`, `music_saved_playlists`) because I chose the action that loses no data: `detach`. The grooming note says tables keyed by guild go, but those three are a user's ledger, reminders and playlists with an optional server link. If the maintainer wants them deleted instead, change three entries of `GUILD_DATA_INVENTORY` from `detach` to `delete`, the tests that name them, and the sentence in privacy 7.2.
- Servers the bot left before the `guilds` table existed (TASK-1831) have no row, so their data in the other tables is never purged. Not part of this ticket. A one-time clean-up by hand, or a ticket, is needed if such data exists on staging or production.
- A bot that starts with an empty server list (a Discord outage at ready) marks every server inactive through `markInactiveExcept` (existing behaviour) and now also stamps `left_at`. The next successful ready or `GuildCreate` clears it, and the purge needs 90 days, so this is harmless unless the bot stays down for 90 days. The in-transaction recheck only protects against a rejoin that was already recorded.
- Two bot identities sharing one database would flap `is_active` and `left_at`, which is harmless for the same reason.
- The `guilds` row is deleted, so the owner console no longer lists a server 90 days after the bot left it (as the acceptance says).
- `reminders.channel_id` of a detached reminder still names a channel of the deleted server; the scheduler's channel fallback then fails and logs "unreachable", the DM path is unaffected.

## PROGRESS · 2026-10-17T16:00:00Z · ticket-worker (sonnet) / claude-sonnet-5-5 · REVIEW (rework addendum)

Maintainer decisions (2026-10-17): the three `detach` tables stay as chosen; the backfill changes. This entry replaces the backfill described in the entry above (and its "Before the first deploy" advice).

- Migration `0004_guild_left_at` (unreleased, edited in place): servers that are already inactive get `left_at` = the time the migration runs, so nothing is purged before 90 days after the 2.0 deploy. PostgreSQL: `UPDATE "guilds" SET "left_at" = now() WHERE "is_active" = false AND "left_at" IS NULL`. SQLite: `UPDATE guilds SET left_at = CAST((julianday('now') - 2440587.5) * 86400000 AS integer) WHERE is_active = 0 AND left_at IS NULL`. `left_at` is Drizzle `timestamp_ms` on SQLite, so it holds milliseconds since the epoch; I used `julianday` instead of `unixepoch('subsec')` because it works in every SQLite version. The migration comment says so. Embedded modules regenerated (`db:generate-migrations`); `pnpm db:check` passes.
- Test (`guild-data.behaviour.test.ts`, both dialects): runs the embedded statement on a server inactive for a year, reads `left_at` back through `GuildRepository` and asserts it is a `Date` within seconds of now (this proves the storage mode), that the active server stays NULL and a server already stamped keeps its time, and that right after the migration `listDepartedBefore(now - 90 days)` lists only the server stamped 100 days ago, while `purgeGuild` on the migrated server returns null and leaves its row.
- `docs/database.md` section 4.1 now says the 90 days of servers that are already inactive start when the migration runs. Nothing in `docs/legal/privacy.md` named `updated_at`.
- Effect for staging: no purge of departed-server data can happen until 90 days after the deploy, so the earlier pre-deploy query is no longer needed.
