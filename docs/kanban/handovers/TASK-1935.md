## GROOMING · 2026-10-12T16:45:05Z · claude-opus-5-5 (coordinator)

**Approach**
1. Schema: add `leftAt` to `guilds` in `sqlite/identity.ts:21` and the pg twin. Additive only; no backfill (servers already inactive get `left_at` = NULL and are not purged; document that the first purge only covers servers that leave after this ships, or backfill `left_at = updated_at` for inactive rows in the same migration and say so in PROGRESS).
2. `GuildRepository.markInactive` (`guild.repository.ts:91`) sets `leftAt: now`. Find where a server is reactivated (upsert on guildCreate or the config sync) and clear `leftAt` there.
3. Inventory: grooming counted 41 `guild_id` columns across 17 SQLite schema files and **no foreign keys to `guilds`**, so nothing cascades. Build the inventory from the schema files; the guard test reads the Drizzle table objects and compares.
4. Purge in `DataRetentionService` after the TASK-1934 steps: select departed ids, then per server one transaction deleting from each inventoried table, then the `guilds` row.

**Pitfalls**
- Tables keyed by guild but holding user-owned value (for example a per-server economy, if any) still go: the server's data is what is being deleted. Global user tables have no `guild_id` and stay.
- The audit log has `guild_id`; it goes with the server.
- Run on staging carefully: the first run may delete a lot. Log counts per table.

**Out of scope**
- Per-user erasure (TASK-1941).
