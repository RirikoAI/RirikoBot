## GROOMING · 2026-10-09T18:41:41Z · claude-opus-5-5 (coordinator)

**Approach**
- Add `adopt-baseline.ts`, called by the runner when the tracking table is missing and application tables exist.
- Find the expected shape:
  - Run the baseline statements in a scratch database: an in-memory SQLite database, or a temporary PostgreSQL schema created and dropped inside the adoption transaction.
  - Read the columns, types, nullability, defaults and indexes of both databases with the same queries: `information_schema.columns` and `pg_indexes` on PostgreSQL, `PRAGMA table_info` and `PRAGMA index_list` on SQLite.
  - This avoids parsing SQL.
- Diff: create missing tables from their `CREATE TABLE` statement in the baseline. Add a missing column with its type and default as the scratch database reports them. Create missing indexes from their baseline statement.
- Refuse cases: list them all in one `DatabaseError`, with the details in `details`.

**Relevant code** (from CodeGraph during grooming)
- `packages/database/src/migrations/guild-registry.ts`: per-column checks on both dialects, including the SQLite `PRAGMA table_info` path.
- `packages/database/src/migrations/text-ids.ts`: the PostgreSQL uuid-to-text repair. It must run before the type comparison, or every uuid column shows as a mismatch.
- `packages/database/src/migrations/card-serials.ts`: the duplicate-serial audit. It refuses instead of repairing; keep that behaviour.

**Pitfalls**
- Staging today: created by `PG_SCHEMA_DDL` plus the `ensure*` upgrades, then filled with the maintainer's data (2026-10-08). Its exact drift is unknown. The fixture in the acceptance list covers the known "needs `db:push`" columns; the generic diff covers the rest.
- PostgreSQL type names: compare `data_type` and `udt_name` with care (`character varying(32)` against `varchar`). Normalise both sides the same way, through the scratch schema.
- SQLite cannot add a column with a non-constant default (for example `CURRENT_TIMESTAMP`) through `ALTER TABLE`. If the baseline has one, refuse with a clear message, or rebuild that table. Check whether any baseline column needs this before you choose.
- Defaults on added NOT NULL columns fill existing rows, which matches the "existing rows keep working" rule.

**Out of scope**
- Removing extra columns or tables. Those are only logged.

**Decisions & gotchas**
- **Order inside a run** (all under the runner's lock, so a second process waits and then finds the tracking table):
  1. `checkAdoption`, read-only: scratch baseline shape, live shape (PostgreSQL uuid columns of `TEXT_ID_COLUMNS` count as the text columns the repair makes of them), the plan, and the duplicate card serial audit. Every problem goes into one `DatabaseError` ("cannot be adopted. Nothing was changed.") with `details.problems`. A dry run stops here and returns the plan in `adoption`.
  2. SQLite backup (`VACUUM INTO`, the runner's existing step), only after the check passed, so a refusal leaves no backup.
  3. `adoptBaseline`: `ensureTextIdColumns` on its own connection, then one transaction (BEGIN IMMEDIATE on SQLite): tracking table, the baseline row check, a re-read of the live shape, the plan again, the statements, the `adopted` row. A statement failure (for example a unique index over duplicate rows) rolls the whole transaction back, including the tracking table, and is reported as "Adopting the existing database failed and was rolled back".
  - The one change that stays when step 3 fails is the uuid-to-text repair on PostgreSQL, which `ensureTextIdColumns` commits on its own. It is idempotent and matches the baseline.
- **Expected shape without parsing SQL**, as groomed: SQLite runs the baseline in an in-memory database. PostgreSQL runs it in a transaction with `SET LOCAL search_path TO pg_temp`, so the baseline's `CREATE TABLE` statements create temporary tables, and the transaction is rolled back. This needs no CREATE privilege on the database or a schema. Both dialects read columns and indexes with the same queries for the live and the scratch side (`pg_attribute` and `format_type`, `pg_get_expr` for defaults, `pg_indexes`; `PRAGMA table_xinfo` and `sqlite_master`). The scratch shape is read once per run.
- Baseline statements are only parsed to find the names they create (`CREATE TABLE`, `CREATE [UNIQUE] INDEX ... ON`, `ALTER TABLE ... ADD CONSTRAINT`), which is how a missing table, its foreign key and its indexes are created. A statement of another kind makes the plan throw, so a future baseline format change cannot be silently skipped. A foreign key statement is run only for a table adoption created.
- Added column: `ADD COLUMN "c" <type> [DEFAULT <expr>] [NOT NULL]` with the type and default the scratch database reports. Refused with a reason: NOT NULL without a default; primary key or identity/generated column; on SQLite a default that is not a constant (`CURRENT_TIMESTAMP`, expressions). The current baseline has none of the SQLite cases (checked: no `CURRENT_*`, `strftime` or expression defaults in the SQLite baseline).
- Differing nullability or defaults on an existing column, extra tables and extra columns are logged through `log.warn` and returned in `adoption.notes`; they never refuse.
- Index matching is by name. A baseline index whose name is missing is created even if an equivalent index under another name exists; the extra index is harmless. A unique index that cannot be built over existing rows refuses (rolls back) as described.
- **Not done: removing `ensureAdventureSchema`, `ensureCardSerialSchema`, `ensureGuildRegistrySchema`.** The acceptance item allows removal only when no caller outside startup needs them. Their callers are exactly the startup paths and fixtures that TASK-1854 rewires (`apps/bot/src/main.ts`, `getDatabase` in `apps/web/src/lib/server/services.ts`, `copy-database.ts`, `testing/dialects.ts`, `bot-harness.ts`, and several service tests). Removing them here breaks the build, so they stay exported and I raised a FLAG on TASK-1854 to remove them (with their tests) when it replaces those callers. `ensureTextIdColumns` stays, as the ticket says. The adoption tests cover the same upgrade cases against the baseline (missing tables, indexes, columns, duplicate serials), so no coverage is lost.
- **Test infrastructure change in `runner.test.ts`:** PostgreSQL advisory locks are database-wide, not schema-wide. The existing `heldLocks()` assertions counted every `classid = 1706` lock in the test database, so they failed when another test file (mine) ran `migrateDatabase` at the same time. The helper now counts only locks held by connections with this test's `application_name` (the test schema name, set in the URL). This does not weaken the assertion.
- Most adoption tests use a small baseline that both dialects accept; PostgreSQL builds the 93-table schema only in the two tests that need the real baseline. This keeps the file at about 6 s instead of 21 s, so it adds less load to the slow copy tests.
- `next dev` on :3000: unaffected. Nothing at runtime calls the runner or adoption yet, and no schema or startup path changed. I did not run `db:push`.
