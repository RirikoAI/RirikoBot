## 1. Summary of Work Accomplished

- [crafting-recipes.ts](file:///Z:/Projects/ririko-v2-2026/packages/services/src/waifu-tcg/equipment/crafting-recipes.ts): a static, typed `CRAFTING_RECIPES` table (26 recipes) plus `findCraftingRecipe(code)`.
  - **Coverage**: six per-slot upgrade chains (WEAPON, ARMOR, RELIC, RING, AMULET, TALISMAN), each RARE → SUPER_RARE → ULTRA_RARE → top tier (SECRET_RARE, or SPECIAL_ILLUSTRATION_RARE for RELIC since no non-signature SECRET_RARE relic exists, or MYTHIC for WEAPON since no non-signature SECRET_RARE weapon exists) — every non-signature, drop-only piece in `CANONICAL_ITEMS` is covered. Plus 2 potion recipes: `CRAFT_POTION_MAJOR_HP` (3x `POTION_MINOR_HP`) and `CRAFT_POTION_GREATER_MANA` (3x `POTION_MANA_DRAUGHT`). `POTION_ELIXIR_VITALITY`, `POTION_COSMIC_ETHER` and all `ENERGY_POTION`s are deliberately excluded (reward-tier, would trivialize their systems if dust-buyable) — documented in a comment.
  - **Boss signature drops are never craftable** — verified by cross-checking every `outputCode` against `assets/tcg/catalog/bosses/s1_infernal_crucible.json`'s `signatureDropCode`s in the test suite (not hand-maintained duplicate list, so it can't drift).
  - **Pricing formula** (documented inline): `creditCost = round(shopPrice * (DAILY_ROTATION_MARKUP + 0.25))` — i.e. 1.75x list price, always above the Town Shop's 1.5x daily-rotation markup, so crafting a rotation item never undercuts buying it the day it's stocked. `dustCost = round(shopPrice/1000 * 40 * RARITY_ENHANCEMENT_MULTIPLIERS[rarity])`, reusing `enhancement-service.ts`'s existing rarity multiplier scale so dust costs land on the curve players already know from +1..+10 enhancement.
  - **Gear-gated progression**: each chain tier's `unlockFloor` is set to the floor of the first S1 boss wall of that rarity bracket (10, 20, 30, 40; 45 for the WEAPON_WORLD_BREAKER MYTHIC capstone, one past the SECRET_RARE wall) — a piece helps clear the *next* wall after the player has proven they can clear the wall before it, so crafting never skips a boss fight. Upgrade-chain tiers 2+ also consume 1x the previous tier as an ingredient (melt-down-to-upgrade), reinforcing the gate.
- [crafting.service.ts](file:///Z:/Projects/ririko-v2-2026/packages/services/src/waifu-tcg/equipment/crafting.service.ts): `CraftingService` class.
  - `getHighestClearedFloor(userId, tx?)` — reads the active (non-tutorial) season via `DungeonSeasonRepository.findActiveSeason`, then `UserDungeonProgressRepository.findByUserAndSeason`; returns 0 if there's no active season or no progress row yet.
  - `listRecipes(userId): Promise<RecipeStatus[]>` — every recipe joined with its catalog item, lock status, owned dust/credits, and per-ingredient owned/required/sufficient counts, plus an overall `affordable` flag.
  - `craft(userId, recipeCode, quantity = 1): Promise<CraftReceipt>` — validates recipe existence, quantity bounds, unlock floor, dust, credits and ingredients (with clear `DatabaseError` messages matching `EnhancementService`'s style), then spends and grants.
  - **Quantity rule (decided & documented)**: EQUIPMENT/ACCESSORY output recipes cap at 1 per call (`MAX_EQUIPMENT_CRAFT_QUANTITY`) since each instance needs its own enhancement level; MATERIAL/CONSUMABLE (potion) recipes allow up to 10 (`MAX_CONSUMABLE_CRAFT_QUANTITY`).
  - **Ingredient consumption**: stackable materials/potions come off the IDLE stack via `ItemGrantService.consume`; individual gear/accessory ingredients are selected from `UserInventoryItemRepository.findByUser(userId, { state: 'IDLE' })` only (excludes `EQUIPPED` rows entirely) and removed lowest-`enhancementLevel`-first.
  - **Atomicity**: the entire `craft()` body runs inside one `withTransaction(this.dbClient, ...)` call (the same primitive `MarketService` and `EconomyRepository.modifyBalance` use — SQLite `BEGIN IMMEDIATE`/`SAVEPOINT`, Postgres native tx). Every balance/floor/ingredient check re-reads state from inside that transaction right before spending, then dust → credits → ingredients are consumed and the output is granted; any throw anywhere rolls the whole thing back, so there is no window where currency can be lost or a partial spend observed. No new DB tables were needed.
  - Constructor: `new CraftingService(itemRepo, inventoryRepo, economyRepo, progressRepo, seasonRepo, dbClient)` — `GameItemRepository`, `UserInventoryItemRepository`, `EconomyRepository`, `UserDungeonProgressRepository`, `DungeonSeasonRepository`, `DatabaseClient`, all from `@ririko/database`.
  - Errors: throws `DatabaseError` (from `@ririko/core`) for every domain failure (unknown recipe, bad quantity, locked, insufficient dust/credits/ingredients) — same convention `EnhancementService`/`TcgShopService` already use in this folder.
- [index.ts](file:///Z:/Projects/ririko-v2-2026/packages/services/src/waifu-tcg/equipment/index.ts): exports `crafting-recipes.js` and `crafting.service.js`, same pattern as the other equipment services.
- [crafting.test.ts](file:///Z:/Projects/ririko-v2-2026/packages/services/src/waifu-tcg/__tests__/crafting.test.ts): 15 tests, real in-memory SQLite (`createDatabaseClient({ dialect: 'sqlite', url: ':memory:', autoMigrate: true })`), following `item-grants.test.ts`/`crafting-dust.test.ts` conventions.
  - Table invariants: unique codes, every output/ingredient code exists in `CANONICAL_ITEMS`, no signature drop craftable (cross-checked against the boss JSON, not a hand copy), positive costs/quantities/floors.
  - Service behavior: locked recipe rejected; insufficient dust rejected (no balance change); insufficient credits rejected (no balance change); missing ingredient rejected (no balance change); successful base-tier craft deducts exactly and grants output; ingredient-consuming upgrade craft removes the ingredient and grants the upgrade; **equipped ingredient is never consumed** (craft fails while the only copy is equipped, succeeds and takes only the unequipped copy once one exists, equipped copy stays equipped throughout); quantity cap of 1 enforced for equipment; quantity cap of 10 enforced for potions; batched potion craft scales dust/credits/ingredients by quantity; `listRecipes` reports lock/affordability/ingredient shortfalls correctly.

## 3. Roadblocks, Gotchas & Decisions Made

- No `.codegraph/` index exists in this repo despite the global CLAUDE.md mentioning it — fell back to `grep`/`Read`/`Bash` exploration as instructed for unindexed repos.
- `EnhancementService` does **not** debit credits itself (the docstring says "the caller debits them through the economy ledger" — credits are passed in and only checked). `CraftingService` instead follows the `TcgShopService` pattern and owns the credit debit directly via `EconomyRepository.modifyBalance`, per the task's explicit guidance to study both. Worth knowing for TASK-1602: the bot layer does **not** need to pre-fetch/debit credits for crafting the way it might for enhancement — `craft()` handles credits end-to-end.
- `RELIC` and `WEAPON` chains only have 4 non-signature drop-only tiers each in the current catalog (no non-signature SECRET_RARE relic or weapon exists), so their top tier uses `SPECIAL_ILLUSTRATION_RARE` (Phoenix Feather) and `MYTHIC` (World Breaker) respectively instead of `SECRET_RARE`, with `unlockFloor` set accordingly (40 and 45). This is intentional, not a gap — if a future season adds a non-signature SECRET_RARE relic/weapon, it slots naturally into the existing `GEAR_CHAINS` array in `crafting-recipes.ts`.
- `getHighestClearedFloor` reads the currently-active, non-tutorial season (`DungeonSeasonRepository.findActiveSeason`). If a new season starts, players' `highestClearedFloor` progress resets per-season (existing dungeon-progress design, not something this task changed) — so crafting unlocks re-gate to the new season's progress too. That matches how the dungeon system already works; no special-casing was added.
