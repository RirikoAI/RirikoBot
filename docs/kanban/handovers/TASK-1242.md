## GROOMING · 2026-10-02T12:28:45Z · Claude Code (Opus 5.5)

**Approach**
- `TradeService.acceptTrade` (`trade-service.ts:178`) and `MarketService.buyListing` (`market-service.ts:126`) check status before `withTransaction` and never re-check inside it.
- Inside each transaction, move the trade or listing state first with a conditional update (`WHERE id = ? AND status = 'PENDING'` / `'ACTIVE'`). When no row changed, throw the existing not-found or not-active error so the transaction rolls back.
- Add a `describeDialects` test that runs two accepts and two purchases concurrently.

**Relevant code**
- `packages/database/src/transactions/index.ts:53` `withTransaction`: SQLite serialises with a mutex, Postgres uses a pool transaction.
- `economy.repository.ts:213-223` locks balances `FOR UPDATE`.

**Pitfalls**
- On Postgres, two concurrent conditional updates on one row serialise on the row lock; the loser sees 0 rows after the winner commits (READ COMMITTED re-check).

- Against the old services (`git show HEAD:…`), both race tests fail on both dialects: both accepts and both purchases succeed.

**Decisions & gotchas**
- On Postgres the second concurrent claim blocks on the row lock and, after the first commits, re-checks the WHERE under READ COMMITTED and matches nothing. On SQLite the transaction mutex serialises the two calls.
- Reject, cancel and expiry share the same check-outside-transaction pattern, so they got the same claim. Without it, a cancel racing an accept could mark an accepted trade CANCELLED, and an expiry racing a purchase could mark a sold listing EXPIRED and reset the buyer's card state.
- The race tests run the second call on a second connection pool on Postgres (`db.openClient()`), as two bot processes would.
