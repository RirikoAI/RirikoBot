## GROOMING · 2026-10-02T15:41:07Z · Claude Code (Opus 5.5)

**Approach**
- Add a `release` workflow in `.circleci/config.yml`. Its filters run it on tags `^v\d+\.\d+\.\d+(-.+)?$` and ignore every branch.
- The job builds `bot-runner` and `web-runner`, runs `scripts/docker-smoke.ts`, logs in with the `dockerhub` context, and pushes the tags.
- A small script in `scripts/` derives the tags from the git tag: `X.Y.Z`, `X.Y` and `X`, or only the full version for a prerelease. It has unit tests and never returns `latest`.

**Relevant code**
- `.circleci/config.yml:221-231`: the `ci` workflow, which stays unchanged.
- The existing `docker` job: copy its build and smoke steps.

**Pitfalls**
- Agents never run the push. The maintainer creates the `dockerhub` context.
- CircleCI runs jobs on tags only when every job in the workflow has a tag filter.

## PROGRESS · 2026-10-02T16:20:33Z · Claude Code (Opus 5.5) · REVIEW

**Files changed**
- `scripts/release-tags.ts` (new): `releaseTags` turns `v2.1.3` into `2.1.3`, `2.1` and `2`, and a prerelease into its full version only. It throws for anything else and never returns `latest`. The CLI prints one tag per line.
- `scripts/release-tags.test.ts` (new) checks the derivation and the CLI. It also checks that the CircleCI tag filter matches `RELEASE_TAG_PATTERN` and that the config never names a `:latest` image.
- `.circleci/config.yml`:
  - The image build, buildx setup and smoke steps moved into a `build-and-smoke` command, which the `docker` job now uses unchanged.
  - A new `release` job derives the tags first, so a bad tag fails before any build. It then builds and smokes both images, logs in with `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`, and pushes `ririkoai/ririkobot` and `ririkoai/ririkobot-dashboard` with each tag.
  - A new `release` workflow runs that job with `context: dockerhub`, only on tags `/^v\d+\.\d+\.\d+(-.+)?$/`, and ignores every branch.

**Verification**
- `pnpm vitest run scripts`: 19 tests pass. `pnpm typecheck`, `pnpm lint --quiet` and `prettier --check .circleci/config.yml` pass.
- I parsed the config with `yaml`: the `ci` workflow still has the same 8 jobs, and `docker` keeps its executor and `BUILDX_VERSION`.
- Not run: the release workflow itself. It needs a pushed tag and the `dockerhub` context, and both are maintainer-only.

**Decisions & gotchas**
- CircleCI runs no workflow on tags unless a job has a tag filter. The `ci` jobs have none, so a release tag runs only `release`.
- The images are built inside the release job instead of reusing the `docker` job's images, because the remote Docker engine does not share images between jobs.
- The pushes are not atomic. If a push fails partway, rerunning the job pushes the same tags again from the same commit.
