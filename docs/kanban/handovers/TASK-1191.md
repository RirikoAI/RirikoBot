**Approach**
1. **Schema.** Add `dbsc_session_id` (text, nullable, unique) and `dbsc_public_key` (text, nullable, JWK JSON) to `webSessions` in `packages/database/src/schema/sqlite/web.ts` and `pg/web.ts`. Regenerate DDL with `pnpm --filter @ririko/database db:generate-ddl`. `WebSessionPatch` picks the columns up automatically.
2. **Repository.** Add `findByDbscSessionId(sid)` to `WebSessionRepository`, for both dialects. Binding uses the existing `update`. Add SQLite tests next to the existing ones.
3. **New `apps/web/src/lib/server/auth/dbsc.ts`** (`server-only`). Keep it small and pure.
   - Constants: `BOUND_COOKIE = '__Host-ririko_bound'`, `DBSC_REGISTER_PATH = '/api/auth/dbsc/register'`, `DBSC_REFRESH_PATH = '/api/auth/dbsc/refresh'`, challenge TTL 2 minutes, bound cookie TTL 10 minutes.
   - `sealChallenge(vault, sid, now)` and `openChallenge(vault, value, sid, now)`, under the vault context `dbsc-challenge`.
   - `sealBoundCookie(vault, sid, now)` and `openBoundCookie(vault, value, now)`, under the vault context `dbsc-bound`. `openBoundCookie` returns the sid or null.
   - `verifyProof(jwt, { publicKey? })`:
     - Parse the three base64url parts. Require `typ: 'dbsc+jwt'` and `alg` in `ES256 | RS256`.
     - Registration: take the key from the header `jwk`. Refresh: use the stored JWK.
     - Verify the signature over `header.payload` with `node:crypto`. ES256 needs `dsaEncoding: 'ieee-p1363'`; RS256 uses `RSA-SHA256`.
     - Return `{ jti, jwk }` or null. Never throw on malformed input.
   - Builders: `registrationHeader(challenge)`, `challengeHeader(challenge, sid)` (structured-field strings, quote-escaped), and `sessionInstructions(sid)` (session instructions JSON):
     - `session_identifier`, `refresh_url`.
     - `scope: { include_site: false }`.
     - `credentials: [{ type: 'cookie', name: BOUND_COOKIE, attributes: 'Path=/; Secure; HttpOnly; SameSite=Lax' }]`.
4. **`SessionService`** (`session-service.ts`).
   - Extract the rotation in `completePasskeyCheck` (new random token, re-encrypted Discord tokens, row rename) into a private `rotate(row, patch)`. Reuse it for binding.
   - `registrationChallenge(session)`: returns a sealed challenge for `session.id`.
   - `bindDevice(token, proof)`:
     - Resolve the row (live, not bound). Verify the proof with the `jwk` from the header and `jti` = an open challenge for the row ID.
     - Rotate, with patch `{ dbscSessionId: random base64url, dbscPublicKey: JSON(jwk) }`.
     - Return `{ token, session, sid, boundCookie }` or a typed failure.
   - `refreshBinding(sid, proof | null)`:
     - Find the row by sid. Missing or not live: `{ kind: 'unknown' }`.
     - No proof or a bad proof: `{ kind: 'challenge', challenge }`.
     - Valid proof: `{ kind: 'refreshed', boundCookie }`.
     - Use the same `isLive` check as `resolve`.
   - `resolve(token, boundCookie?)`: when the row has `dbscSessionId`, require `openBoundCookie(...) === row.dbscSessionId`. Otherwise return null. Do not delete the row in that case: the real browser will refresh.
   - `SessionSummary.deviceBound` comes from `dbscSessionId !== null` in `listForUser`.
5. **Tests.** Generate keys in the test with `generateKeyPairSync('ec', { namedCurve: 'P-256' })` and `'rsa'`. Export JWKs and sign real JWTs with `node:crypto`. Cover:
   - Valid ES256 and RS256 proofs.
   - Tampered signature, `alg: none`, `HS256`, wrong `typ`, missing or invalid `jwk`.
   - A `jti` sealed for another session, an expired challenge, binding twice.
   - The full flow: bind, refresh (challenge, then refreshed), resolve with and without the bound cookie, an expired bound cookie, an unbound session unchanged, and rotation of the old token.

**Pitfalls**
- `exactOptionalPropertyTypes` is on. Type optional params explicitly.
- Base64url decode of the JWT parts must reject garbage without throwing past `verifyProof`.
- `createPublicKey` throws on a bad JWK. Catch it and treat it as an invalid proof.
- Accept only `kty` EC with `crv` P-256 for ES256, and `kty` RSA for RS256. Reject a JWK that contains private parts (`d`).
- Compare challenges and sids with `timingSafeEqual`, the way `openPendingLogin` does.
- Do not delete a bound row when its bound cookie is missing.

**Out of scope**
- Route handlers, cookies on responses, `getSession`, UI and docs. These are TASK-1192.

- `bindDevice`:
  - Verifies the registration proof (the jwk comes from the header) and refuses an already bound session.

- `resolve(token, boundCookie)`:

  - `listForUser` reports `deviceBound`.
- Tests generate EC P-256 and RSA keys in the test and sign real JWTs. They cover every rejection plus the full bind, challenge, refresh and resolve flow, the RS256 binding, and the binding kept through a passkey check rotation.

**Decisions & gotchas**
- The stored JWK holds only the public members (`kty, crv, x, y` or `kty, n, e`). A jwk with private members is rejected, not stripped.
- For `refreshBinding`, a stored key that is not valid JSON returns `unknown`, which cannot happen through `bindDevice`. A bad proof returns a new challenge, as the W3C draft expects.
- `bindDevice` returns `no_session` when the row is renamed concurrently, because `update` on the old ID then misses. Two simultaneous registrations therefore cannot both bind.
- The registration challenge is sealed for the row ID. `completePasskeyCheck` renames the row, so a registration Chrome posts after a passkey check rotated the ID fails with `invalid_proof`. Chrome registers right after the callback response, well before a user finishes a passkey prompt, so this is unlikely. TASK-1192 can also issue a fresh `Secure-Session-Registration` after the verify step if wanted.
- The W3C draft puts the key in the JWT header `jwk`, as groomed. Older Chrome origin-trial builds used a payload `key` claim, and those are not supported.
- Dev databases need `pnpm db:push` for the two new columns and the index. The user's `next dev` shares this tree.
