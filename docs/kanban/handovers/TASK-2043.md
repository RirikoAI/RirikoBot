## GROOMING · 2026-10-23T15:52:42Z · claude-opus-5-5 (coordinator)

**Approach**
- Steps, each idempotent: verify master → tag → push tag → wait for the images → publish the GitHub release → move `latest` → report staging.
- Read the Docker Hub tags from `https://hub.docker.com/v2/repositories/<repo>/tags/<tag>` (digest field).
- Report the staging state from `gh api repos/RirikoAI/RirikoBot/commits/<sha>/status` for the contexts `ci/circleci: deploy-staging` and `deploy-lavalink-staging`.

**Pitfalls**
- `docker buildx imagetools create` wraps the manifest in a new index, so the digest of `latest` differs from the version tag by design. Check the result by its child manifest, not by an equal digest.
- Never click or call `approve-production`.

**How it works**
- Refusals first, read-only (`git fetch origin master`, `git show origin/master:<file>` into a temp dir, then `checkVersion` on it): the version must be in all 17 places on origin/master; no open develop-to-master PR; the latest merged develop-to-master PR's merge commit must be an ancestor of origin/master; a tag on origin or locally at another commit is refused (a version is never reused); the notes file must exist unless the GitHub release already exists.
- Steps, each tested for "already done" first and skipped: (1) `git tag -a vX -m "Ririko X" <origin/master sha>`; (2) `git push origin refs/tags/vX`; (3) poll Docker Hub every 30 s up to 40 min until both images have X.Y.Z, X.Y and X with one digest per image; (4) `gh release create vX --verify-tag --title "Ririko X" --notes-file <notes> --latest` (an existing release that is a draft or not Latest gets `gh release edit --draft=false --latest`); (5) per image `docker buildx imagetools create --tag <repo>:latest <repo>@<digest of X.Y.Z>`, then polls up to 5 min until `latest` shows the same image; (6) prints the `ci/circleci: deploy-lavalink-staging` and `deploy-staging` commit statuses and says production is not approved. It never calls CircleCI.
- Done-check for `latest` compares the child image digests as well as the index digest, because `imagetools create` can wrap the source in a new index (the handover pitfall).
- `--dry-run` runs the refusals and the read-only done-checks, prints every step with its command and "already done, would skip", and changes nothing. The notes file defaults to `.local/release-notes-vX.Y.Z.md`; `--notes <file>` overrides.

**Verification**
- `pnpm vitest run scripts/release`: 6 files, 108 tests pass. `pnpm typecheck`, `pnpm lint --quiet`, `pnpm format:check` pass. By hand, strict tsc (strict, exactOptionalPropertyTypes, noUncheckedIndexedAccess, noUnusedLocals, noUnusedParameters) on `publish.ts` and `publish.test.ts`: clean.
- Manual, read-only: `pnpm release:publish 2.1.0 --dry-run` on the real repository printed all seven steps and reported steps 1 to 6 as already done (tag on master, images on Docker Hub, release Latest, `latest` equal to 2.1.0). Nothing was published, tagged or pushed; the only side effect is the `git fetch origin master` that updates `origin/master`.

**Decisions & gotchas**
- `gh release view --json` has no `isLatest` field in gh 2.100.0 (found by the real dry run); "is Latest" comes from `gh api repos/{owner}/{repo}/releases/latest` (`tag_name`). `{owner}/{repo}` is filled in by gh from the checkout.
- "One digest each" is read as: for each image, the three tags share one digest. A rerun for an older minor after a newer patch moved `X.Y` or `X` would wait until the timeout and say which tags disagree.
- The timeout error and every step failure say to run the same command again; the tag push is the point of no return for CircleCI, so a failure after step 2 never repeats it.
- The dry-run display wraps a command argument in quotes when it contains a space, which includes the `<digest of ...>` placeholder; cosmetic only.
- `docs/release.md` still says agents never tag or move `latest`; that is CHORE-2012 / TASK-2044 territory and was not touched.
