## 1. Summary of Work Accomplished
**Symptom:** `next start` logged `This rendered a large document (>512 kB) without any Suspense boundaries around most of it` on every `/account/album` view, and the album was slow to paint.

**Root cause:** `CardAlbumService.page()` drew all 24 cards of a page before the page could render, and returned each 800×1200 PNG (about 0.6 MB) as a `data:image/png;base64,...` URL. Each URL appears twice in the response, once in the HTML and once in the RSC payload. Measured on a seeded SQLite database: **42,077,236 bytes** of HTML, **5.9 s** to first byte with an empty `public/cards/` cache, 0.5 s with a warm cache.

**Options evaluated:**
- *Suspense boundary around the grid:* silences the warning and paints the header sooner, but still streams the same ~42 MB of base64, which no browser can cache. Rejected.
- *Owner-only route handler + `<img src>`:* chosen. The HTML stays small, the browser loads images lazily and in parallel and can revalidate them, and the CSP is unchanged because images stay on `'self'`.

**Changes:**
- [waifu-card.repository.ts](file:///Z:/Projects/ririko-v2-2026/packages/database/src/repositories/waifu-card.repository.ts): new `findUserAlbumEntry(userId, userCardId)`, the same four-table join as `listUserAlbum`, filtered by owner **and** id. It works on both dialects; on Postgres a non-uuid id returns null, following `UUID_PATTERN` as `ItemCategoryRepository` does.
- [card-album.service.ts](file:///Z:/Projects/ririko-v2-2026/packages/services/src/waifu-tcg/album/card-album.service.ts):
  - `page()` only maps rows. `AlbumCard.image` is removed.
  - New `cardImage(userId, userCardId): Promise<Buffer | null>`: null when the card is not the user's, and the promise rejects when the card cannot be drawn.
  - Draws are queued per user (`oneAtATime`). This keeps the old "one card at a time" load cap now that the browser requests a page's images in parallel.
- [api/album/cards/[userCardId]/route.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/app/api/album/cards/[userCardId]/route.ts) (`GET`):
  - Calls `requireSession('/account/album')` first. Without a session it redirects to login.
  - Returns 404 (`text/plain`, `no-store`) for any card that is not the signed-in user's.
  - Returns 500 and logs `[album] Could not draw card <id>:` when the draw fails.
  - Otherwise returns `image/png` with `Cache-Control: private, no-cache` and a SHA-256 `ETag`, and answers 304 when `If-None-Match` matches.
  - It lives under `/api`, so `proxy.ts` (CSP nonce) skips it, as it skips the auth routes.
- [account/album/card-image.tsx](file:///Z:/Projects/ririko-v2-2026/apps/web/src/app/account/album/card-image.tsx): client component `AlbumCardImage`. It renders a lazy `<img width=800 height=1200>` and swaps in the existing "This card could not be drawn right now." placeholder on `onError`. A mount-time `complete && naturalWidth === 0` check covers an image that failed before hydration.
- [account/album/page.tsx](file:///Z:/Projects/ririko-v2-2026/apps/web/src/app/account/album/page.tsx): uses `AlbumCardImage` with `src=/api/album/cards/<userCardId>`. The filters, pagination, counts and empty states are unchanged.
- [authorization-coverage.test.ts](file:///Z:/Projects/ririko-v2-2026/apps/web/src/lib/server/authorization-coverage.test.ts): the new route is in the expected entry points, so the scan must keep finding its guard.
- [docs/dashboard.md §2.5](file:///Z:/Projects/ririko-v2-2026/docs/dashboard.md) describes the route and caching.

## 3. Roadblocks, Gotchas & Decisions Made
- **E2E suite timing:** the Playwright suite (`TASK-1201`, PR #669) landed on `develop/2.0.0` after this fix was written, so `develop/2.0.0` was merged into this branch and the suite was run against the fix. The Chromium checks of image loading and the fallback described above were one-off scripts and are not part of the suite.
- **Why `no-cache` instead of `max-age`:** a card can be traded, an asset can be taken down (`isDeletedByRequest` renders a silhouette), and a shared browser can switch users. With `max-age`, the browser would show its cached copy without asking the server, which bypasses the owner check. Revalidation costs one owner lookup and one cache-file read per image, and the browser downloads nothing when the image is unchanged.
- **Why not `next/image`:** its optimizer fetches the image server-side without the user's session cookie, so it cannot load an owner-only route.
- **The CSP is unchanged.** `img-src` still allows `data:` because the welcome and farewell card preview ([card-page.tsx](file:///Z:/Projects/ririko-v2-2026/apps/web/src/app/dashboard/[guildId]/welcome/card-page.tsx)) uses a data URL. That page renders a single image, so it does not hit the size problem.
- **Extra DB work:** each image request runs `waifu_cards` `count()` for `maxCollectionNumber`, which is a cheap aggregate. It used to run once per page.
- **No rate limit on the route.** A user can only make the server draw cards they own, and each card is drawn once and then served from `public/cards/`. Silhouettes of taken-down art are the exception: they are drawn again on every request.
- **Not mine:** `BOARD.md` already lists `STORY-167` and `STORY-168` twice on `develop/2.0.0`, so the protocol §8.3 duplicate check prints them. Left as is.
