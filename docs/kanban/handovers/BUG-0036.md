## GROOMING · 2026-10-05T00:09:20Z · Claude Code (Opus 5.5)

**Evidence** (lavalink-staging, smoke start of `lavalink-staging` from `deploy/lavalink/docker-compose.yml` at the pushed branch)
- Image `ghcr.io/lavalink-devs/lavalink:4.2.2`: `User=lavalink`, `id` → uid=322 gid=322. `/opt/Lavalink` is owned 322:322; `/opt/Lavalink/plugins` does not exist in the image.
- The volume `ririko-lavalink_lavalink_staging_plugins/_data` was created `drwxr-xr-x 0 0` (root).
- Log: `java.io.FileNotFoundException: ./plugins/lavasrc-plugin-4.8.3.jar (Permission denied)`. The container status was "Restarting (1)".
- Docker copies ownership into a new named volume only when the mount target already exists in the image. Here it does not, so the volume stays root-owned.

**Approach**
- Per Lavalink service, add an init service, for example:
  ```yaml
  lavalink-staging-plugins:
    image: ghcr.io/lavalink-devs/lavalink:4.2.2   # same pin; a test keeps them equal
    user: root
    entrypoint: ['chown', '-R', '322:322', '/opt/Lavalink/plugins']
    cap_drop: [ALL]
    cap_add: [CHOWN]
    security_opt: [no-new-privileges:true]
    restart: 'no'
    volumes: [lavalink_staging_plugins:/opt/Lavalink/plugins]
  ```
  with `depends_on: { lavalink-staging-plugins: { condition: service_completed_successfully } }` on the Lavalink service.
- Check that `chown` exists in the image (`docker run --rm --entrypoint sh ghcr.io/lavalink-devs/lavalink:4.2.2 -c 'command -v chown'`). If it does not, use the image's busybox or coreutils; do not add a new image.
- In the base `docker-compose.production.yml`, do the same for `lavalink` (volume `lavalink_plugins`).
- In `docker-compose.remote-lavalink.yml`, put the bundled init service in profile `bundled-lavalink` too.

**Pitfalls**
- `network_mode: host` is not needed on the init services.
- `ririko-watchdog` (lavalink role, TASK-1803) must not count an exited init container (status exited 0) as a broken instance. Check how TASK-1803 lists containers and tell the coordinator if it needs a follow-up.
- TASK-1803's deploy recreates only `lavalink-<instance>` with `up -d --no-deps`, which skips the init service. Raise this with the coordinator; the deploy may need `up -d lavalink-<instance>-plugins lavalink-<instance>`, or `--no-deps` dropped.

**Out of scope**
- Pinning plugin versions or changing `application.yml`.
