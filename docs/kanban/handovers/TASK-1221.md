## PROGRESS · 2026-10-02T09:45:30Z · Claude Code (Opus 5.5) · REVIEW

**Files changed**
- `apps/bot/src/health.ts` (new):
  - `probe(path, sources)` builds the `/health` and `/ready` answers. `healthPort` reads `HEALTH_PORT` (default 8080; 0 turns the probes off). `startHealthServer` uses `node:http` on 0.0.0.0, allows GET and HEAD only, and sends `no-store` JSON.
  - `/health` answers 200 or 503 by database ping, with version, uptime, gateway state and ping, and database latency and error.
  - `/ready` answers 200 only when startup has finished, the database is up and the gateway is `READY`.
- `apps/bot/src/main.ts`:
  - The server starts right after the database client is created.
  - `started` flips after the listeners and the case log are registered.
  - The server closes on shutdown.
- `packages/core/src/config/schema.ts`: `HEALTH_PORT`. `.env.example` documents it.
- `apps/web/src/lib/server/health.ts` (new): `webProbe`. Its public bodies carry no error text; errors go to the server log.
- `apps/web/src/app/api/health/route.ts` and `api/ready/route.ts` (new), with `/health` and `/ready` rewrites in `next.config.ts`.
- `apps/web/src/lib/server/rate-limit.ts`: a `probes` limiter and `limitProbeRequest` (30 per IP, 1 per second), because each probe pings the database.
- `testing/authorization-coverage.ts`:
  - `PROBE_ROUTE_ALLOWLIST` makes the two public probe routes call `limitProbeRequest`.
  - The coverage test covers it.
- `Dockerfile`: a `HEALTHCHECK` on both runners, using `node -e fetch`.
  - Bot: `HEALTH_PORT`, start-period 120s.
  - Web: `/api/health`, start-period 60s.
- `scripts/docker-smoke.ts`:
  - The bot boot check also requires the probe server to start.
  - The new `botHealthcheckCheck` runs the image's real HEALTHCHECK command against the bot's probe server inside the image, and checks that `/ready` is 503 while the gateway is not READY.
  - The web check requests `/health`, `/ready` and `/api/health`, and runs the HEALTHCHECK command.
- `docs/deployment.md` section 3 now describes the real probes, with no Redis.
- Tests: `apps/bot/src/health.test.ts` (probe states, port parsing, the HTTP server), `apps/web/src/lib/server/health.test.ts`, and `apps/web/src/app/api/health/route.test.ts` (routes and the 429).

**Verification**
- `pnpm vitest run apps/web/src apps/bot/src packages/core scripts`: 868 pass.
- `pnpm typecheck`, `pnpm build` and `pnpm lint --quiet` pass.
- `docker build` of both targets, then `node scripts/docker-smoke.ts bot web`: 10 of 10 pass, including the STORY-128 legacy migration.

**Decisions & gotchas**
- Without Discord, the bot exits after registering its commands. That is why the smoke script tests the probes through `botHealthcheckCheck`, not the boot container.
- In `botHealthcheckCheck`, the HEALTHCHECK child must be spawned asynchronously. `spawnSync` blocks the event loop of the process that serves the probe, and the call deadlocks.
- The web probes are public, so they answer `{ "ready": false }` with no reason. The bot port is not published, so its probes include the driver error.
