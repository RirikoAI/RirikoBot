## FLAG · 2026-10-10T08:14:32Z · from TASK-1852 · claude-opus-5-5 (coordinator)

**Finding**: `packages/database/src/client/sqlite.ts:33` enables `foreign_keys = ON`. `runner.ts` (`openSqlite` `apply`) runs every statement of a migration inside `withTransaction` (BEGIN IMMEDIATE). drizzle-kit writes a SQLite table rebuild as `PRAGMA foreign_keys=OFF`, create `__new_x`, copy, `DROP TABLE x`, rename, `PRAGMA foreign_keys=ON`. SQLite ignores `PRAGMA foreign_keys` inside a transaction. The `DROP TABLE x` then does an implicit DELETE with foreign keys on: `ON DELETE CASCADE` children are deleted, and other references make the migration fail.
**Impact on this ticket**: such a migration needs the contract marker, because the lint already flags `DROP TABLE`. Without a runner fix, a contract migration on SQLite can still lose rows. Scope added to this ticket (see the GROOMING update below).

## GROOMING · 2026-10-10T08:14:32Z · claude-opus-5-5 (coordinator) · scope update

**Added: SQLite rebuild safety in the runner** (3 to 5 points)
- In `runner.ts`, a SQLite migration that contains `PRAGMA foreign_keys=OFF` runs as SQLite's documented table-rebuild procedure:
  1. Run `PRAGMA foreign_keys=OFF` on the connection before BEGIN.
  2. Run the other statements in the transaction, skipping the two PRAGMA statements.
  3. Before COMMIT, run `PRAGMA foreign_key_check`. Any row rolls back with a `DatabaseError` that names the table.
  4. In `finally`, restore `foreign_keys` to its previous value.
- Test it in `runner.test.ts` (SQLite): a drizzle-style rebuild of a parent table that has `ON DELETE CASCADE` children keeps every child row. A rebuild that leaves a dangling reference rolls back.
- PostgreSQL does not need this: drizzle-kit uses `ALTER TABLE` there.

**How the checks work**
- schema: per dialect, copy `migrations/<dir>` into a temp dir, run `drizzle-kit generate --dialect … --schema <abs> --out ./<dir>` there (cwd = temp dir; drizzle-kit joins `out` to cwd, so an absolute `out` on another drive fails), no stdin, 180 s timeout. A new `.sql` file is a problem and its SQL is printed. A non-zero exit (what a rename prompt gives without a TTY) or timeout is a problem that tells the author to run `pnpm db:generate` locally. The real folder is never written. Checked by hand with an extra table in a temporary schema copy: it reported `0001_….sql` with `CREATE TABLE "tmp_check"`, and `migrations/` stayed untouched.
- embedded: `renderMigrationsModule(readMigrations(dir))` compared with `src/migrations/generated/<dir>.ts` (CRLF tolerated); journal/name errors from the reader become problems.
- safety: `maskSql` blanks comments and the inside of string literals, quoted identifiers and dollar quotes, then DROP TABLE, DROP COLUMN, RENAME, ALTER COLUMN … [SET DATA] TYPE and SET NOT NULL are matched per statement, case-insensitive. A file whose first line is `-- ririko:contract` is skipped. The baselines pass (also asserted in a test).
- Not covered: detecting an edit to an already released migration that was re-embedded (needs git history). The runtime checksum check still stops that on every database that applied it.

**SQLite rebuild safety (FLAG from TASK-1852, addressed)**
- `runner.ts` `openSqlite().apply`: a migration containing `PRAGMA foreign_keys=OFF` reads the current setting, sets `foreign_keys = OFF` before BEGIN, skips both `PRAGMA foreign_keys` statements in the transaction, checks inside the transaction that the setting really is off (another task's open transaction would make the pragma a no-op; it then throws and rolls back), runs `PRAGMA foreign_key_check` before COMMIT (a row throws `DatabaseError` naming each child table and parent; the run reports it as `Migration … failed and was rolled back: The rebuild left dangling foreign keys: table "child" has 1 row(s) …`), and restores the previous setting in `finally`.
- Tests (SQLite, `runner.test.ts` "table rebuilds"): a drizzle-style rebuild of a parent with an `ON DELETE CASCADE` child and a plain referencing table keeps every row and leaves foreign keys on; a lossy rebuild rolls back, names both tables and records nothing; a failing statement restores the setting; a connection that had foreign keys off keeps them off; the no-op-pragma case is refused; one test shows the old behaviour (pragma ignored in a transaction, `DROP TABLE` cascades) so the hazard stays documented.
