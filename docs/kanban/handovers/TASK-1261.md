## GROOMING · 2026-10-01T16:10:59Z · Claude Code (Opus 5.5)

**Approach**
1. Pull `ririkoai/ririkobot:latest` (approved by the maintainer; about 708 MB, amd64) and record its digest.
2. Run it once against a throwaway named volume, with dummy credentials. Its `CMD` runs `npm run migration:run && npm run seed:run && npm run start:prod`, so the database is complete before the login fails:
   `docker run --name ririko14 -v ririko14_data:/app/data -e DATABASE_TYPE=better-sqlite3 -e DATABASE_NAME=/app/data/ririko.db -e DISCORD_BOT_TOKEN=x -e DISCORD_APPLICATION_ID=1 ririkoai/ririkobot:latest`
3. `docker cp ririko14:/app/data/ririko.db` to the scratchpad. Dump `SELECT sql FROM sqlite_master WHERE sql IS NOT NULL`, using better-sqlite3 from the workspace, into `packages/database/src/migration/__fixtures__/legacy-1.4.0-schema.sql`. Record the seed rows it inserted in the PROGRESS entry (for example item categories), but do not commit data.
4. In `migration.test.ts`, build the legacy database from the fixture file. Insert rows with the real column names, including values in the formats TypeORM writes (dates as `datetime('now')` strings, booleans as 0/1, and so on).
5. Run the tests and fix each transformer or inspector mismatch with the smallest change in the responsible mapping.
6. Note the fixture's origin in `docs/migrations.md`. Remove the container and volume, and the pulled image if it is not needed again (TASK-1262's smoke check builds its legacy database from the fixture, not from the image).

**Relevant code** (from CodeGraph during grooming)
- `packages/database/src/migration/transformer.ts:37` `getTableRows`: tries several table names (`user` and `users`, and so on). The real names come from `@Entity()` in `.local/RirikoBot/src/database/entities/*.entity.ts` and from the 12 TypeORM migrations.
- `packages/database/src/migration/inspector.ts:52` `expectedLegacyTables`: the inspector's own list of names.
- `packages/database/src/migration/types.ts`: the `Legacy*` row interfaces, which must match the real columns.

**Pitfalls**
- **Synchronize may be on:** the 1.4.0 image may also run TypeORM `synchronize` (`DATABASE_SYNCHRONIZE`). Do not set it. The schema should come from the migrations alone, as for most users. Note any difference you find.
- **Test hygiene:** tests run offline with no network, so the test must never pull the image. Only the committed `.sql` file is used.
- **Coverage:** keep the coverage thresholds green.

**Out of scope**
- The startup upgrade step, `legacy_migrations` and the image changes (TASK-1262).
- Postgres-sourced 1.4.0 databases.
