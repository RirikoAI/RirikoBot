## 1. Summary of Changes

### The Problem
When a user executed a tool in AI chat (e.g. `get_current_time`, `reminders.create`), the tool's result was summarized and embedded directly into the assistant's textual message (`🔧 *[tool_name]*: ...`). In isolated conversation memory (`ai_messages`), the turn was recorded with `toolCalls: [...]`.

In subsequent chat turns, `getContextMessages()` retrieved this previous assistant message with `toolCalls`. Because subsequent user messages do not contain `role: 'tool'` response messages for those past tool calls, the OpenAI Chat Completions API failed with HTTP 400:
```
OpenAI API error: 400 An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'. The following tool_call_ids did not have response messages: call_pYEEnFAui9JdsgyhFi8DvC66, call_OdQvaRsnbzWkdlA7OMFP3Cu3
```
This failure cascaded down the fallback chain to Ollama, which threw a 404 (model not found), rendering AI chat completely unusable for that user.

### The Solution
1. **OpenAI Provider (`packages/ai/src/providers/openai.provider.ts`)**:
   - In `mapMessages`, we inspect the conversation context to determine which assistant tool call IDs actually have matching `role: 'tool'` response messages (`respondingToolCallIds`).
   - If an assistant message contains `toolCalls` but none have matching tool responses in context (i.e. historical resolved turns loaded from DB), the unresponded `tool_calls` payload is omitted, mapping the message cleanly as a standard text assistant message (`role: 'assistant', content: msg.content`).
   - In active tool-calling loops where matching tool responses exist, tool calls and tool responses are preserved 1:1.
   - Any orphan tool messages without a matching assistant tool call are excluded to avoid OpenAI schema rejections.

2. **Gemini Provider (`packages/ai/src/providers/gemini.provider.ts`)**:
   - In `mapMessages`, unresponded function calls in historical assistant turns are omitted so that Gemini does not throw a 400 error requiring consecutive `functionCall` and `functionResponse` turns.

3. **Ollama Provider (`packages/ai/src/providers/ollama.provider.ts`)**:
   - In `mapMessages`, unresponded tool calls in historical assistant turns are omitted so that Ollama models supporting tool calling do not fail on unfulfilled tool calls.

## 3. Key Decisions & Gotchas

- **DB Schema Unaltered**: `tool_calls` column in `ai_messages` remains intact. This preserves full auditability in the database and dashboard so admins can see when tools were called without crashing future LLM generation turns.
- **Bi-Directional Safety**: In an ongoing multi-turn tool calling loop, tool calls and responses match by `toolCallId`. In subsequent conversational turns, the resolved response functions as standard assistant text.
