## GROOMING · 2026-10-10T10:11:45Z · claude-opus-5-5 (coordinator)

**Report** (maintainer, on the development database `./data/ririko.sqlite`, after PR #693):
```
✖ Migration failed: The existing database cannot be adopted. Nothing was changed.
- "adventure_players.last_start_at" is BIGINT but the baseline has INTEGER
- "adventure_players.cooldown_until" is BIGINT but the baseline has INTEGER
- "adventure_sessions.deadline" is BIGINT but the baseline has INTEGER
- "adventure_sessions.created_at" is BIGINT but the baseline has INTEGER
```
The same four lines then print a second time, indented.

**Root cause**
- `ensureAdventureSchema` (removed in TASK-1854; see `git show 8ffd7a6:packages/database/src/migrations/adventure-schema.ts`) created the tables with one DDL for both dialects: `cooldown_until BIGINT NOT NULL DEFAULT 0, last_start_at BIGINT NOT NULL DEFAULT 0` and `deadline BIGINT NOT NULL, created_at BIGINT NOT NULL`.
- The SQLite baseline (drizzle `integer`) declares `INTEGER`.
- `readSqliteShape` keeps the declared type text, and `planAdoption` compares it exactly.
- In SQLite, BIGINT and INTEGER have the same affinity and store the same values, so the refusal is wrong.
- PostgreSQL is fine: its baseline declares `bigint`, and `guilds.invited_*` are `varchar(32)` and `varchar(16)` in both the old upgrade and the baseline.

**Approach**
- Add a small `sqliteAffinity(declared)` that follows the five rules of datatype3.html section 3.1, in that order.
- In `planAdoption`, when `dialect === 'sqlite'` and the declared types differ:
  - same affinity: push a note such as `"adventure_players.last_start_at" is BIGINT, the baseline has INTEGER (same SQLite affinity); left as it is`;
  - different affinity: push the existing problem.
- Leave PostgreSQL exact.
- In `runDbMigrate` (around `db-migrate.ts:164`), when `details.problems` is present, print only the first line of the message, then the list.

**Pitfalls**
- Do not rewrite the columns to INTEGER (that would need a table rebuild). Adoption stays additive.
- The type compare must stay strict for different affinities: a TEXT column where the baseline has INTEGER is a real problem.
- Never run anything against the maintainer's `./data/ririko.sqlite`. The coordinator does a read-only `--dry-run` there during review.

**Out of scope**
- Normalising the declared types of existing SQLite tables.
