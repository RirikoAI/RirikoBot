## GROOMING · 2026-10-21T12:48:19Z · claude-opus-5-5 (coordinator)

**Asked by the maintainer** (2026-10-21, after PR #732): fix the shared reset date found while grooming BUG-0050.

**The bug**
- `player_energy.last_reset_date` serves two schedules. `EnergyLifecycleService` (built in `apps/bot/src/services.ts` with `resetSchedules.energy`) compares and writes it with the energy day key. `PlayerEnergyRepository` (built with `resetSchedules.energyPotions`) compares and writes it with the potion day key in `consumeEnergyPotion`, `create` and `getOrCreate`.
- With the defaults (`RIRIKO_RESET_TIME` for both) the keys match and nothing goes wrong. With, say, `RIRIKO_RESET_TIME_ENERGY=00:00` and `RIRIKO_RESET_TIME_ENERGY_POTIONS=06:00`, between 00:00 and 06:00 the energy key is day D and the potion key is D-1. Each potion writes D-1. The next `getOrReconcileUserEnergy` sees D-1 ≠ D and runs the daily rollover again: a full refill and another `dailyBonusIncrement`. So every potion in that window gives a free refill.
- The potion counter is also reset by the energy rollover (`getOrReconcileUserEnergy` sets `dailyEnergyPotsUsed = 0`), so it follows the energy boundary instead of its own.

**Relevant code** (no CodeGraph index in this container; line numbers from develop at b784b7e)
- `packages/database/src/repositories/player-energy.repository.ts:40-42` `currentDayKey` (potion schedule); `:66-100` `create`; `:102-150` `getOrCreate`; `:218-273` `consumeEnergyPotion` (compares and writes `lastResetDate`).
- `packages/services/src/waifu-tcg/energy/energy-lifecycle.service.ts`: `EnergyLifecycleOptions` (~:57), constructor (~:107-121), `getOrReconcileUserEnergy` (~:159-223, the rollover block at `record.lastResetDate !== today`), `consumePotion` (~:245), `replenishUserEnergy` (~:275-300).
- `packages/database/src/schema/sqlite/tcg.ts:~140-152` and `pg/tcg.ts:~134-145` `playerEnergy`.
- `apps/bot/src/services.ts:358` repository with `resetSchedules.energyPotions`; `:465` lifecycle with `resetSchedule: resetSchedules.energy`.
- `packages/core/src/time/reset-config.ts` `resolveResetSchedules`: all features share one offset; only the wall-clock time differs.

**Approach**
1. Schema: add `lastPotionResetDate` (`last_potion_reset_date`), nullable, no default, to `playerEnergy` in both dialects (`text` in SQLite, `varchar(16)` in PostgreSQL, like `last_reset_date`). Run `pnpm db:generate` (optionally `--name`, see `packages/database/scripts/generate-migrations-sql.mjs`); it writes `migrations/{sqlite,pg}/0005_*.sql`, the meta snapshots, the embedded `src/migrations/generated/*.ts` and the DDL files. Review the SQL: one `ALTER TABLE ... ADD` per dialect. Then `pnpm db:check`.
2. Repository: a helper such as `potionDayOf(record) = record.lastPotionResetDate ?? record.lastResetDate`. `consumeEnergyPotion` compares that against `currentDayKey()` and writes `lastPotionResetDate: today` (drop the `lastResetDate` write). `create` sets `lastPotionResetDate: data.lastPotionResetDate ?? today`; `getOrCreate` sets it in both dialect branches.
3. Lifecycle: add `potionResetSchedule?: ResetSchedule | undefined` to `EnergyLifecycleOptions`, defaulting to the resolved energy `resetSchedule` (the bare-`ResetSchedule` constructor form gets the same schedule for both). In `getOrReconcileUserEnergy`, remove `dailyEnergyPotsUsed = 0` from the energy rollover, and add a separate check: if `(lastPotionResetDate ?? lastResetDate) !== potionToday`, set `dailyEnergyPotsUsed = 0` and `lastPotionResetDate = potionToday`. `replenishUserEnergy` sets `lastPotionResetDate` with the potion key alongside its existing fields. `/energy` and the inventory potion summary read the reconciled row, so they follow the potion boundary with no change.
4. `services.ts`: pass `potionResetSchedule: resetSchedules.energyPotions` to the lifecycle.
5. Tests:
   - `reset-boundary.test.ts` (or a new file beside it): energy 00:00 and potions 06:00 in the same offset, time pinned between them (fake timers or `vi.setSystemTime`). Reconcile, drink a potion, reconcile/spend again: no second refill, `bonusEnergy` grew once. Potion counter: it is not reset by the energy boundary and is reset by the potion boundary.
   - `player-energy.repository.behaviour.test.ts`: a row with `lastPotionResetDate` null falls back to `lastResetDate`; `consumeEnergyPotion` leaves `lastResetDate` unchanged.

**Pitfalls**
- Migrations are never edited after release (AGENTS.md rule 5.9). Generate a new one; do not touch `0000`-`0004`.
- `PlayerEnergy` type comes from the schema (`schema/types`), so the new field shows up as `string | null`. Test fixtures that build a full `PlayerEnergy` literal may need `lastPotionResetDate: null` to typecheck; adding a field to a fixture is fine, removing an assertion is not.
- `schema.test.ts` and some migration tests create `player_energy` by hand or compare the DDL; update them only as far as the new column needs.
- `consumePotion` in the lifecycle reconciles first, so after the change the repository sees an up-to-date `lastPotionResetDate`. Keep the repository check anyway: `ConsumableService` and `InventoryService` fall back to the repository when no lifecycle is wired.
- The `exactOptionalPropertyTypes` setting: write optional option types as `T | undefined`.

**Out of scope**
- New rows still get `lastResetDate` from the potion schedule in `getOrCreate`; the lifecycle reconciles it on first read. Leave it.
- No change to the reset settings, the energy rules or the docs (`docs/waifu-tcg.md` already says energy and potions use the daily reset time).
