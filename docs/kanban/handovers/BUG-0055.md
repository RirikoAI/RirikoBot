## GROOMING · 2026-10-26T12:30:00Z · claude-opus-5-5 (coordinator)

**Found** on 2026-10-26, while responding to Node2Shell (CVE-2026-111497, a Brotli RCE in Node.js) and the eMudhra CA key compromise (CVE-2026-111943: eight intermediate CA keys can be recovered from their certificates, and each key is certified twice, so 16 certificates are affected). The maintainer asked for a patch release. These checks were made during grooming:

- **Bot and dashboard images: already patched, nothing to change.**
  - The config of the published `ririkoai/ririkobot` and `ririkobot-dashboard` 2.0.2, 2.1.0 and 2.1.1 images has `NODE_VERSION=22.23.4`, the fixed release. Node 22.23.4 also updates the bundled root store for eMudhra.
  - `node:22-trixie-slim` (Dockerfile lines 9 and 67) has the same digest as `node:22.23.4-trixie-slim`. CI has no Docker layer caching, so every build pulls the current base.
  - The `apt-get upgrade` layer of 2.1.1 has `ca-certificates 20250419+deb13u1` (DSA-6572-1). emSign ECC Root CA - G3 and AAA Certificate Services are gone from its store.
  - Do not touch the Dockerfile or `engines`.
- **Lavalink: not patched.**
  - `ghcr.io/lavalink-devs/lavalink:4.2.2` (deploy/lavalink/docker-compose.yml lines 22, 47 and 71; docker-compose.production.yml lines 45 and 61) is built `FROM eclipse-temurin:18-jre-jammy`, per the Lavalink repository's `LavalinkServer/docker/Dockerfile` at tag 4.2.2.
  - That base is Temurin 18.0.2.1, last rebuilt on 2022-09-02. Its `/opt/java/openjdk/lib/security/blocked.certs` has 39 lines: `Algorithm=SHA-256` and 38 fingerprints, none of them for eMudhra.
  - Java does not use the OS trust store. Lavalink 4.2.2 is the newest release.
- **The fixed list.** These builds ship a `blocked.certs` with the eMudhra entries, and the files are byte-identical:
  - Amazon Corretto 17.0.21 (`amazoncorretto:17`, 2026-10-23) and SapMachine 21.0.13.0.2 (`sapmachine:21-jre`).
  - sha256 `2596bb6dda83c66d96c5a252d7b2ae1f24cc1ae3f1890223b4f3591a8d52bf10`, 87 lines, ending with a newline. That is the 38 old fingerprints, none removed, plus 48 new ones: the 16 certificates in their as-issued and malleated encodings.
  - Zulu 17.0.20.1 and the current Temurin 17/21 images still have the old 39-line file.
  - The copy to use is `/tmp/claude-0/-home-user-RirikoBot/a5aebf59-6c8c-558f-9b22-4347831cdb6c/scratchpad/jdk/corretto17/usr/lib/jvm/java-17-amazon-corretto.x86_64/lib/security/blocked.certs`. Check its sha256 before you copy it.
- **`pnpm audit`:**
  - `next@16.3.8` (apps/web/package.json line 22 `~16.3.8`) has two critical advisories:
    - GHSA-2464-fhr4-w9xw: image optimizer RCE. Already blocked by our `sharp: ^0.35.5` override; the lockfile has sharp 0.35.5.
    - GHSA-673q-mjm6-r5xr: `use cache` RCE. Not reachable, because apps/web has no `use cache`.
  - It also has one high advisory, GHSA-p3m5-59mp-jv5r: a Server Actions DoS. It applies, because welcome backgrounds upload through a Server Action (next.config.ts `serverActions.bodySizeLimit`).
  - All three are fixed in 16.4.1. The latest is 16.4.3. The root package.json line 60 has `@next/eslint-plugin-next ~16.3.8`.
  - `tinypool@1.1.1` is only pulled in by `@docusaurus/core` 3.10.2, the latest, which asks for `^1.0.2`. It has two critical advisories (GHSA-5gmw-xhrv-c9v3, GHSA-85c8-ppgw-ccpr), fixed only in 2.1.2 or later. tinypool 1.1.1 and 2.2.0 are both `"type": "module"` with the same `exports`, and 2.2.0 has engines `^20 || >=22`.

**Approach**

1. *Why inline.* A Lavalink host gets only the files `LAVALINK_FILES` names in `deploy/host/bin/ririko-deploy.sh` (line 61): `deploy/lavalink/docker-compose.yml` and `docker/lavalink/application.yml`. The script is installed on the host by bootstrap and is not updated by a deploy. A new bind-mounted file would never reach the hosts, and Docker would create an empty folder in its place. So the list goes inline, as a Compose config with `content:` (Compose 2.23.1 and newer). Compose copies it into the container when it creates it, at the target path, mode 0444, and replaces the image's file.
2. *Host compose* (`deploy/lavalink/docker-compose.yml`): add a top-level `configs:` with `java-blocked-certs`, whose `content: |` is the vendor file with every line unchanged. On `lavalink-production` (line 46) and `lavalink-staging` (line 70) only, add:

   ```yaml
   configs:
     - source: java-blocked-certs
       target: /opt/java/openjdk/lib/security/blocked.certs
   ```

   Do not put it in the `x-plugins-init` anchor (line 21). The init services run `chown` only.

   Above the config, add a short comment:
   - eMudhra CA compromise (CVE-2026-111943);
   - the image's Java (Temurin 18, end of life) has no fix;
   - this is the `blocked.certs` of Corretto 17.0.21 and SapMachine 21.0.13.0.2, with its sha256;
   - inline because ririko-deploy downloads only this file and application.yml;
   - remove it once Lavalink ships an image on a fixed JRE.

   Changing the file changes its sha256, so `ririko-deploy` recreates the instance with `up -d lavalink-<instance>`, which injects the config.
3. *Self-host compose* (`docker-compose.production.yml`): add the same top-level config with identical content, and mount it on `lavalink` (line 60), not on `lavalink-plugins`. Use the same comment, with "the release ships only the compose files" instead of the ririko-deploy reason.
4. *Tests* (`scripts/compose-production.test.ts`): add a `describe('Java blocklist for Lavalink (BUG-0055)', …)` that covers both files:
   - parse with `{ merge: true }`;
   - `createHash('sha256').update(configs['java-blocked-certs'].content).digest('hex')` equals the constant;
   - every Lavalink service mounts it at the exact target with that source: `lavalink-production` and `lavalink-staging` in the host file, `lavalink` in the production file;
   - the init services have no `configs`.

   Extend the `ComposeService` interface as needed. Keep the style of the file's other `describe` blocks.
5. *Docs*:
   - docs/deployment.md line 16: "Docker Engine 23 or newer, with the Compose plugin version 2.24.4 or newer. Docker Desktop includes both." Section 8 step 1 (line 416) can stay.
   - In the services table, the `lavalink` row (line 531): add that the compose file replaces Java's list of blocked certificates (`blocked.certs`), because the image's Java has no fix for the eMudhra CA compromise.
   - Add one sentence where section 8.1 describes the host compose, and keep it short.
   - README.md line 42: "Compose 2.24.4 or newer".
   - Do not change `apps/starter/src/run.ts`. The starter is released on its own, on npm.
6. *Next.js*: in apps/web/package.json set `"next": "~16.4.3"`; in the root package.json set `"@next/eslint-plugin-next": "~16.4.3"`. Run `pnpm install` and check that pnpm-lock.yaml resolves `next@16.4.3`.
7. *tinypool*: in `pnpm-workspace.yaml`, add `tinypool: ^2.2.0` to `overrides` (after line 29) with a comment line in the same style as the existing entries: what pulls it in (`@docusaurus/core`, docs build only) and that it is fixed in 2.1.2. Run `pnpm install`, then `pnpm docs:build`. If the docs build fails because of the override, remove it, run `pnpm install` again, and explain in the PROGRESS entry.

**Pitfalls**
- **Byte-identical content.**
  - With `content: |`, keep the indentation the same on every line, so YAML strips exactly the block indent and keeps one final newline.
  - The hex has no `$`, so Compose interpolation leaves it alone. Prettier formats YAML; run `pnpm format:check`.
  - The sha256 test is the proof, so do not weaken it.
- **Running the compose check.** `docker compose config` needs no daemon, and Compose v5.6.1 is installed here. The env files in both compose files must exist, so verify_cmd points them at `/dev/null`. The `${WG_ADDRESS:?}`, `POSTGRES_PASSWORD` and `LAVALINK_PASSWORD` variables are required, so verify_cmd sets them.
- **Never edit the vendor file**, never sort it, and never add or drop fingerprints.
- **Other tests read these files:**
  - `scripts/compose-production.test.ts` already checks the Lavalink host services and the "declares each plugin volume … runs nothing else" case (lines 277-287). Make sure the new top-level `configs` key does not break them.
  - `scripts/export-install-files.test.ts` and `scripts/deploy-host.test.ts` read the compose files too; run them, as `test:coverage` does.
- **`pnpm install` and Node.** It runs on this machine's Node 22.22.0. That is fine, because the root `engines` stays `>=22.0.0`.

**Out of scope**
- Dockerfile, `engines`, the starter package, `ririko-deploy.sh` and `bootstrap.sh`, `docker/lavalink/application.yml`, the Lavalink image tag.
- zod 4, undici, and the dev-only high advisories (vite and vitest, brace-expansion, body-parser, serialize-javascript). They are reported to the maintainer instead.
