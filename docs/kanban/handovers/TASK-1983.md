## GROOMING · 2026-10-21T15:45:00Z · claude-opus-5-5 (coordinator)

**Approach**
1. New folder `packages/services/src/tickets` with `ticket.service.ts`, `transcript.ts` (pure functions: format a header and a message list into text), `messages.ts` (embeds and button rows), `types.ts` and `index.ts`. Export it from `packages/services/src/index.ts`.
2. `TicketService` takes `TicketRepository`, `GuildSettingsRepository` (for the log channel fallback) and an optional `now`. Methods take discord.js objects (`GuildMember`, `TextChannel`, `User`) and return a result object `{ ok: true, ... } | { ok: false, message }`. TASK-1984 turns the result into replies, so the service never replies to interactions itself.
3. Create the channel with `guild.channels.create({ name, type: ChannelType.GuildText, parent: categoryId, permissionOverwrites })`. `AutoVoiceService` in `packages/services/src/autovoice/service.ts` (around line 80) creates channels with overwrites the same way.
4. Transcript: page with `channel.messages.fetch({ limit: 100, before })` until empty or 5,000 messages, then reverse. Attach with `new AttachmentBuilder(Buffer.from(text, 'utf8'), { name })`.
5. Log channel fallback: read `logChannelId` from `GuildSettingsRepository.findById`, as `ModerationLogService` does (`moderation-log.service.ts` line 120).

**Relevant code**
- `packages/services/src/roles/reaction-role.service.ts` `hasPermission`: checking Ririko's own permissions with `guild.members.me`.
- `apps/bot/src/commands/giveaway/components.ts`: reading role ids from a member whose `roles` may be partial. Prefer `member.roles.cache.has(id)` for the staff check.

**Pitfalls**
- Check permissions on the category with `category.permissionsFor(me)`, not only guild-wide. A category overwrite can deny Manage Channels.
- Bots and the opener's later departure: the opener may have left the server before close. Use the stored `opener_id` for the transcript header, not a fetched member.
- Never log message content or transcript text (privacy). Logging ids and counts is fine.
- Use deterministic fixtures in tests. No real timers or the network.

**Out of scope**
- Slash and prefix commands, buttons and modals (TASK-1984). Settings UI (TASK-1985).

**Decisions & gotchas**
- The service returns `{ ok: true, ... } | { ok: false, message }` and never replies to interactions. Success carries `ticket` (and `channel`, `welcomePosted` for `open`; `transcriptChannelId`, `channelDeleted` for `close`). TASK-1984 turns these into replies. Button ids are exported as `TICKET_OPEN_BUTTON_ID` (`ticket:open`), `TICKET_CLAIM_BUTTON_ID`, `TICKET_CLOSE_BUTTON_ID`.
- **Channel number vs. record order.** The channel must exist before `openTicket` (it needs `channel_id`), but the name needs the number. The channel is created with `ticket_settings.next_number` (the number the server hands out next) and renamed with `setName` only when a concurrent open took it. A rename failure is logged and ignored.
- The welcome message pings the opener and the staff roles in `content` (with `allowedMentions` limited to them) and also lists the roles in the embed. If only the welcome post fails, the ticket stays open and `welcomePosted` is false.
- Staff roles that no longer exist in the guild are left out of the overwrites (Discord rejects unknown ids).
- `close` refuses with "stays open" when the destination channel is gone, is not text based, Ririko cannot send/embed/attach there, the history cannot be read or the post fails. A destination is chosen as `transcriptChannelId`, else the guild `logChannelId`; with neither, the ticket is closed and deleted without building a transcript. An in-memory set stops two simultaneous Close presses from posting two transcripts.
- Order in `close`: post transcript, `TicketRepository.close`, `channel.delete`. If the delete fails the ticket is still closed (`channelDeleted: false`). The later channelDelete event finds a closed ticket and does nothing.
- Extra: `remove` refuses to remove Ririko itself (it would lose access to post the transcript). `add` refuses the opener (already in). Subject is capped at 200 characters and the reason at 500 (embed field limits).
- Races not covered: two staff pressing Claim at the same instant can both pass the unclaimed check (the repository `setClaimedBy` has no "only if unclaimed" condition); the last write wins. Judged acceptable; a conditional update would be a repository change.
- Messages are only held in memory while building the file; nothing from them is stored or logged (tests check the console output and repository arguments).
