# BUG-0012 — Daily Energy Replenishment Never Fires: EnergyLifecycleService Is Unwired

**Status**: REVIEW
**Points**: 3
**Parent**: EPIC-015
**Branch**: `feat/STORY-161-configurable-reset-boundary` → `develop/2.0.0` (shipped with STORY-161)

---

## 1. The bug

`EnergyLifecycleService.getOrReconcileUserEnergy` and `replenishUserEnergy` had **no callers**
anywhere in `apps/` or `packages/`. The service was complete and correct but dead code.

Consequence: player energy was never replenished, and `max_energy` never scaled with level. A
player spent their starting 100 energy and could never recover it except through the 3/day potion
ceiling. STORY-161 made the reset boundary correct and configurable, but nothing evaluated it.

Every consumer called `PlayerEnergyRepository.consumeEnergy` directly, bypassing the lifecycle
entirely.

---

## 2. Fix

### 2.1. The service is now the gateway

`EnergyLifecycleService` owns every mutation of the pool. Each method reconciles the reset
boundary **before** acting:

| Method | Used by |
|---|---|
| `spendEnergy` | expeditions, dungeon runs, boss raids, PvP duels |
| `consumePotion` | `ConsumableService`, `InventoryService` |
| `refundEnergy` | floor 1–10 defeat refund |
| `getOrReconcileUserEnergy` | status reads, full-restore sizing |

This is what fixes the user-visible bug: a player who has not been seen since the last boundary
is replenished first, then the debit is evaluated — instead of being refused for insufficient
energy that should already have been restored.

### 2.2. Level resolution moved into the service

`getOrReconcileUserEnergy(userId, playerLevel = 1)` had a **dangerous default**. Capacity is
recomputed on every reconcile, so any caller relying on the default would have overwritten a
level-50 player's `max_energy` of 228 with level 1's 100 — silently shrinking their pool.

The level parameter is now optional with no numeric default, and the service resolves level
itself through an injected `PlayerLevelResolver`. When no resolver and no explicit level are
available the **stored capacity is preserved** rather than recomputed, so the shrink is
impossible by construction.

`createXpLevelResolver` sums the user's XP across every guild via the new
`XpRepository.getUserTotalXp` and runs it through `LevelingService.getLevelProgress`.

**Design note**: energy is a global per-user resource, but `xp_accounts` is keyed
`(user_id, guild_id)`. Account-wide level is therefore derived from *summed* XP across guilds,
not from any single guild's row. `docs/waifu-tcg.md` §12.2 previously implied `xp_accounts.level`
and has been corrected.

### 2.3. Injection is optional everywhere

Each consumer takes `energyLifecycle` as an **optional trailing** constructor argument (or an
options-object key for `DungeonRunner` and `InventoryService`) and falls back to the raw
repository when absent. This kept all 12 existing test call sites compiling unchanged while the
composition root wires the real thing.

`EnergyLifecycleService`'s own constructor accepts either a bare `ResetSchedule` or an options
object, so STORY-161's call sites kept working.

### 2.4. Composition order

`energyLifecycleService` is now built immediately after `levelingService` (it needs the leveling
curve for the resolver) rather than 250 lines later, because `InventoryService` is constructed
before the old location and needs to receive it.

## 6. Gotchas for the next agent

- **`EnergyLifecycleService` is the only supported way to mutate energy.** Calling
  `PlayerEnergyRepository.consumeEnergy` directly bypasses reconciliation and reintroduces this
  exact bug. The repository method is still public because the optional-injection fallback needs
  it; treat it as internal.
- **Never pass a literal level to `getOrReconcileUserEnergy` unless it is the player's real
  level.** Capacity is recomputed from it on every call.
- **Tests construct services without the lifecycle**, so they exercise the raw-repository
  fallback path. A test that needs reconciliation must pass the lifecycle explicitly.
- **The level resolver runs a `SUM` over `xp_accounts` per reconcile.** It is indexed on
  `user_id` and only fires on energy operations, but it is a query per spend — if energy
  operations ever become hot, cache it.
- **BUG-0013** tracks the remaining dead field: `bonus_energy` is summed into the effective cap
  in four places but only ever written as 0.
