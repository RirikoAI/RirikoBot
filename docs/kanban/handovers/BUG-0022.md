# Handover Note: BUG-0022 Reminder Times Were Read in the Host's Time Zone Instead of the User's

- **Ticket Type & Points**: Bug | 2 pts (parent `STORY-123`, `EPIC-012`)
- **Author / Agent**: Claude Code (Opus 5.5)
- **Status**: DONE (fixed on `feat/STORY-123-ci-pipeline`)
- **Timestamp**: 2026-09-26

## 1. Summary of Work Accomplished
**Symptom:** the first CircleCI run (UTC host) failed four reminder tests. `tomorrow 9am` for a Kuala Lumpur user gave `09:00Z` instead of `01:00Z`. The tests passed on the maintainer's machine because its zone is also Asia/Kuala_Lumpur.

**Root cause:** `parseReminderTime` passed the IANA zone name to chrono-node as `{ timezone: 'Asia/Kuala_Lumpur' }`. chrono-node 2.10 reads `timezone` only as an abbreviation (`JST`, `CET`) or offset minutes. An unknown name maps to `null`, and chrono then uses the host's zone. On a UTC server every wall-clock reminder ("tomorrow 9am", "2026-12-25 08:00") would fire hours off for any user not in UTC. Relative reminders ("in 2 hours", "30m") were unaffected.

**Fix (`packages/services/src/reminders/reminder-time.ts`):**
- Compute the zone's UTC offset at `now` with the existing `zoneOffsetMs` helper and pass it to chrono as minutes.
- If the text has no explicit zone and the target date has a different offset (a DST change in between), parse again with the target date's offset.
- An invalid zone falls back to UTC, as `formatLocalTime` already does.

## 2. Verification
- New tests: DST crossing in Europe/London (BST now, GMT at Christmas) and an explicit `UTC` in the text overriding the user zone.
- `vitest run packages/services/src/reminders apps/bot/src/commands` passes with host `TZ=UTC`, `TZ=America/Los_Angeles` and the default Asia/Kuala_Lumpur.
- CircleCI runs in UTC, so the gate now covers host-zone independence.

## 3. Gotchas
- Reminders already stored with a wrong `trigger_at` keep it. The bot has not been hosted on a non-UTC+8 machine, so no production data is affected.
