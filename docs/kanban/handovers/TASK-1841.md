## GROOMING · 2026-10-09T16:02:24Z · claude-opus-5-5 (coordinator)

**Approach**
1. **Schema.** Add `invitedVia` (`invited_via`, nullable; varchar(16) in PostgreSQL, text in SQLite) to `guilds` in both identity schemas; regenerate the DDL. Extend `ensureGuildRegistrySchema` so it checks and adds each column (`invited_by_id`, `invited_via`) on its own. TASK-1831 is not released, but the maintainer's local database and dev server already ran it, so a database with `invited_by_id` and without `invited_via` must upgrade cleanly. Values: `oauth`, `audit_log`, `integration`; export a type for them.
2. **Repository** (`guild.repository.ts`):
   - `setInviterIfMissing(id, userId, via)` stores the source too.
   - New `recordInvite(guild: GuildRegistration, inviterId)`: upsert as active (same CASE rules for `joined_at`), and set `invited_by_id = inviterId`, `invited_via = 'oauth'` unconditionally, because the invite flow is authoritative.
   - The bot's `upsert` keeps both inviter columns for an active row and clears both when a left server is rejoined (as it does for `invited_by_id` today).
3. **Bot fallback** (`guild-registry.listener.ts`): `findBotInviter` returns `{ userId, via } | null`. Audit log first (`audit_log`); if it gives nothing or is denied, `guild.fetchIntegrations()` and take the integration whose `application?.id` is the bot's ID, using its `user?.id` (`integration`). Treat 50001 and 50013 as silent, as today. Keep the ready backfill one guild at a time.
4. **OAuth client.** Discord's invite needs its own redirect URI. Either give `DiscordOAuthClient` an invite variant or build a second instance in `services.ts` with `redirectUri: ${DASHBOARD_URL}/api/invite/callback`. Add:
   - an authorization URL with `scope=bot applications.commands identify`, `permissions=BOT_INVITE_PERMISSIONS`, `response_type=code`, PKCE, `state`, and, when given, `guild_id` plus `disable_guild_select=true`. No `prompt=none` (the bot scope always shows the consent screen).
   - token revocation (`POST /oauth2/token/revoke` with client credentials) to drop the user token after use.
   - the token response's `guild` object (`id`, `name`, `icon`, `owner_id`), which Discord includes for the `bot` scope; `RESTPostOAuth2AccessTokenResult` may not type it, so parse it defensively.
5. **Routes** (mirror `app/api/auth/login/route.ts` and `callback/route.ts`):
   - `app/api/invite/route.ts` `GET`: `limitAuthRequest`; validate `guild` as a snowflake or ignore it; state + PKCE sealed in a new short-lived cookie (its own name, not `OAUTH_COOKIE`, so an invite never clobbers a pending sign-in); redirect to Discord. No session needed.
   - `app/api/invite/callback/route.ts` `GET`: `limitAuthRequest`; `error` param or bad state → redirect with an error; exchange the code with the verifier; `getCurrentUser`; `users.upsert` like the login callback; `guildRegistry.recordInvite` from the token's guild with `joinedAt` now and the icon URL built like the bot's; revoke the token in `after()`; clear the cookie; redirect to `/servers?invited=<guildId>` (the page may ignore the param). Never create a session.
   - Add both to `AUTH_ROUTE_ALLOWLIST` (`apps/web/src/lib/server/testing/authorization-coverage.ts`) with `['GET']`. Add invite error codes next to the login errors if the page shows them.
6. **Servers page.** "Invite Ririko" links to `/api/invite?guild=<id>`. Remove `botInviteUrl` if nothing else uses it (update `guild-access.test.ts`).
7. **Docs.** `docs/dashboard.md`: the invite flow and the three Developer Portal steps in order (STORY-184 note). `docs/database.md`: `invited_via`.

**Relevant code** (from CodeGraph during grooming)
- `apps/web/src/lib/server/auth/discord-oauth.ts` `DiscordOAuthClient`: `authorizationUrl`, `exchangeCode`, `requestToken` (Basic auth, never echoes error bodies).
- `apps/web/src/app/api/auth/login/route.ts` and `callback/route.ts`: sealed state and PKCE cookie, `openPendingLogin`, `users.upsert`, failure redirects.
- `apps/web/src/lib/server/services.ts:167`: the login `redirectUri`.
- `apps/web/src/lib/server/guilds/permissions.ts:24` `botInviteUrl`, `BOT_INVITE_PERMISSIONS`.
- `apps/web/src/app/servers/page.tsx:52`: the invite button.
- `apps/bot/src/listeners/guild-registry.listener.ts` `findBotInviter`.
- `packages/database/src/repositories/guild.repository.ts` and `migrations/guild-registry.ts` (TASK-1831).

**Pitfalls**
- With Requires OAuth2 Code Grant on, the bot joins only after the code exchange; a callback failure means no join. Report failures clearly and never leave the user on a blank page.
- The state cookie must be `SameSite=Lax` (Discord redirects back with a top-level GET), like the login cookie.
- Never log tokens or the token response body.
- `recordInvite` may run before or after the bot's `GuildCreate`; both orders must end with the oauth inviter kept (test both).
- A user who authorizes without the bot scope would produce a token response with no guild: treat as an error, record nothing.
- Use fake snowflakes and `example.com` URLs in tests.

**Out of scope**
- Changing the Developer Portal settings (maintainer).
- The Servers tab display (TASK-1842).
- Signing the inviter in to the dashboard.

**Decisions & gotchas**
- `@ririko/database` resolves to `dist` in the web tests: run `pnpm build` (or `pnpm -F @ririko/database build`) before the web tests, or `recordInvite` is "not a function".
- `recordInvite` is `upsert` then `update` (two statements). Either order against the bot's `GuildCreate` ends with the oauth inviter kept (tested: bot first, oauth first, left and rejoined).
- Callback redirects: errors go to `/?error=<code>` (works without a session; `/servers` would bounce a visitor through sign-in and lose the notice). Success goes to `/dashboard/<id>` when `getSession()` finds a session (a read failure counts as no session), else `/servers?invited=<id>`.
- The token is revoked in `after()` right after the exchange, so it is also revoked when the response names no server, the scope is missing or the profile read fails. A revocation failure is logged without the token and never fails the invite.
- A response without a `guild` (or one missing `id`, `name` or `owner_id`) gives `invite_no_server`; a token without `identify`/`bot`/`applications.commands` gives `invite_failed` and records nothing.
- `Requires OAuth2 Code Grant` and the Developer Portal steps stay manual (documented in `docs/dashboard.md` 2.0).
- Several files in this checkout have CRLF working copies with LF in the index; my scripted edits normalised some to LF. Prettier (`endOfLine: auto`) passes either way.
