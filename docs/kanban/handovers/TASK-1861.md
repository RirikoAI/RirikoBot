## GROOMING · 2026-10-09T18:41:41Z · claude-opus-5-5 (coordinator)

**Approach**
- In `apply_release` (`deploy/host/bin/ririko-deploy.sh:376`), after the pull and before `up -d`:
  - Run `compose "$version" run --rm --no-deps bot ririko db:migrate`.
  - `--no-deps` stops compose from starting the new web or Lavalink containers. Postgres is already running, because it is the same service across releases. Check this in `compose()` and the compose file: the network and volume names must match between releases.
- Map the CLI's exit codes:
  - 1 is a migration failure: deploy exit 6.
  - 2 is a downgrade-guard refusal: also exit 6, with its own message.
- Return before `up -d`, so `cmd_deploy` does not start the rollback path. Nothing was stopped.
- `status`: add the migration status line from the running release's bot container (`compose exec -T bot ririko db:migrate --status`).

## FLAG · 2026-10-10T09:25:00Z · from TASK-1854 · claude-medium (claude-sonnet-5-5)

**Finding**: `ririko db:migrate` exists (`apps/cli/src/commands/db-migrate.ts`) with the behaviour this ticket's grooming assumes.
**Impact on this ticket**:
- Exit codes: 0 done or nothing to do, 1 failure (including a refused adoption), 2 refused by the downgrade guard (the database holds a contract migration this release does not know). `--status` always exits 0 and prints `Latest`, `Pending`, `Unknown` and `Adopted` lines; `--dry-run` prints the plan and changes nothing. Both flags together are a usage error (exit 1 through the CLI's error handler).
- The command reads `DATABASE_DIALECT` and `DATABASE_URL` from its environment, as the bot does. It prints only host, port and database of a PostgreSQL URL, and scrubs the URL and password from error text.
- The bot also migrates at startup unless `DB_AUTO_MIGRATE=false`. When the deploy runs `db:migrate` first, the bot then finds nothing to do. With `DB_AUTO_MIGRATE=false` set on the host, the bot refuses to start on pending migrations, so the deploy step is what keeps it starting.
- The dashboard answers `/ready` with 503 (and logs the pending migrations) while the database is behind, so `wait_ready` on the web service is not satisfied before the migration has run.
