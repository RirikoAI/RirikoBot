## GROOMING · 2026-10-09T18:41:41Z · claude-opus-5-5 (coordinator)

**Approach**
- In `apply_release` (`deploy/host/bin/ririko-deploy.sh:376`), after the pull and before `up -d`:
  - Run `compose "$version" run --rm --no-deps bot ririko db:migrate`.
  - `--no-deps` stops compose from starting the new web or Lavalink containers. Postgres is already running, because it is the same service across releases. Check this in `compose()` and the compose file: the network and volume names must match between releases.
- Map the CLI's exit codes:
  - 1 is a migration failure: deploy exit 6.
  - 2 is a downgrade-guard refusal: also exit 6, with its own message.
- Return before `up -d`, so `cmd_deploy` does not start the rollback path. Nothing was stopped.
- `status`: add the migration status line from the running release's bot container (`compose exec -T bot ririko db:migrate --status`).

**Relevant code** (from CodeGraph during grooming)
- `deploy/host/bin/ririko-deploy.sh`:
  - `predeploy_dump` (line 625): runs before `apply_release` when a release is running.
  - `apply_release` (line 376).
  - The exit codes table in the header (lines 31–35).
  - `diagnose` (line 400).
- `scripts/deploy-host.test.ts`: runs the script against a fake `docker` and `flock` (see how existing tests stub `compose`). Extend it in the same style.
- `.circleci/config.yml:80` `ssh-host`: maps the host's exit codes to messages (line 133). Add 6.

**Pitfalls**
- Running `run --rm` while the old bot is up is intended (expand rule). Do not stop the old release first.
- On the first deploy to a host with no release, there is no pre-deploy dump. The migration then creates the schema from `0000`. Keep that path working.
- `shellcheck -x` runs in CI on `deploy/host`.

**Out of scope**
- Automatic database restore.

## FLAG · 2026-10-10T09:25:00Z · from TASK-1854 · claude-medium (claude-sonnet-5-5)

**Finding**: `ririko db:migrate` exists (`apps/cli/src/commands/db-migrate.ts`) with the behaviour this ticket's grooming assumes.
**Impact on this ticket**:
- Exit codes: 0 done or nothing to do, 1 failure (including a refused adoption), 2 refused by the downgrade guard (the database holds a contract migration this release does not know). `--status` always exits 0 and prints `Latest`, `Pending`, `Unknown` and `Adopted` lines; `--dry-run` prints the plan and changes nothing. Both flags together are a usage error (exit 1 through the CLI's error handler).
- The command reads `DATABASE_DIALECT` and `DATABASE_URL` from its environment, as the bot does. It prints only host, port and database of a PostgreSQL URL, and scrubs the URL and password from error text.
- The bot also migrates at startup unless `DB_AUTO_MIGRATE=false`. When the deploy runs `db:migrate` first, the bot then finds nothing to do. With `DB_AUTO_MIGRATE=false` set on the host, the bot refuses to start on pending migrations, so the deploy step is what keeps it starting.
- The dashboard answers `/ready` with 503 (and logs the pending migrations) while the database is behind, so `wait_ready` on the web service is not satisfied before the migration has run.

**Decisions & gotchas**
- The migration command is `compose <version> run --rm --no-deps -T bot ririko db:migrate`: the acceptance text plus `-T` (no TTY, because the deploy runs through a forced SSH command) and stdin from `/dev/null`. Its output is captured, printed line by line with a `db:migrate:` prefix (stdout and deploy.log), and its last line goes into the exit 6 message.
- First deploy and "postgres is not running": `--no-deps` does not start postgres, and on a first deploy nothing runs it. `migrate_database` checks `ps --status running --services` of the new release and, only when postgres is absent, runs `up -d --no-build --wait --wait-timeout $READY_TIMEOUT postgres` first. When postgres already runs (the normal case) it is not touched. This is one more docker call than the grooming described, and the first-deploy test now expects it.
- `DB_AUTO_MIGRATE` is `${DB_AUTO_MIGRATE:-false}` and not a fixed `'false'`: the acceptance asks for false on the bot, and this keeps a hand-run `docker compose up` possible by setting it to true in the env file (ADR-015 says self-hosters keep migrate-on-start). Say if you want it fixed; the compose test does not assert it yet.
- The Lavalink host never reaches `apply_release` (it has `apply_lavalink`), so the "skipped for a Lavalink host" criterion holds by construction; the Lavalink test asserts only the two docker calls (pull, up) happen.
- Rollback never migrates: the old image cannot migrate the database back, and the expand rule lets it run on the new schema. A same-version redeploy still runs the (idempotent) migration.
- A refused downgrade guard (CLI exit 2) and a failure (exit 1, or any other nonzero code from compose or docker) both exit 6, with different text. Nothing is rolled back or diagnosed on exit 6, since nothing of the new release was started.
- `ririko-deploy-ssh` only passes the exit code through (it has no message table), so only the CircleCI `ssh-host` step needed the exit 6 mapping.

**New CodeGraph queries**
- None that helped: CodeGraph does not index bash, so the script was read by line range. `deploy-host.test.ts` is indexed only partly (fakeDocker and the harness are in the first 400 lines).
