## GROOMING · 2026-10-09T18:41:41Z · claude-opus-5-5 (coordinator)

**Approach**
- Add `packages/database/src/migrations/runner.ts` with `migrateDatabase` and `migrationStatus`. Accept the migration list as a parameter, defaulting to the embedded module for the client's dialect, so tests can inject their own list.
- PostgreSQL:
  - Take one client with `client.raw.connect()`.
  - Call `SELECT pg_advisory_lock(1706, 1)`. The existing upgrades use 1701–1705, so continue the series.
  - Run each migration as `BEGIN`, its statements, the tracking insert, `COMMIT`.
  - Call `pg_advisory_unlock` and `release()` in `finally`.
  - Pass the statements as simple-query text, the way `ensurePostgresSchema` does.
- SQLite:
  - Use `client.raw` (better-sqlite3). Run each migration in a `db.transaction(...).immediate()`, or as `BEGIN IMMEDIATE` and `COMMIT`.
  - The backup: `VACUUM INTO '<path>'`, with the path escaped as an SQL string literal. Find the database path from `client.raw.name`.
- Tracking row: `id`, `checksum`, `contract` (boolean or integer), `applied_at`, and `adopted` (TASK-1853 sets it).

**Relevant code** (from CodeGraph during grooming)
- `packages/database/src/migrations/postgres-schema.ts`: the connect, `BEGIN`, lock, `COMMIT`/`ROLLBACK`, `release` pattern to copy.
- `packages/database/src/migrations/text-ids.ts:50`: the same pattern with several statements.
- `packages/database/src/testing/dialects.ts`: helpers that run a test on both dialects. Use them.

**Pitfalls**
- A statement that fails in the middle of a migration must roll back that whole migration and its tracking row. Earlier migrations stay applied.
- SQLite `ALTER TABLE` inside a transaction is fine, but `VACUUM INTO` cannot run inside a transaction. Take the backup before the first `BEGIN`.
- Timestamps: the codebase stores milliseconds in some tables and seconds in others. Store `applied_at` with each dialect's usual type: `timestamp` on PostgreSQL, integer milliseconds on SQLite. Document the choice.

**Out of scope**
- Adoption of databases without the tracking table (TASK-1853). Until then, the runner refuses a database that has application tables but no tracking table, with "adoption not available".

**Decisions & gotchas**
- Tracking table: `id text PK`, `checksum text`, `contract` (boolean on PostgreSQL, integer 0/1 on SQLite, default false), `adopted` (same, default false, for TASK-1853), `applied_at` (`timestamptz` on PostgreSQL, integer milliseconds on SQLite). The table is created lazily, only after all checks pass and a non-dry run has pending work. It is created in `current_schema()`.
- `migrations` is an option (default: the embedded list of the client's dialect), so tests inject their own. The list is sorted by id; a duplicate id throws.
- PostgreSQL: `client.raw.connect()` gives one connection that takes `pg_advisory_lock(1706, 1)` before state is read, runs `BEGIN`, statements, tracking insert, `COMMIT` per migration, and in `finally` calls `pg_advisory_unlock` and `release()`. If unlock fails, the connection is destroyed (`release(true)`), which ends the session lock. A dry run takes no lock. The tests check `pg_locks` after success, failure, checksum error and dry run.
- SQLite: each migration runs in `withTransaction` (BEGIN IMMEDIATE behind the connection mutex) and re-checks inside the transaction that the id is not recorded yet, so a second process (bot plus CLI on one file) cannot apply it twice; such an id lands in `alreadyApplied`.
- SQLite backup: `VACUUM INTO <db dir>/backups/pre-migrate-<YYYYMMDDTHHMMSSmmmZ>.sqlite`, taken before the tracking table is created and before the first BEGIN, only when something is pending and the database already has tables other than the tracking table. Not for `:memory:`, empty databases, dry runs, or when a check stopped the run. Pruning keeps the newest 5 files matching `pre-migrate-*.sqlite` by name; other files in `backups/` are untouched.
- Order of checks (all before any change): adoption refusal, checksum mismatch, unknown contract migration. An unknown ordinary migration logs one warning and the run continues. The same checks run on a dry run.
- A database with application tables but no tracking table throws `DatabaseError` "adoption not available" (also in a dry run). `migrationStatus` does not throw on it: it reports everything pending and `adopted: false`. TASK-1853 replaces the refusal.
- `migrationStatus.latest` is the newest id the image knows (not the newest applied); `null` for an empty list.
- A failing migration throws `DatabaseError("Migration <id> failed and was rolled back: ...")` with the cause; earlier migrations stay applied.

**Notes for later tickets**
- TASK-1853: the tracking table is not part of `PG_SCHEMA_DDL` or `SQLITE_SCHEMA_DDL`; parity checks that compare a migrated database with the DDL must ignore `ririko_schema_migrations`. For adoption, insert rows with `adopted = true` and the embedded checksum.
- TASK-1854: `migrateDatabase` expects an empty database or one with the tracking table. Test helpers that build a database from the full DDL (`describeDialects`, `autoMigrate`) have tables but no tracking table, so they cannot call the runner until adoption exists.
