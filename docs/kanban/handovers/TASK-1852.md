## GROOMING · 2026-10-09T18:41:41Z · claude-opus-5-5 (coordinator)

**Approach**
- Add `packages/database/src/migrations/runner.ts` with `migrateDatabase` and `migrationStatus`. Accept the migration list as a parameter, defaulting to the embedded module for the client's dialect, so tests can inject their own list.
- PostgreSQL:
  - Take one client with `client.raw.connect()`.
  - Call `SELECT pg_advisory_lock(1706, 1)`. The existing upgrades use 1701–1705, so continue the series.
  - Run each migration as `BEGIN`, its statements, the tracking insert, `COMMIT`.
  - Call `pg_advisory_unlock` and `release()` in `finally`.
  - Pass the statements as simple-query text, the way `ensurePostgresSchema` does.
- SQLite:
  - Use `client.raw` (better-sqlite3). Run each migration in a `db.transaction(...).immediate()`, or as `BEGIN IMMEDIATE` and `COMMIT`.
  - The backup: `VACUUM INTO '<path>'`, with the path escaped as an SQL string literal. Find the database path from `client.raw.name`.
- Tracking row: `id`, `checksum`, `contract` (boolean or integer), `applied_at`, and `adopted` (TASK-1853 sets it).

**Relevant code** (from CodeGraph during grooming)
- `packages/database/src/migrations/postgres-schema.ts`: the connect, `BEGIN`, lock, `COMMIT`/`ROLLBACK`, `release` pattern to copy.
- `packages/database/src/migrations/text-ids.ts:50`: the same pattern with several statements.
- `packages/database/src/testing/dialects.ts`: helpers that run a test on both dialects. Use them.

**Pitfalls**
- A statement that fails in the middle of a migration must roll back that whole migration and its tracking row. Earlier migrations stay applied.
- SQLite `ALTER TABLE` inside a transaction is fine, but `VACUUM INTO` cannot run inside a transaction. Take the backup before the first `BEGIN`.
- Timestamps: the codebase stores milliseconds in some tables and seconds in others. Store `applied_at` with each dialect's usual type: `timestamp` on PostgreSQL, integer milliseconds on SQLite. Document the choice.

**Out of scope**
- Adoption of databases without the tracking table (TASK-1853). Until then, the runner refuses a database that has application tables but no tracking table, with "adoption not available".
