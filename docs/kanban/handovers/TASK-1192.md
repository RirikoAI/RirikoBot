## GROOMING · 2026-10-04T09:10:00Z · Claude Code (Opus 5.5)

**Approach**
1. **`apps/web/src/app/api/auth/dbsc/register/route.ts` `POST`.**
   - Call `limitAuthRequest` first.
   - Read `SESSION_COOKIE` and the proof from the `Secure-Session-Response` request header. Per spec, the body may carry it too; check the spec and accept both if needed.
   - Call `sessions.bindDevice`.
   - On success: 200 with `sessionInstructions(sid)` JSON. Set the rotated `SESSION_COOKIE` (max age to `expiresAt`) and `BOUND_COOKIE` with `setCookie`.
   - On failure: 400, or 401 when there is no session.
2. **`apps/web/src/app/api/auth/dbsc/refresh/route.ts` `POST`.**
   - Call `limitAuthRequest` first.
   - Read `Sec-Secure-Session-Id` (a structured-field string; strip the quotes) and the optional `Secure-Session-Response`.
   - Map the result:
     - `challenge`: 403 with `Secure-Session-Challenge`.
     - `refreshed`: 200 with `BOUND_COOKIE` set (and optionally the instructions JSON).
     - `unknown`: 404.
   - No same-origin check is needed. The browser sends the request itself, and the proof is the authentication. Keep rate limiting.
3. **Callback.** After `sessions.create` in `apps/web/src/app/api/auth/callback/route.ts`, set `Secure-Session-Registration` with `registrationHeader(sessions.registrationChallenge(session))` on the redirect.
   - Confirm in the spec or the Chrome docs that the header is processed on a 303 redirect response.
   - If it is not, send it from the first authenticated page response instead, and record why in the PROGRESS entry.
4. **`getSession`** (`apps/web/src/lib/server/auth/session.ts`): pass `cookies().get(BOUND_COOKIE)?.value` to `sessions.resolve`. Other direct `resolve` callers: check them with CodeGraph.
5. **Logout:** also `clearCookie(response, BOUND_COOKIE)`.
6. **Coverage test:** add both routes to the auth-route allowlist in `apps/web/src/lib/server/authorization-coverage.test.ts` (and the helper in `lib/server/testing/authorization-coverage.ts` if the list lives there).
7. **Sessions page** (`apps/web/src/app/account/sessions/page.tsx`): a small "Device-bound" badge when `deviceBound`, styled like the existing current-session marker.
8. **Docs.**
   - ADR-013: decision 4 and revision item 4 say DBSC is implemented in STORY-119 (Chrome 146+ on Windows). Add a short "Revision 2026-10-04" with the design: sealed challenges, a 10-minute bound cookie, no downgrade, rotation at binding.
   - `docs/dashboard.md`: the threat table row and the story table row (STORY-119, 8 pts).
9. **Route tests** next to the routes, following `callback/route.test.ts` and `logout/route.test.ts`. Use keys generated in the test. Cover:
   - Register succeeds, and its cookies carry `__Host-` attributes.
   - Refresh without a proof gets 403 with the challenge header. A signed refresh gets 200. A bad proof gets 403.
   - After logout, refresh gets 404.
   - The callback sets the registration header.

**Relevant code** (from CodeGraph during grooming)
- `apps/web/src/app/api/auth/callback/route.ts:16` `GET`, `apps/web/src/app/api/auth/logout/route.ts:8` `POST`.

- TASK-1191's `dbsc.ts` and the `SessionService.bindDevice / refreshBinding / registrationChallenge` methods: read its PROGRESS entry for the final names.

**Pitfalls**
- `getSession` is wrapped in React `cache`. Keep it that way.
- The CSP proxy matcher excludes `/api`, so the new routes need no nonce.
- Header values are RFC 8941 structured fields. Quote strings and escape `"` and `\`. Sealed values are base64url with dots, so quoting is enough.

**Out of scope**
- Changing passkey, step-up or sign-in gate behavior.

**FLAG addressed.** `verify_cmd` runs from the repository root; it passes as written.

**Decisions and gotchas**
- **Redirects.** The W3C draft processes `Secure-Session-Registration` on any response, redirects included, so the header is on the callback's 303. No fallback to a later page was needed.
- **Register.** The proof comes from the `Secure-Session-Response` request header only (the draft sends it there; no body). Status codes: 401 without a session cookie or a vanished session, 400 for a missing or refused proof or an already bound session. Rotated session cookie (max age to `expiresAt`) and bound cookie (600 s) are set. Responses are `Cache-Control: no-store`.
- **Refresh.** `Sec-Secure-Session-Id` must be a quoted structured string matching base64url (else 400); results map to 403 (+ `Secure-Session-Challenge`), 200 (+ bound cookie), 404. No same-origin check, rate limit kept.
- **Passkey re-registration NOT done (as the GROOMING addition allowed).** `finishPasskeyCheck` is a Server Action; Next gives Server Actions no API to set a response header (`headers()` is read-only), so it cannot send `Secure-Session-Registration`. I invented no workaround. Consequence: a registration Chrome posts after a passkey check rotated the row ID fails with 400; Chrome registers right after the callback response, so this is unlikely. Recorded in ADR-013.
- **`ActiveSession.deviceBound` not added.** Its only stated purpose was the re-registration decision above. The sessions page uses `SessionSummary.deviceBound`, which TASK-1191 already provides.
- CRLF files (callback, logout, session.ts, docs) kept their line endings.
