## GROOMING · 2026-10-23T15:52:42Z · claude-opus-5-5 (coordinator)

**Found** on 2026-10-22: the bot started before Lavalink, logged "Unable to connect after 5 attempts" and kept music off until a restart.

**Cause**: lavalink-client 2.11.0 node defaults are `retryAmount: 5` and `retryDelay: 1e4` (dist/index.js line 1701); after that it emits the error and stops reconnecting. `LavalinkService` (packages/music/src/lavalink/lavalink-service.ts) only logs node `error` and `disconnect`.

**Approach**: in `wireManagerEvents`, on a node `disconnect` or the give-up error, schedule `node.connect()` with backoff unless already connected or destroyed. Clear the timer on `connect`. Add a `destroy()`/stop path if none exists, and call it where the service shuts down.

**Pitfalls**: avoid two loops racing the library's own retries. Start the outer loop only after the library gives up (the error message) or on a disconnect with no reconnect pending.

**Files changed**
- `packages/music/src/lavalink/lavalink-service.ts`: keeps the node options in `nodeOptions`; a `destroy` node event with reason `NodeReconnectFail` (what lavalink-client emits after "Unable to connect after 5 attempts", right after it deletes the node) schedules a background reconnect with backoff 30 s doubling to 300 s; the attempt calls `nodeManager.createNode(nodeOptions)` (recreates the deleted node) then `connect()`, logging one line per attempt. A `connect` event resets the backoff and clears the timer. New public `destroy()` stops the loop for good. The timer is `unref`'d.

**Decisions & gotchas**
- The library does not just stop retrying: `executeReconnect` emits `error` then `destroy("NodeReconnectFail")`, which deletes the node from `nodeManager.nodes`. `play()` then throws "No Lavalink node available", so the loop recreates the node with `createNode` rather than calling `connect()` on the dead one. The library's own 5-retry cycle runs again after each of our attempts; when it gives up again the next, longer backoff is scheduled, so the two loops never race (we schedule only from the give-up event).
- `destroy()` only clears the timer and blocks new schedules. It is not wired into `MusicPlayerService` or `apps/bot/src/main.ts`: there is no music shutdown path today, and `handleShutdown` ends with `process.exit(0)`, with the timer `unref`'d. Wiring a `MusicPlayerService` shutdown hook is left to the coordinator if wanted.
