## 3. Roadblocks, Gotchas & Decisions Made

- **No bug found in TASK-1601's `CraftingService`** — read the full service and recipe table before wiring it in, and nothing needed changing. Its constructor signature, `listRecipes`/`craft` contracts, and `DatabaseError` messages all matched the handover note exactly.
- **Category select is a dropdown, not buttons.** The task described "category select (by equipment slot + Potions)" — 7 options. `shop-menu.ts`'s category picker uses buttons, but Discord action rows cap at 5 buttons; 7 categories would need two rows and asymmetric styling. A `StringSelectMenuBuilder` (same pattern as `gear:slot` in `gear-menu.ts`) handles all 7 cleanly in one row and matches the literal word "select" in the task description.
- **Menu craft is always quantity 1.** `CraftingService` caps equipment/accessory recipes at 1 anyway; only potions could batch. The task's menu spec didn't call for a quantity picker inside the menu (unlike `shop-menu.ts`'s `Buy 1x`/`Buy 5x` split), so the menu always crafts 1 and batching lives only in the direct `/item action:craft recipe:... quantity:...` path — keeps the menu's button row identical in shape to `gear-menu.ts`'s (one primary action + Close) instead of inventing a new quantity-stepper UI for a case (potion batching) that's already served by the direct command.
- **`resolveRecipeCode` is a deliberate small UX addition** beyond the literal spec: since autocomplete isn't available in this framework, typing an exact `CRAFT_...` code from memory is unfriendly, so it also accepts the bare output item code (with or without the `CRAFT_` prefix), case-insensitively. This only affects the direct-craft path in `item.command.ts`; the service's own `craft()` still only accepts an exact recipe code, so no behavior changed in `@ririko/services`.
- Verified the WIP invariant before starting: `active_in_progress_ticket` was `null` and no ticket was `IN_PROGRESS` on the board (only `STORY-161`/`BUG-0012` were `REVIEW` from a prior session), so TASK-1602 could move straight to `IN_PROGRESS` without an interruption/pause conversation.
