## GROOMING · 2026-10-22T06:10:00Z · claude-opus-5-5 (coordinator)

**Approach**
1. `apps/bot/src/listeners/starboard.listener.ts` exports `registerStarboardListener(client, services)`. Use the same `guarded` pattern as `event-log.listener.ts`.
2. For each reaction event:
   - Take `reaction.message`.
   - If it is partial, `await message.fetch().catch(() => null)`, and stop if that returns null.
   - Skip when there is no guildId.
   - Call `starboardService.reactionChanged(message)`.
   - `messageReactionRemoveAll` passes `(message, reactions)`, and `messageReactionRemoveEmoji` passes `(reaction)`.
3. On `messageDelete` call `messageDeleted(guildId, message.id)`. On `messageDeleteBulk` call it for each key.
4. Wiring in `services.ts`: build the repository and service, invalidate on `starboard` config changes, and add the case to guild-config-sync.test.ts. Register the listener in `main.ts`.

Leave `reaction.listener.ts` and `event-log.listener.ts` unchanged. Several listeners on the same event is fine.

- `reaction.listener.ts` and `event-log.listener.ts` are untouched.

**Acceptance**
1. `registerStarboardListener(client, { starboardService })` subscribes to `messageReactionAdd`, `messageReactionRemove`, `messageReactionRemoveAll`, `messageReactionRemoveEmoji`, `messageDelete` and `messageDeleteBulk`, each through its own `guarded` wrapper (try/catch, logs `[Starboard] Failed to handle <event>:`).
   - The four reaction events share one helper: skip when the message has no `guildId` (DM, before any fetch); if the message is partial, `await message.fetch().catch(() => null)` and stop on null or when the fetched message has no `guildId`; then `reactionChanged(fullMessage)`. RemoveAll takes the message directly, the others take `reaction.message`.
   - `messageDelete` calls `messageDeleted(guildId, message.id)` and skips DMs. `messageDeleteBulk` skips DM-based channels and calls `messageDeleted(channel.guildId, id)` once per key, one after the other.
2. The reaction role and event log listeners are unchanged (`git diff` shows no edit to either file).
3. `services.ts` builds `new StarboardService({ repo: new StarboardRepository(db), guilds })`, and a `guild:configChanged` handler calls `starboardService.invalidate(guildId)` for module `starboard`. `main.ts` registers the listener. `guild-config-sync.test.ts` has: cache drop on a `starboard` bump (the service looks up the starboard channel only after the tick), cache kept when `general` changes, and the guilds lookup going through a supplied client.
4. Tests: `starboard.listener.test.ts` covers, for each of the four reaction events, a cached message, a partial fetch, a failed fetch, a DM skipped without fetching, a fetched message that is a DM, and a service error logged; for `messageDelete` the IDs, a partial message, DM skip and error; for `messageDeleteBulk` one call per message, DM channel skip and error; and one handler failing without stopping the next event.

**Client wiring choice.** `createBotServices(db, discordClient?)` takes the client as an optional argument (main.ts passes `bot.client`; many tests pass none). So the client exists when services are built in production but not in tests. I did not build the service in main.ts, to keep every service in one place and `BotServices.starboardService` non-null for the listener and tests. I pass a lazy getter instead: `guilds: { cache: { get: (id) => discordClient?.guilds.cache.get(id) } }`. With no client no server is found, so `messageDeleted` does nothing. It is the same optional-client pattern as the other services in the file, with no new null type on `BotServices`.
