## GROOMING · 2026-10-04T18:58:43Z · Claude Code (Opus 5.5)

**Approach**
1. Pin `ghcr.io/lavalink-devs/lavalink` to the newest 4.x release (check GitHub releases) in `docker-compose.production.yml`.
2. Write `docker-compose.remote-lavalink.yml`:
   ```yaml
   services:
     lavalink:
       profiles: [bundled-lavalink]
     bot:
       depends_on: !override
         postgres:
           condition: service_healthy
       environment:
         LAVALINK_HOST: ${LAVALINK_HOST:?set LAVALINK_HOST}
         LAVALINK_PORT: ${LAVALINK_PORT:-2333}
   ```
3. Write `deploy/lavalink/docker-compose.yml` and `deploy/lavalink/lavalink.env.example`.
4. Extend `scripts/compose-production.test.ts` (TASK-1761). The `yaml` parser does not know Compose's `!override` tag: pass a `customTags` entry that keeps the mapping, or assert the merged result from a stored `docker compose config` run instead.

**Pitfalls**
- `!override` and `!reset` need Docker Compose 2.24.4 or newer. The bootstrap installs the current plugin; say so in the docs.
- `network_mode: host` is required on the VPS. With published ports, Docker forwards traffic through its own chains and the per-peer nftables rules in TASK-1802 would not see it.
- `network_mode: host` cannot be combined with `ports:`.
- The mount path `../../docker/lavalink/application.yml` is relative to `deploy/lavalink/`, so the deploy keeps the repository layout.
- Keep the `LAVALINK_PASSWORD:?` check in the base compose: the bot still needs it.

**Out of scope**
- Host scripts and CI (TASK-1802, TASK-1803).
