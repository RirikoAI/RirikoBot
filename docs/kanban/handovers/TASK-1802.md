## GROOMING · 2026-10-04T18:58:43Z · Claude Code (Opus 5.5)

**Approach**
1. Add `--role` to `bootstrap.sh` and branch only where the roles differ: timers, directories, deploy keys, nftables.
2. Keys: `umask 077; wg genkey > /etc/wireguard/private.key` only when missing; print `wg pubkey < private.key`.
3. Config in `ririko.conf`:
   - `WG_ADDRESS=10.77.0.1/24`
   - `WG_LISTEN_PORT=51820` (lavalink role)
   - `WG_PEERS` as lines `<public key> <allowed /32> [<endpoint host:port>]`
   - `WG_ALLOWED_ENDPOINTS` as the Lightsail static IPs (lavalink role)
4. Rendering functions in `deploy/host/lib/render-wireguard.sh` and `render-nftables.sh`, sourced by `bootstrap.sh`. Validate keys (44-character base64 ending in `=`) and addresses before writing anything.
5. nftables: write `/etc/nftables.d/ririko.nft` with `table inet ririko`, load it with `nft -c -f` then `nft -f`, and enable a small systemd unit (or `include` from `/etc/nftables.conf` without `flush ruleset`).

**Pitfalls**
- Ubuntu's default `/etc/nftables.conf` starts with `flush ruleset`. Loading it after Docker starts wipes Docker's NAT rules. Never use the global flush; delete and recreate only `table inet ririko`.
- Allow established and related traffic first, or the host loses its own outbound connections (apt, Docker Hub, cloudflared).
- The VPS provider may have no network firewall in front of the VPS; nftables is the only boundary, so the default must be drop.
- Lightsail's firewall is stateful, so WireGuard replies to the outbound keepalive come back in without an inbound rule.
- Test on Windows too: the render functions must not depend on GNU-only flags beyond what Git Bash has.

**Out of scope**
- Deploy and watchdog changes (TASK-1803).

**Facts from the staging host**
- `ririko-staging` has the static IPv4 `203.0.113.10` and the IPv6 `2001:db8::10`. Both are its outbound addresses. Lightsail changes the IPv6 only when IPv6 is disabled and re-enabled.
- A Lightsail host prefers IPv6 when the WireGuard endpoint resolves to an IPv6 address, so its packets then come from the IPv6 address. Either:
  - set `Endpoint` to the VPS's IPv4 literal on the app hosts, or
  - let `WG_ALLOWED_ENDPOINTS` take IPv4 and IPv6 entries and render both an `ip saddr` and an `ip6 saddr` rule.

  Prefer the IPv4 literal; still validate and support both families in the renderer.

**Decisions & gotchas**
- `WG_PEERS` format. ririko.conf is `KEY=value` lines parsed without sourcing, so a multi-line list is not possible. Entries are separated by `;` (newlines also work in the renderers). Fields: `<public key> <peer ip>/32 [<endpoint host:port> | -] [<tcp ports, comma list> | -]`. The ports field gives each peer its own firewall ports (one or many), so production can move to its own VM by dropping a peer entry. On the shared VPS: `WG_PEERS="<prod key> 10.77.0.2/32 - 2333; <staging key> 10.77.0.3/32 - 2334"`. On an app host: `WG_PEERS="<VPS key> 10.77.0.1/32 198.51.100.20:51820"` (an IPv4 literal, so Lightsail connects from its IPv4 address). The VPS side: `WG_ALLOWED_ENDPOINTS="203.0.113.10"`; the renderer also takes the IPv6 address (`ip6 saddr` rule), in case it is needed.
- Nothing on a host changes until `ririko.conf` is filled in. Without `WG_ADDRESS` and `WG_PEERS`, the key is created, the public key printed and `wg0.conf` skipped with a warning. Without `WG_PEERS` and `WG_ALLOWED_ENDPOINTS`, the firewall step leaves the host exactly as it is, so the interim table keeps protecting the VPS. Flow for lavalink-staging: run once with `--role lavalink`, read the public key, fill `WG_ADDRESS=10.77.0.1/24`, `WG_PEERS` and `WG_ALLOWED_ENDPOINTS`, run again.
- Firewall order: render, `nft -c -f` on the temp file (nothing is installed if it fails), `sync_file` to `/etc/nftables.d/ririko.nft`, install and enable the unit, `systemctl restart ririko-firewall.service` (only when something changed, the unit is inactive, or the table is not loaded), verify with `nft list chain inet ririko input | grep 'policy drop'`, then `remove_interim_firewall` (disable and stop `ririko-firewall-interim.service`, remove the unit and `/etc/ririko/firewall-interim.nft`, `nft delete table inet ririko_interim`, daemon-reload), then verify again, and reload `ririko-firewall.service` if the interim service's own stop took our table with it (I do not know that unit's `ExecStop`). Docker's tables are never touched. `nftables.service` is neither enabled nor disabled, and our unit orders itself after it, so its stock `flush ruleset` cannot run later.
- SSH reaches the VPS only through the tunnel on loopback, so the table has no port 22 rule (as the interim table). A bootstrap run over a plain public-IP SSH session survives the load (established is accepted), but a new one would not.
- The forced commands of the two lavalink keys carry an argument (`ririko-deploy-ssh staging`). `bin/ririko-deploy-ssh.sh` ignores positional arguments today and reads `SSH_ORIGINAL_COMMAND`, so nothing breaks. TASK-1803 must read `$1` there (and map it to the instance) when it adds the Lavalink role to the deploy scripts. I did not touch that script.
- The watchdog on the Lavalink host does nothing until TASK-1803: it only looks at compose project `ririko`, and the Lavalink compose project is `ririko-lavalink`.
- `shellcheck source=/dev/null` is used on the three `. "$SRC/lib/..."` lines: CI runs shellcheck from the repository root, where a relative `source=` path is reported as unfollowable (SC1091). The libs are shellchecked on their own.
- The lavalink role still creates `/opt/ririko`, `releases`, `state` and `/etc/ririko` (TASK-1803 decides what its deploy script needs); only the backup directories are app-only.
- The Edit tool on this Windows checkout writes CRLF into the files it touches. I normalized `bootstrap.sh` and the libs back to LF (the repository test fails on any CR). Re-check with `tr -cd '\r' < file | wc -c` after editing these files with Edit.
