## 1. Summary of Work Accomplished

### 1.1. Root Cause & Problem
Previously in `apps/bot/src/services.ts`, canonical equipment and items were seeded with:
```ts
for (const item of CANONICAL_ITEMS) {
  const exists = await gameItemRepo.findByCode(item.code);
  if (!exists) {
    await gameItemRepo.create(item);
  }
}
```
Because the loop only inserted rows if `!exists`, any future balance patches, stat tweaks, price alterations, or copy/description changes to items in `CANONICAL_ITEMS` were silently ignored for any database that had already booted once. Furthermore, naive overwrites or delete-and-reinsert strategies would mutate or destroy existing `game_items.id` primary keys, breaking foreign keys in `user_inventory_items` (`item_id`).

### 1.2. Solution & Design Decisions
1. **`syncCanonicalItems` in `packages/services/src/waifu-tcg/equipment/catalog.ts`**:
   - Introduced `syncCanonicalItems(itemRepo: GameItemRepository, items = CANONICAL_ITEMS): Promise<{ created: number; updated: number }>`.
   - If an item code is not found in the DB, it creates it via `itemRepo.create(item)`.
   - If the code already exists, it updates catalog-owned fields (`name`, `description`, `type`, `subtype`, `rarity`, `baseStats`, `battlePerks`, `consumableEffect`, `isShopBuyable`, `shopPrice`, `maxDailyPurchases`, `isTradeable`) via `itemRepo.update(exists.id, ...)`.
   - **Crucially preserves the primary key `id`**: player inventory items in `user_inventory_items` point to `exists.id`, so zero foreign key constraints or inventory references are invalidated.
2. **`apps/bot/src/services.ts`**:
   - Replaced the insert-only loop with `const { created, updated } = await syncCanonicalItems(gameItemRepo);`.
   - Added descriptive logging: `[tcg] Canonical items synced: X created, Y updated.`.
3. **Automated Verification (`packages/services/src/waifu-tcg/__tests__/catalog-sync.test.ts`)**:
   - Tested empty database creation: all items created.
   - Tested item update: catalog field changes (e.g. name, description, shopPrice, maxDailyPurchases) propagate cleanly while existing item `id` remains identical.
   - Verified that user inventory items referencing `itemId` continue pointing to the updated record without dissociation.
   - Tested partial and incremental syncing.

## 3. Roadblocks, Gotchas & Decisions Made

- **Catalog-Owned Fields**: Only intrinsic item definition fields from `CANONICAL_ITEMS` are updated. Runtime state, user inventories, card loadouts, and transaction histories are untouched.
- **Foreign Key Safety**: `GameItemRepository.update(id, ...)` uses the existing UUID `id`, ensuring SQLite and PostgreSQL foreign keys in `user_inventory_items(item_id)` remain 100% stable.
