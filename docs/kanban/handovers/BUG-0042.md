## GROOMING · 2026-10-10T10:27:59Z · claude-opus-5-5 (coordinator)

**Report**: CircleCI `docker` job 2109 on PR #693, step "Smoke-check both images" (`node scripts/docker-smoke.ts bot web`):
```
[web] health probe: dashboard not available: Error [SchemaNotReadyError]: The database schema is behind this dashboard: 1 pending migration(s) (0000_baseline). ...
1 check(s) failed.
```

**Root cause**
- TASK-1854 made `getDatabase` (`apps/web/src/lib/server/services.ts`) reject with `SchemaNotReadyError` while the schema is behind.
- `webProbe` (`apps/web/src/lib/server/health.ts`) answers 503 for both `health` and `ready` when `deps.database()` rejects.
- `webServeCheck` (`scripts/docker-smoke.ts:520`) starts the web image alone on an empty database, so nothing migrates it. It expects 200 from `/health`, `/ready`, `/api/health` and the HEALTHCHECK, and a sign-in redirect.
- ADR-015 decision 6 asks only readiness to wait. A failing liveness probe marks the container unhealthy, and `ririko-watchdog` restarts unhealthy containers.

**Approach**
- In `webProbe`, catch `SchemaNotReadyError` (it carries `pending`):
  - `health`: 200, with `database: { status: 'MIGRATION_PENDING', pending }`;
  - `ready`: 503, and log the message.
- Keep every other failure as it is today.
- `webServeCheck`:
  - First, start the web image on an empty database and assert liveness 200, readiness 503 and the log line.
  - Then build a migrated SQLite file in a throwaway `ririko-bot:smoke` container: `DATABASE_URL=/tmp/m/ririko.sqlite ririko db:migrate`, then `docker cp <container>:/tmp/m -` to get a tar. Follow `buildLegacyDatabase` and `firstTarFile` for the tar handling.
  - Copy it into `/app/data/ririko.sqlite` of a second web container through the `prepare` hook. Mind file ownership: the image runs as a non-root uid (see how the legacy check handles it).
  - Assert the original expectations on that second container.

**Pitfalls**
- Docker is not running on the maintainer's machine, so the smoke script cannot run locally. Keep it type-checked and linted. CircleCI's `docker` job is the proof, and the coordinator checks it after the push.
- Keep the probe bodies free of anything sensitive (the dashboard is public): ids of pending migrations are fine.

**Out of scope**
- The bot's probes. The bot exits on a migration failure; that is by design.

**Decisions & gotchas**
- Tar handling and ownership, reasoned from `buildLegacyDatabase` and `firstTarFile`: the legacy builder runs as root and copies a folder, so entries land under `/app/legacy`. Here the builder runs as the image user (uid 10001) and copies the single file, so the tar has one entry, `ririko.sqlite`, extracted straight into `/app/data` (owned by 10001 in the image). `docker cp` without `-a` writes the file as root, so the copy uses `-a` (keeps uid 10001 from the tar header) and the builder also runs `chmod 666` on the file, so even a root-owned copy can be opened for writing by the app user; WAL files are created by the app user in the writable directory. `firstTarFile` is used only to confirm the copy is a non-empty regular file.
- `SchemaNotReadyError` is also thrown for the downgrade guard (unknown contract migrations, `pending` is empty). It also gets liveness 200 now with `MIGRATION_PENDING` and an empty list, as the ticket says to catch the error class. Restarting would not help in that case either, but the status name is slightly off; a separate status could be added later if the coordinator wants it.
- If `docker cp -a -` should turn out to be rejected on CircleCI's remote engine, the fallback is to drop `-a` (the `chmod 666` already covers it).
- The smoke script keeps `/api/ready` in both states; the route exists (`apps/web/src/app/api/ready/route.ts`).
