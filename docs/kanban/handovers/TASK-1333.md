## GROOMING · 2026-10-09T18:04:50Z · claude-opus-5-5 (coordinator)

**Request (user, 2026-10-10)**
For the welcome card and the farewell card, including the dashboard, add a checkbox and a configurable text box for a text message sent to the card's channel. Example from the user: `Welcome to the server, {user}! Please read the rule here #channel`.

**Approach**
1. **Schema.** Add `textMessageEnabled` (`text_message_enabled`, boolean, NOT NULL, default false) and `textMessage` (`text_message`, text, NOT NULL, default `''`) to `guildWelcomer` and `guildFarewell`. Do this in both `packages/database/src/schema/sqlite/utilities.ts` (around line 93) and `packages/database/src/schema/pg/utilities.ts` (around line 95). Regenerate both DDL files with `pnpm -F @ririko/database db:generate-ddl`. `WelcomeConfig` and `FarewellConfig` are inferred types, so they pick the fields up. The repository needs no change, because it upserts whole rows.
2. **Rules** in `packages/core/src/config/welcomer.ts`, next to `WelcomerMessageSetting`:
   - `MAX_WELCOMER_TEXT_LENGTH = 2000`.
   - `WELCOMER_TEXT_VARIABLES = ['user', 'username', 'server', 'memberCount']`.
   - `WelcomerTextSetting`: trimmed, may be empty, at most 2000 characters.
   - Add `textMessageEnabled: FlagSetting` and `textMessage: WelcomerTextSetting` to the `welcome` and `farewell` objects in `guild-config.ts` (around line 417).
   - Reject "on with an empty message" with a `superRefine` on those objects, or in the store's `check`. Pick whichever path reports the error under the `textMessage` field on the dashboard and in the CLI; see how `escalationSteps` errors reach the form.
3. **Store.** `welcomerCardStore` (`packages/services/src/guild/guild-config.service.ts:225`) reads both fields with safe defaults (false and `''`) and writes them. Check the other `WelcomeConfig` literal in `runWelcomerCardCommand` (`welcomer-card.ts:150`); it must carry the new fields too, or TypeScript will fail.
4. **Fill and resolve.** In `packages/services/src/welcomer/welcomer.service.ts`, add a pure helper next to `fillWelcomerMessage`, for example `fillWelcomerText(template, { user, username, serverName, memberCount, channels })`.
   - `channels` is a list of `{ id, name }` for the server's text channels.
   - Replace placeholders first. Then replace each `#name` that exactly matches a channel name with `<#id>`. Discord channel names are lowercase with no spaces, so the token is `#[a-z0-9_-]+`, compared case-insensitively.
   - Leave `<#123>` untouched, and leave unknown `#words` as typed.
   - Keep `fillWelcomerMessage` for the card text. The card has no mentions.
5. **Send.** In `registerMemberListener` (`apps/bot/src/listeners/member.listener.ts`, the welcome send around line 80 and the farewell send around line 117):
   - When `textMessageEnabled` is on and the message is not empty, add `content` to the existing `send({ files })` call.
   - Welcome: `{user}` = `<@member.id>`, with `allowedMentions: { users: [member.id] }`.
   - Farewell: `{user}` = username, with `allowedMentions: { parse: [] }`.
   - Build `channels` from `member.guild.channels.cache` (text-based channels only).
6. **Commands** (`apps/bot/src/commands/utility/welcomer-card.ts`):
   - Add `textMessage` to `CardChanges`.
   - Slash: a `text` STRING option on `/welcomer` and `/farewell`. A message sets the text and turns it on; `none` turns it off and keeps the stored text.
   - Prefix: the `text <message>` and `text none` actions in `readChanges`.
   - Validate with the same core schema in `problemWith`, and show the text state in the summary reply.
   - Discord's limit is 100 characters for an option description.
7. **Dashboard.** In `card-page.tsx`, add `ToggleField name="textMessageEnabled"` ("Also send a text message") and `TextAreaField name="textMessage"` (maxLength 2000, rows 3) after the card message field. The description lists the placeholders and explains `#channel-name`. In `actions.ts` `saveCardSettings`, add `textMessage` to `text` and `textMessageEnabled` to `flag` in `readFormFields`. Under the preview, show the filled text when it is on: use the viewer as `{user}`, and leave `#names` as typed.
8. Update `docs/modules.md`, in the welcomer section.

**Pitfalls**
- **Existing databases need `pnpm db:push`** for the two new columns on both tables. The user runs `next dev` on :3000 from this checkout; it breaks on the new columns until db:push runs. Say so in the PROGRESS entry.
- The listener tests and `migration.test.ts` create tables from the generated DDL. If the DDL is not regenerated, the inserts fail.
- `exactOptionalPropertyTypes` is on. Build `allowedMentions` and `content` without `undefined` values.
- The farewell `member` can be partial: `member.user` may be missing. Keep the current `'Unknown User'` fallback for `{user}` and `{username}`.
- Replace placeholders before you resolve `#channel`. This way a server name like "#general fans" put in through `{server}` could still be resolved, which is acceptable. Never mention-resolve inside a user-supplied `{username}`: apply the channel step to the template before you insert the username, or escape the values. Pick one approach and test it.
- A ping must never escape. `allowedMentions` is the guard; do not rely on stripping `@everyone` from the text.
- Discord rejects message content over 2000 characters. Mentions are longer than names, so resolving `#name` to `<#id>` can push a 2000-character template over the limit. Cap the content after filling.

**Out of scope**
- A text-only mode with the card off. The text rides on the card message; the card's `enabled` switch still gates both.
- Embeds, role mentions, or `{channel}`-style placeholders beyond those listed.
- Migrating any 1.4.0 welcome text. The legacy schema has no such field.
- Changing the card renderer or the 200-character card message.

  3. Review the SQL. It must only add things: `ALTER TABLE ... ADD COLUMN ... DEFAULT ...` for the four columns.
  4. Commit the migration files, the snapshots, the embedded modules and the DDL.
- `pnpm db:check` must pass. It is now part of `verify_cmd`.
- The pitfall about `db:push` and the maintainer's `next dev` changes: the bot, or `ririko db:migrate`, applies the migration to the local database. Staging gets it on its next deploy through the gated step (STORY-186), or on bot start before STORY-186 lands.
