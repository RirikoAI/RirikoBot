## GROOMING · 2026-10-04T18:50:17Z · Claude Code (Opus 5.5)

**Approach**
1. `deploy/host/bin/ririko-deploy-ssh.sh` (runs as `deploy`): split `SSH_ORIGINAL_COMMAND` with `read -r -a`, require exactly `deploy <version>` or `status`, check the version regex, then `exec sudo -n /usr/local/bin/ririko-deploy "$@"`.
2. `deploy/host/bin/ririko-deploy.sh` (runs as root): the steps in the acceptance list, in that order. Read defaults from the environment, then `/etc/ririko/ririko.conf`: `RIRIKO_REPO=RirikoAI/RirikoBot`, `RIRIKO_ENV_FILE=/opt/ririko/.env.production`, `READY_TIMEOUT=300`, `RIRIKO_LOCK=/run/lock/ririko-deploy.lock`.
3. Compose call: `RIRIKO_VERSION=<v> RIRIKO_ENV_FILE=<env> docker compose -p ririko -f <release>/docker-compose.production.yml --env-file <env> ...`. The compose file mounts `./docker/lavalink/application.yml`, which resolves from the release directory.
4. Readiness:
   - bot: `docker compose exec -T bot node -e "fetch('http://127.0.0.1:'+(process.env.HEALTH_PORT||8080)+'/ready').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"`;
   - web: the same against `http://127.0.0.1:3000/api/ready`.
5. Add the config keys to `deploy/host/ririko.conf.example` with comments.
6. Tests in `scripts/deploy-host.test.ts`: a temporary `RIRIKO_ROOT`, a fake `docker` that logs its argv to a file and fails on demand, and a fake `curl` that writes the two files.

**Relevant code**
- `scripts/release-tags.ts:14` `RELEASE_TAG_PATTERN` allows any prerelease suffix (`-.+`). The host regex is deliberately stricter because the version becomes part of a URL and a path.
- `apps/bot/src/health.ts:41-82` `probe` and `healthPort`.
- `apps/web/src/lib/server/health.ts:18` `webProbe`; the routes are `apps/web/src/app/api/ready/route.ts` and `/api/health`.
- `Dockerfile:99-122`: the HEALTHCHECK commands use the same `node -e fetch` approach, because the images have no curl.

**Pitfalls**
- Lock exit 3, rollback exit 4, failed first deploy exit 5, rejected command exit 2. TASK-1782 documents these, so keep them stable.
- Use plain files for `state/current` and `state/previous`; symlinks behave differently under Git Bash on Windows, where the tests also run.
- `docker compose exec` fails while a container restarts. Treat any error as not ready and keep polling.
- `sudo` resets the environment. Pass the words as arguments, never through environment variables.
- The bot's `/ready` needs a valid Discord token, so staging needs its own Discord application.
- Rolling back the image is safe only while schema changes are additive (`ensurePostgresSchema`). The exit message must name the pre-deploy dump for a manual restore.

**Out of scope**
- CircleCI changes (TASK-1782). Locking for backup and watchdog (TASK-1791, TASK-1792), apart from defining the lock path.

## PROGRESS · 2026-10-04T22:10:00Z · claude-medium (Claude Sonnet 5.5) · REVIEW

**Files changed**
- `deploy/host/bin/ririko-deploy-ssh.sh` (new, the forced command): one anchored regex over the whole `SSH_ORIGINAL_COMMAND` (`status` or `deploy <version>` with the ticket's version pattern, `LC_ALL=C`), so a newline, extra word or shell character anywhere rejects it with `command not allowed` and exit 2. Then `exec sudo -n /usr/local/bin/ririko-deploy "${words[@]}"` with the words split by `read -r -a`.
- `deploy/host/bin/ririko-deploy.sh` (new, root). `deploy <version>`: validate the version (exit 2), require root only when `RIRIKO_ROOT` is the real `/opt/ririko`, `flock -n` on `RIRIKO_LOCK` (exit 3), read `ririko.conf`, validate it, download, dump, apply, record state. `status`: prints `current=… previous=…` and `docker compose ps` of the current release. Everything is logged with a UTC timestamp to stdout and `/opt/ririko/deploy.log`.
  - Config: `ririko.conf` is parsed, never sourced (known keys only: `RIRIKO_REPO`, `RIRIKO_COMPOSE_FILES`, `RIRIKO_ENV_FILE`, `READY_TIMEOUT`; single or double quotes stripped; the file wins over the environment). Repo, compose file names (relative, no `.`/`..`), timeout and poll interval are validated before anything is downloaded; the env file must exist.
  - `download_release <version> <files…>`: curl (`--fail --proto =https`, retries) into `releases/.tmp.XXXXXX`, repository layout kept, every file must be non-empty, then the directory replaces `releases/<version>/` in one `mv`. It writes `.compose-files` (the list used) into the release, which is how a later pre-deploy dump or rollback finds that release's files even if `RIRIKO_COMPOSE_FILES` changed meanwhile. Stale `.tmp.*` directories are removed at the start of each run.
  - Dump: only when `state/current` names a release directory and `ps --status running --services` (with the running release's files) lists `postgres`; `exec -T postgres sh -c 'exec pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB"'` into `backups/predeploy/<UTC>-from-<current>.dump.part` (umask 077), moved into place when non-empty; exit 1 before any pull on failure; the newest 5 `*.dump` are kept.
  - `compose()` is `env RIRIKO_VERSION=… RIRIKO_ENV_FILE=… docker compose -p ririko -f <release>/<file>… --env-file <env> …`; `apply_release` = `pull`, `up -d --no-build --remove-orphans`, `wait_ready`. `wait_ready` runs `exec -T bot node -e fetch(…/ready)` (HEALTH_PORT from the bot's own env, default 8080) and `exec -T web node -e fetch(http://127.0.0.1:3000/api/ready)` (4 s abort per fetch) every `READY_POLL_SECONDS` (default 5) until `READY_TIMEOUT` (default 300); any exec error counts as not ready.
  - Success writes `state/previous` (only when the old current differs) then `state/current`, as plain files. Failure prints `docker compose ps` and `logs --tail 100 bot web`, then with a different current release starts that release the same way (pull failure tolerated, no new dump) and exits 4 with a message naming the pre-deploy dump and saying the database was not restored; with none (first deploy, or redeploying the current version) exits 5.
  - `download_release`, `compose`, `apply_release` and `wait_ready` take the version and file list as arguments, so TASK-1802/1803 can call them for the Lavalink role.
- `deploy/host/ririko.conf.example`: the four keys with defaults, commented out, plus the Lightsail remote-Lavalink value of `RIRIKO_COMPOSE_FILES`.
- `scripts/deploy-host.test.ts`: 23 new tests (43 in the file). Each scenario is one bash script fed through stdin that writes the scripts under test and fake `docker`, `curl`, `sudo` (and a no-op `flock` where the host bash has none, as Git Bash) into `mktemp -d`, so it runs the same with Git Bash, WSL and Linux bash. Covered: 19 forced-command cases (16 rejected, 3 accepted, including `latest`, `2.1.3;id`, `../x`, empty, a newline, `status\n`); direct rejects (exit 2, nothing touched); first deploy (URLs, layout, exact compose calls, probes, state, log timestamps); upgrade with the two-file `RIRIKO_COMPOSE_FILES`, dump ordering and 5-dump pruning; same-version redeploy; rollback exit 4 (dump named, second `up` for the old version, no second dump, state unchanged); first-deploy failure exit 5 (dashboard never ready); retry until ready; dump failure exit 1 before pull; missing tag and missing file leave everything unchanged; busy lock exit 3 (skipped without a real `flock`); six invalid `ririko.conf` values; a custom `RIRIKO_REPO`; `status` with and without a deployment; and wiring checks (file names, conf example keys).

**Verification**
- `verify_cmd` passes (Git Bash): `pnpm vitest run scripts` 5 files, 87 tests passed, 1 skipped (the lock test, Git Bash has no `flock`); `pnpm lint --quiet` clean; `pnpm format:check` clean.
- From PowerShell (WSL bash, real `flock`): `pnpm vitest run scripts/deploy-host.test.ts` 43 tests, none skipped.

**Decisions & gotchas**
- Exit 1 is used for every failure that leaves the running release untouched (bad tag or file, dump failure, invalid config, missing env file, not root); TASK-1782 should document 0/1/2/3/4/5.
- `ririko.conf` wins over the environment, so the test overrides go through a conf file in a temporary directory; the env overrides the ticket lists (`RIRIKO_ROOT`, `RIRIKO_CONF`, `RIRIKO_LOCK`, `DOCKER`, `CURL`, `READY_POLL_SECONDS`) still work. The forced command has no override at all (tests put a fake `sudo` on PATH).
- No `HEALTH_PORT` conf key: the bot probe reads the bot container's own `HEALTH_PORT`, so it follows the env file. `HEALTH_PORT=0` there turns the probes off and every deploy would fail; the conf example says so.
- A same-version redeploy never rolls back (the running release is the one being replaced), so a failure exits 5; `state/previous` is kept.
- If the rollback itself does not become ready, the exit code is still 4 and deploy.log/stdout carry `ROLLBACK FAILED`.
- Old release directories are never pruned (they hold two small files). `bootstrap.sh` installs `bin/*.sh` to `/usr/local/bin/<name without .sh>` already.
- The scripts keep the repository's LF line endings (the existing no-CR test passes for both).
- `.idea/vcs.xml` left alone.

**New CodeGraph queries**
- None needed beyond the ticket's two (`releaseTags RELEASE_TAG_PATTERN release-tags.test`, `bot health server /ready readiness HEALTH_PORT web api ready route`); the second gave `probe`, `healthPort`, `webProbe` as groomed.
