## GROOMING · 2026-10-18T15:30:00Z · claude-opus-5-5 (coordinator)

**Approach**
1. New workspace app `apps/starter` (`apps/*` is already in pnpm-workspace.yaml), TypeScript built with `tsc` like `apps/cli`; source in `apps/starter/src/` so the coverage config (`apps/*/src/**`) counts it. Package name `ririko`, not private, no runtime dependencies: Node's `fetch`, `node:child_process`, `node:readline/promises`, `node:fs`.
2. Keep the logic testable: pure functions for argument parsing, release lookup (fetch injected), and building the command list for each path; a thin `main` runs them.
3. Release lookup: `GET https://api.github.com/repos/RirikoAI/RirikoBot/releases/latest`; if there is none (v2.0.0 may have no GitHub Release yet), `/tags`, keep `^v\d+\.\d+\.\d+$`, take the highest by version. Send a User-Agent header. Rate limits and network errors give a clear message.
4. Docker path: mirror docs/deployment.md 2.3 to 2.7 without `git clone`: download the files that `docker-compose.production.yml` needs from `https://raw.githubusercontent.com/RirikoAI/RirikoBot/<tag>/...`, run the wizard one-liner from 2.4 with the exact image version, ask, then start.
5. Source path: `git clone --branch <tag> --depth 1 https://github.com/RirikoAI/RirikoBot.git <folder>`, enable pnpm through corepack, `pnpm install`, `pnpm installer`.

**Relevant code**
- `apps/cli/src/commands/setup.ts` `registerSetupCommand`: the wizard options (`--docker`, `--env-file`, `--listen`, `--no-open`, `--port`) and `PROFILE_FILES`.
- `docs/deployment.md` 2.3 to 2.7: the steps the Docker path automates; the wizard one-liner is in 2.4.

**Pitfalls**
- Check which files the compose file bind-mounts (for example Lavalink config under `docker/`); a missing file makes `docker compose up` create a directory in its place.
- Windows: spawning `docker`, `git`, `corepack` and `pnpm` needs `.cmd` resolution or `shell: true` on win32. The wizard one-liner uses `$PWD`; build the volume path with `resolve()` instead.
- The wizard runs in a container with `--listen 0.0.0.0` and `-p 127.0.0.1:3999:3999`: keep the host side on 127.0.0.1.
- Tests run offline (vitest.setup.ts network guard): never call the real API in tests.

**Out of scope**: publishing, the npm README and docs (TASK-1962); any change to the bot, the wizard or the images.

**Design**
- Zero dependencies: global `fetch`, `node:child_process`, `node:readline`, `node:fs`. All outside effects go through the `StarterDeps` interface (fetch, run, ask, inspectFolder, writeFiles, fileExists, log, error, cwd, node version), so tests inject everything.
- Order in `runStarter`: parse args (help/version exit 0; error prints message and help, exit 1), check the folder (exists and not empty, or not a folder: exit 1, before anything else), choose the mode (`--docker`/`--source`, else ask with Docker as default; no terminal and no flag is an error), check tools (before any network call), find the release (`--ref` skips it), run the path.
- Release: `GET api.github.com/repos/RirikoAI/RirikoBot/releases/latest`; its `tag_name` is used only if it matches `^v\d+\.\d+\.\d+$`. On 404 or another tag shape, `/tags?per_page=100&page=N` (up to 5 pages), highest stable tag by number. Sends `User-Agent: ririko-starter/<version>`. Network error, 403/429 (rate limit), other HTTP errors and non-JSON answers each give a message that ends with the `--ref v2.0.0` hint and exit 1. `--ref` accepts `vX.Y.Z` and `vX.Y.Z-suffix` only (this also blocks a value that starts with `-`).
- Docker path downloads all four files first and writes them only if all arrived (a failure writes nothing). After the wizard it checks that `.env.production` exists in the folder; if not it stops with the "Download the file" advice, before `up`. The start question is `[Y/n]`; its text tells a remote-Lavalink reader to answer n and use the command on the wizard's last page. Without a terminal the answer is no, never a start.
- `docker compose up -d` gets `RIRIKO_VERSION=<X.Y.Z>` in the process environment only (compose reads `RIRIKO_VERSION` for the image tag, default `2`), so the stack runs the same version as the wizard image and the downloaded files. Nothing is written into `.env.production`; the final note says to set `RIRIKO_VERSION` there to pin it.
- Windows: `pnpm` and `corepack` are .cmd files, so on win32 they run through a shell with a single command string; each word must match `^[A-Za-z0-9_.:=@/-]+$` or the step does not start. `docker` and `git` are spawned directly. The wizard volume is the `resolve()`d folder, not `$PWD`. `COREPACK_ENABLE_DOWNLOAD_PROMPT=0` is set for corepack and pnpm.
- Failing step: `Step "<name>" failed with exit code <n>.` and the program exits with `<n>`; a tool that cannot start gives `could not start`. The `Enable pnpm` failure adds advice (corepack may need permission). No secret is read, printed or logged: the starter reads no settings file (it only checks that `.env.production` exists) and prints no environment value.

**Downloaded files (Docker)**, from `https://raw.githubusercontent.com/RirikoAI/RirikoBot/<tag>/<path>` into the folder (same relative paths):
