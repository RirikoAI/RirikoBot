## GROOMING · 2026-10-04T18:50:17Z · Claude Code (Opus 5.5)

**Approach**
1. In `packages/core/src/config/schema.ts`, export `ClientIpHeaderSchema` (`z.string().trim().toLowerCase().regex(/^[a-z0-9-]+$/).optional()`) and add `CLIENT_IP_HEADER: ClientIpHeaderSchema` to `BaseWebConfigSchema`.
2. In `apps/web/src/lib/server/auth/request.ts`, add a cached reader that parses `process.env.CLIENT_IP_HEADER` with `ClientIpHeaderSchema` once. When it is set, `clientIp` returns that header's trimmed value if `isIP` from `node:net` accepts it, else `null`, with no fallback. When it is unset, keep today's code path.
3. Keep the signature `clientIp(headers: Headers): string | null` so the nine callers stay unchanged. Give the test a way to reset the cache (an exported test-only reset, or read the env on each call; the parse is cheap, so reading per call is fine too).
4. Tests in `apps/web/src/lib/server/auth/request.test.ts` and the core schema tests.
5. Docs: `.env.production.example` (commented line with the warning), `.env.example`, `docs/deployment.md`.

**Relevant code**
- `apps/web/src/lib/server/auth/request.ts:24-32` `clientIp` and its comment. The comment says the value is informational and never used for authorization; it is used for rate-limit keys, so update the comment.
- `apps/web/src/lib/server/rate-limit.ts:74-89` `limitProbeRequest` and `limitAuthRequest` are synchronous and have no config access. This is why `clientIp` reads the env itself.
- `apps/web/src/lib/server/request-context.ts:17-33` `checkDashboardRequest` and `requestActor`.
- `packages/core/src/config/schema.ts:177-207` `BaseWebConfigSchema` and `WebConfigSchema`.

**Pitfalls**
- Cloudflare appends the connecting address to any X-Forwarded-For the client sent, so the first entry is attacker-controlled behind Cloudflare. `CF-Connecting-IP` is set by Cloudflare alone.
- The setting is only safe when the dashboard port is unreachable except through the tunnel (TASK-1761 binds it to loopback). Say so in the docs.
- Requests without the header (the container HEALTHCHECK, the deploy readiness poll) get `null` and share the `ip:unknown` bucket; the probe limit (30 burst, 1/s) covers them.
- `exactOptionalPropertyTypes` is on.

**Out of scope**
- Changing the rate-limit sizes or keys.

## PROGRESS · 2026-10-04T19:45:00Z · worker-sonnet-1762 (Claude Sonnet 5.5) · REVIEW

**Files changed**
- `packages/core/src/config/schema.ts`: exported `ClientIpHeaderSchema` (trim, lower-case, `/^[a-z0-9-]+$/`, optional; a blank value is preprocessed to unset so `CLIENT_IP_HEADER=` in an env file does not stop startup) and added `CLIENT_IP_HEADER` to `BaseWebConfigSchema`.
- `apps/web/src/lib/server/auth/request.ts`: `clientIp` stays synchronous. A private `trustedClientIpHeader()` reads `process.env.CLIENT_IP_HEADER`, parses it with `ClientIpHeaderSchema` and caches the result keyed by the raw value (so tests can change the env without a reset export). When set, `clientIp` returns that header's trimmed value only if `isIP` accepts it, else `null`, with no fallback. A malformed value fails closed (`null`). When unset, the old X-Forwarded-For / X-Real-IP path is untouched. Comment rewritten.
- `apps/web/src/lib/server/auth/request.test.ts`: 7 new tests (spoofed XFF ignored, invalid value null, missing header null with no XFF/X-Real-IP fallback, IPv6, case/trim, malformed env fails closed, changed/blank env). Existing tests unchanged.
- `packages/core/src/config/client-ip-header.test.ts` (new): schema trims/lower-cases, blank is unset, rejects spaces/underscores/colons/commas, `WebConfigSchema` default, normalisation and startup failure.
- `.env.production.example`, `.env.example`, `docs/deployment.md` (Hardening list): documented, with the Cloudflare-only warning.
