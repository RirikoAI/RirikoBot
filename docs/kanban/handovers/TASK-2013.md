## GROOMING · 2026-10-22T06:10:00Z · claude-opus-5-5 (coordinator)

**Approach**
1. `packages/services/src/starboard/`:
   - `starboard.service.ts`
   - `embeds.ts`: the pure copy builder, easy to unit test
   - `types.ts` and `index.ts`
   - Export it all from the services index.
2. The settings cache is a copy of the LevelRoleService one.
3. Find the reaction with `message.reactions.cache.find(r => matches(r.emoji, parsed))`. For custom emoji compare the id. For Unicode compare the name with U+FE0F removed.
4. Counting:
   - Start from `reaction.count`.
   - Bot reactions: only Ririko's own matter in practice. If `reaction.me` is true, subtract 1.
   - Self-star: when allowSelfStar is off and the count is at or above the threshold, fetch the reactors with `reaction.users.fetch()`. If the author is among them, subtract 1.
5. Queue: a `Map<messageId, Promise>` chain. Remove the entry when its chain is done.
6. The copy:
   - Send it to the starboard channel, and resolve it from the guild cache.
   - Skip when the channel is missing or not text-based.
   - Edit it with `channel.messages.edit(id, ...)`, or fetch it first. If the copy is gone (Unknown Message), treat it as removed by staff.
7. `messageDeleted(guildId, messageId)`: look the ID up as an original first, then as a copy.

Never throw. Never log message content.

**Public API** (`@ririko/services`)
- `new StarboardService({ repo, guilds, cacheTtlMs?, now? })`. `repo` is a `Pick` of `StarboardRepository` (`getSettings`, `findByMessage`, `findByStarboardMessage`, `insertPost`, `updatePost`, `deletePost`). **`guilds` is new and not in the groomed plan**: `{ cache: { get(guildId) } }`, so TASK-2014 passes `client.guilds`. It is needed because `messageDeleted(guildId, messageId)` takes IDs only and must reach the starboard channel to delete the copy.
- `invalidate(guildId?)`: drops one server or all (TASK-2014 calls it on `guild:configChanged` for module `starboard`).
- `reactionChanged(message: Message)`: pass the fetched `Message` (a partial has no author or reactions). Covers add, remove, remove-all and remove-emoji.
- `messageDeleted(guildId, messageId)`.
- Also exported: `buildStarboardEmbed(message)`, `formatStarboardContent(emojiText, count, channelId)`, `STARBOARD_COLOR`, types `StarboardConfig`, `StarboardServiceOptions`.

**Acceptance**
1. Settings cached per server for 5 minutes (`cacheTtlMs`, `now`), `invalidate(guildId?)`; a server with no row or no channel is cached as off; a failed read is logged and not cached. Every public method runs through a guard and cannot throw. Logs hold guild, channel and message IDs and the error text only (a test checks that message content is absent).
2. The reaction is found in `message.reactions.cache` by `parseStarboardEmoji` (custom: by id; Unicode: name without U+FE0F). Count starts at `reaction.count` minus Ririko's own reaction. Only when that could reach the threshold are the reactors read (pages of 100, at most 10 pages), and every bot reactor and (unless `allowSelfStar`) the author are taken off. If the reactors cannot be read, nothing changes and the error is logged. No matching reaction counts as 0, which removes an existing copy (remove-all).
3. Skips: no guild, webhook, system message, starboard off, message in the starboard channel or an ignored channel (a thread follows its parent), starboard channel missing or not text, NSFW source with a non-NSFW starboard (a thread follows its parent's NSFW flag).
4. At or above the threshold with no row: send, then `insertPost`. If `insertPost` returns false or throws, the just-sent copy is deleted. With a row: `messages.edit(copyId, { content })` only when the count changed. Below: delete copy, then row. A row with `removed` is never touched. A row with no copy id is sent again. Per-message-ID promise chain (`queues` map, entry removed when the chain ends), shared by `reactionChanged` and `messageDeleted`.
5. `messageDeleted`: an original deletes the copy and the row (a removed row or one with no copy only loses the row); a copy marks its row `removed`. A row of another guild is ignored.
6. Copy: embed with the author name (nickname first) and avatar, content cut to 4096, first image attachment (by content type, else by file extension) or image/gifv embed as the image, other attachment names, a Source field with `<#channel>` and a jump link; content line `<emoji> <count> | <#channel>`; `allowedMentions: { parse: [] }` on sends and edits.
7. Tests: 75 in `starboard/__tests__` covering counting, each skip rule, post, edit, remove, removed rows, the queue (a burst posts once; a delete waits for a post), original and copy deletion, failed sends/edits/deletes, and the embed.

**Verify** `pnpm vitest run packages/services/src/starboard && pnpm --filter @ririko/services typecheck && pnpm lint --quiet && pnpm format:check` passes (2 files, 75 tests). Coverage of `starboard/` alone: statements 99.2%, branches 96.6%, functions 98.6%, lines 99.5%. Not run: the whole `pnpm test:coverage` and `pnpm build`.

**Notes for the coordinator**
- Choices that go beyond the groomed text: the `guilds` option (above); other bots are not counted when the reactors are read (acceptance said "bot reactions are not counted"); a failed reactor read changes nothing; a copy that cannot be deleted for another reason than Unknown Message keeps its row so the next event retries; a failed edit with Unknown Message marks the row removed (staff deleted the copy while the bot missed the event).
- `messageDeleted` finds the copy in the channel of the **current** settings. If an admin changed or cleared the starboard channel after posting, the old copy is not deleted (the row still is). Rows do not store the starboard channel id.
- When the service deletes a copy itself, the gateway sends a delete event for it. That event finds the row only if the row is not yet deleted, and then marks it removed just before the row goes; the outcome is the same. TASK-2014 does not need to filter these.
- TASK-2014 should call `reactionChanged` with a message fetched with `message.fetch()` when it is partial, and `reaction.message.reactions` is updated by discord.js on every event, so the cache read is current. For remove-all/remove-emoji events the cache is already cleared.
