## GROOMING · 2026-10-12T16:25:21Z · claude-opus-5-5 (coordinator)

**Approach**
1. Inventory first: list every column in `packages/database/src/schema/sqlite/*.ts` that stores a Discord user id (names like `user_id`, `owner_id`, `target_id`, `moderator_id`, `actor_user_id`, `requested_by`, `host_id`, `winner`, `from_user`/`to_user`; check each file, the names vary). Grooming counted user-keyed columns in adventure, ai, economy, games, giveaways, identity, images, moderation, music, tcg, utilities, web and xp. Put the inventory in a typed constant (table, column, action) that the command and the guard test share.
2. CLI command in `apps/cli/src/commands/`, registered in `createProgram`, styled after `passkeys-reset` (it opens the database the same way and writes an audit entry).
3. Plan, print, then apply with `--yes` in a transaction.

**Pitfalls**
- The economy ledger is double-entry: deleting one side breaks balances. Tombstone the id instead.
- Trades and giveaways involve other users: tombstone.
- Never print or log the raw user id in the audit entry.

**Out of scope**
- A dashboard page or a bot command for self-service erasure.

**Decisions & gotchas**
- No schema change: the inventory and the tombstone strings fit the existing columns (`varchar(32)`; the marker is 23 characters).
- **The tombstone is a pseudonym, not full anonymisation.** `erased:<16 hex digits of SHA-256(id)>` is the same for the same user. It is what the acceptance asks for, but a Discord ID is a guessable snowflake: someone who suspects an ID can check it against the marker. If the maintainer wants true anonymisation, the marker needs a host secret as salt (HMAC), at the price that the audit `subject` could not be recomputed from an ID without that secret. Decision for the review.
- `--include-moderation` is my reading of "kept unless". With it, cases about the user get a tombstone (the case number sequence stays complete), notes and warnings about the user are deleted, and `moderation_cases.metadata` is scrubbed. The moderator and author side is always tombstoned. The `reason` and `content` free text is not touched.
- Pending trades (my addition, not in the acceptance): cards are locked `IN_TRADE` on both sides at proposal, so deleting the user's cards without cancelling the trade would leave the other party's cards locked for ever. The plan shows them as `cancel` on `card_trades.status`.
- Waifu guilds led by the user alone are deleted (a guild name is user-chosen text); the others keep their members and lose the leader's ID.
- `audit_logs` rows of the user also lose `ip_address` and `user_agent`.
- The bot keeps `ConsentService` acceptances in memory (TASK-1931), so an erased user may not see the terms notice again until the bot restarts. This is documented in `docs/development.md`.
- The command prints the user ID it was given (the host typed it); only the audit entry avoids it.
- `ririko user erase` is a command group, unlike the colon style (`passkeys:reset`), because the ticket and the acceptance name `ririko user erase <discordUserId>`.
- `$TEMP` is shared between sessions on this machine. My logs there are named `t1941-*`, but my verify run wrote `lint.log`, `build.log`, `typecheck.log`, `vitest.log` and `format.log` there (scratch files, overwritten).
